# 怎样给并行测试提速

拿到慢用例，先写出它要抓住的具体错误。再逐项检查最耗时的动作对抓住这个错误有什么作用。例如，验证“批准后只重试评审”时，提供开发报告和失败的评审结果，运行真实的挂起、批准与恢复逻辑。断言角色调用顺序为“开发、评审、评审”，就能抓住重复启动开发者的错误。[评审状态用例](../../tests/test_sde_executor.py)

## 找出值得改的动作

用开发者日常等待的整条命令建立基线。记录提交、机器和并行配置，从命令启动计时到退出。在 Hibernaut 仓库根目录运行下列命令。

```sh
uv run --locked --extra dev pytest -n auto --dist worksteal -q
```

另跑一次带 `--durations=0 --durations-min=0` 的全量测试。看单例耗时，找出一次执行代价高的用例。按文件累计各个 worker 的耗时，找出单次很短却反复执行的操作。再看最后几个 worker 在跑哪些用例，定位拖长收尾的工作。按 `(nodeid, phase)` 汇总时，每个阶段只计一次，避免把子测试耗时又加到父用例。

把候选用例拆成准备、执行、等待和清理，分别计时或计数。例如终端用例很慢，可以分别测启动 shell、等待结果、关闭终端各花了多久。找到最慢的动作后，想一想，如果把它的结果作为现成输入，原来的错误还会触发断言吗？

## 按要验证的行为选择测试边界

| 用例要抓的错误 | 怎样准备输入，怎样保留证据 |
|---|---|
| 复审选错了上轮快照 | 预制 diff 和变更路径，按前后两棵树索引，让真实状态机选择。它传错任一快照，夹具就会报错。另用真实 Git 验证未提交改动、未跟踪文件和文件模式如何进入快照。[流程夹具](../../tests/review_flow_support.py) · [Git 证据用例](../../tests/test_review_git_evidence.py) |
| 回收误删了仍有工作的分支 | 用真实 Git 构造一次 squash 合并历史，只复用不可变对象。每条用例独占分支、索引和工作区，实际执行回收，检查哪些分支和目录仍然存在。[回收用例](../../tests/test_verified_delivery.py) |
| 超时后子进程仍然存活，或消息在重试期限前发出 | 对进程清理，等子进程报告就绪，再触发已进入的超时并检查进程是否退出。对重试，等系统写入下次重试时间，再推进测试时钟。把时钟替换限定在被测模块，避免把其他依赖的等待也算进断言。[超时夹具](../../tests/async_deadline.py) · [消息重试用例](../../tests/test_switchboard_dual_process_e2e.py) |

## 证明改快以后仍能抓错

给目标路径一个可观察的断言。以“CI 已通过、合并前主干版本才变化”为例，从已打开的 PR 开始，让旧提交先通过 CI，再推进主干。断言版本重算、新提交重新过 CI，最终合并的也是新提交。若测试提前走进“等待 CI 时 PR 已冲突”的路径，即使最终版本号相同，也应当失败。[两条 CI 用例](../../tests/test_pr_delivery.py)

改夹具前先复现目标行为。可以临时传错快照、调换事件顺序或返回旧提交，确认断言因预期原因失败，再恢复正确输入并跑绿。遇到偶发失败时，保留原始输出，单独复现对应的时序，区分故障发生在产品逻辑、夹具还是清理阶段。若提速方案会改变用户看到的行为，例如手工解冲突后是否复审，先说明取舍，由负责人决定。[交付策略](../architecture.md)

## 复测并选择下一轮

把验证过的改法应用到准备动作相同、断言目的也相同的用例。先跑这些定向测试，核对原有场景、断言和跳过项，再跑仓库门禁与全量验收。改前、改后各连续跑五次，逐次记录墙钟耗时、退出码、通过数、子测试数和跳过数。用中位数判断通常要等多久，用最大值检查最慢一次。

共享机器波动较大时，交替运行新旧版本作对照。定向收益落在全量波动范围内时，只记录已经验证的局部改善。每轮重排热点，依据新的耗时分布决定下一步。
