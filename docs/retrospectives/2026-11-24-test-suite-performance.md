# Hibernaut 并行测试提速复盘

2026-11-24，任务 `hb/task-79`。本次验收看开发者等多久。目标是在同一台 18 核机器上连续五次全量通过，命令从启动到退出的墙钟耗时中位数在 20 秒以内。

## 下次怎样跑一轮

1. **固定基线。** 记下提交和机器，用下方命令连跑五次。由外层计时器包住整条命令，逐次保存墙钟耗时、退出码和 pytest 原始摘要，包括通过、跳过和子测试数。失败的轮次也计入记录。
2. **找出时间花在哪里。** 另跑一次带 `--durations=0 --durations-min=0` 的全量测试，分别看最慢单例、按文件累计的 worker 耗时，以及最后几个 worker 在跑什么。按 `(nodeid, phase)` 归集，避免把子测试又算进父用例。一次剖析里 7,500 次同步 Git 调用累计占 113 个 worker 秒，这个数用来找重复工作。全量收益由墙钟复测。
3. **先写出这条用例要抓的错，再问最慢的动作是否有必要。** 例如“批准重试评审时又启动了开发者”。给定上轮快照、开发报告和评审失败的结果，运行真实的挂起、批准与恢复逻辑，断言调用顺序为“开发、评审、评审”。删除重复的开发或 Git 操作时，保留能让错误实现失败的断言。[评审状态用例](../../tests/test_sde_executor.py)
4. **沿同一边界改一组，重新排名。** 先跑定向用例，用一个已知错误验证断言确实会红。核对原有场景、断言和跳过项，再跑仓库门禁和同口径的五次全量。遇到偶发失败，先保留输出并定向复现，修复后重新计五次。共享机器波动大时，把新旧版本交替各跑五次，分别报告中位数和最大值。单项收益落在全量波动范围内时，只记录已测得的局部提速。

```sh
uv run --locked --extra dev pytest -n auto --dist worksteal -q
```

## 哪些动作值得保留

| 用例要证明什么 | 本次有效的做法 |
|---|---|
| 给定变更后，哪些问题能阻断复审 | 预制 diff 和路径列表，按前后两棵树索引。真实状态机若传错了上轮快照，取不到对应输入。另用真实 Git 验证未提交文件、未跟踪文件和文件模式如何进入快照。[流程夹具](../../tests/review_flow_support.py) · [Git 证据用例](../../tests/test_review_git_evidence.py) |
| squash 合并后，能否安全回收工作区 | 用真实 Git 构造一次合并历史，复用不可变对象。每条用例独占 refs、索引和工作区，实际执行回收，断言该保留或删除的分支和目录。[回收夹具](../../tests/test_verified_delivery.py) |
| 超时、重试或停机时，哪一步必须先发生 | 等子进程就绪后触发真实 deadline，等工作区已占用后再并发提交，或等消息已记为待重试后推进测试时钟。只替换被测模块的时钟。一次全局替换 `time.sleep` 把 Git 子进程等待的 1 毫秒也记进了协议断言。[超时夹具](../../tests/async_deadline.py) · [协议校验用例](../../tests/test_runner_service.py) |

**通过数只能说明用例跑过。** 原有两条 CI 用例都走到了“等待期间 PR 已冲突”。给“CI 已过、合并前主干版本才变化”的用例加上分支断言后，它立即失败。把起点设为两个已打开的 PR，在首个提交通过 CI 后推进主干，再断言新提交重新过 CI、版本重算且实际合并。相邻用例仍验证等待期间发现冲突的路径。[两条 CI 用例](../../tests/test_pr_delivery.py)

**产品取舍交给负责人。** 手工解决交付冲突后是否沿用原评审，会改变用户看到的交付行为。本次先比较方案耗时和评审者会多看到的主干差异，确认后才改为从上次通过的工作区快照直接比较，手工解冲突后一律复审。[交付策略](../architecture.md)

## 五次测量给出的结论

| 样本 | 五次墙钟耗时（秒，按该版本运行次序） | 中位数 | 最大值 | 全绿 |
|---|---|---:|---:|---:|
| 初始基线 `8f4839a` | 84.92、97.41、95.70、104.77、65.92 | 95.70 | 104.77 | 1/5 |
| `c9cf572` 提交后连续复测 | 18.859、19.136、19.986、20.525、19.547 | 19.547 | 20.525 | 5/5 |
| `8af46a7` 最终连续验收 | 21.86、22.83、25.64、25.17、25.69 | 25.17 | 25.69 | 5/5 |
| 交替对照，旧版 `c9cf572` | 23.475、26.829、25.801、26.506、25.681 | 25.801 | 26.829 | 5/5 |
| 交替对照，新版 `8af46a7` | 21.590、30.922、23.734、25.292、23.969 | 23.969 | 30.922 | 5/5 |

初始基线期间有失败，随后变基带入了主干新增用例。`c9cf572` 首次验收的中位数为 19.99 秒，提交后复测达到 19.547 秒。后来同一提交在交替对照中测得 25.801 秒。同期新版的中位数省了 **1.832 秒（7.1%）**，最慢一次增至 **30.922 秒**。旧版每轮 2,057 项通过，新版 2,058 项通过，两版每轮均有 1 项平台跳过、1,352 个子测试通过。
