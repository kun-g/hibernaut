# 项目群需求

这份文档管项目群：把和合作方的飞书群绑到一个项目的 Inbox，群里名单上的人提的事由这个项目的 Steward 处理。怎么做见 [设计文档](../architecture.md)；用词以 [glossary.md](../glossary.md) 为准。要求和约束来自 Kun 2026-11-27 的任务（水果机项目和郭勇的群搬进 hb），编号（R/C）不改，改之前先问。

## 要的结果

一个飞书群能绑到某个项目的 Inbox。名单上的人（Kun 和合作方）在群里说的话进这个 Inbox，被当成对这个项目的请求：能答问题、派这个项目的开发、开 PR，答复回这个群。名单外的人、没绑定的群照旧不进。

不归这里：系统 Inbox 的群（`sys:ops`）见 [系统 Steward 需求](system-steward.md) R9、R10；接入项目本身（建项目段、Steward 绑定）归系统 Steward；Switchboard 的路由归部署。

## 要求

**R1 名单上的人在绑定的群里 @机器人说的话进这个项目的群 Inbox，由项目 Steward 处理；答复回群里同一话题，派出去的开发的答复也回这里。** 为什么：现在这个群由一个 Claude Code 会话人工协调，经旧的工作台收发。

**R2 名单外的人在群里说的话、没绑定的群（被 Switchboard 路由到这个 Inbox 也算）、单聊，都不进这个 Inbox，也不回。** 为什么：群里可能有别人，别的聊天不能冒充这个群。

**R3 项目 Steward 知道群里谁是 Kun、谁是合作方，答复对着提问的人；几个人的话交错时，引一句原话再答。** 为什么：多人群里不说答谁，答复会被误认成答另一个人。

**R4 合作方提的开发、改动类请求，Steward 先用一条回复复述要做什么，提的人在同一话题里确认后才派。** 为什么：合作方的话是一句需求，不是精确的任务；派错了要花 Kun 的额度，也会在对方仓库开出不要的 PR。

**R5 交付默认只开 PR、不合并（对方的仓库），项目配置可设。** 为什么：合并进对方 main 不可撤回，默认留给人。

## 约束

**C1 群里谁说的话都只作用于绑定的项目：不能转到别的项目、系统 Inbox（`sys:*`）、全局 Steward（`user:*`），经项目里别的 Inbox 也转不出去；改不了 hb 配置。这由代码判定，不靠 Steward 自觉。** 来自：系统安全（给非 Kun 的人开入口）。
为什么：合作方能影响的只该是他参与的项目；代价是 Kun 在这个群里说别的项目的事也不会被转走，要回单聊说。

**C2 群 Inbox 只能由没有 Shell 的项目 Steward 处理；SDE 只能经 Steward 派活拿到群里的话。** 来自：系统安全。
为什么：SDE 有 Shell，群里的原话不该直接变成 SDE 的任务。

**C3 要花钱、对外发到别处、删除、合并到对方 main 这类事，仍要 Kun 审批：审批卡发给 Kun（Switchboard 的审批聊天），不发群里；这个项目所有 Inbox 的审批只认 `approvers` 列出的人，合作方点了不算，也不占掉 Kun 的那一次。** 来自：系统安全。
审批只认 approver 本人在审批卡上的点击：本机或远端经 `POST /events`、MCP 等入口送来的审批结果都不算；一个项目有几个群时，按审批所在的 Inbox 认那个群的 `approvers`，不把各群的名单并起来；认不出审批属于哪个项目（比如一个 Inbox 匹配两个项目）就谁都不认。

**C4 远端（别的主机、经代理）的 `POST /events` 投不进群 Inbox；投进项目其他 Inbox 的照旧，但不算群里的人说的。** 来自：系统安全。

**C5 系统 Inbox 的群绑定照旧（R9、R10 of [系统 Steward 需求](system-steward.md)）。** 来自：兼容。

## 按默认定

- 一个项目一个专用的群 Inbox，命名 `proj:<p>:chat`，绑定写在 `proj:<p>:.+` 那条之前；也可以直接绑项目主 Inbox，规则相同（这个 Inbox 只收这个群、远端 403）。专用的好处：群里的对话和 GitHub、Ash 转来的活各排各的队，主 Inbox 的入口不变。
- 配置写在 `hibernaut.toml` 的 `[[feishu_groups]]`：`chat_id`、`inbox_id`、`members`、`approvers`。`approvers` 只用于项目群、必填，一般只写 Kun；系统 Steward 改不了这一节（系统 Steward 需求 C3）。
- 「项目所有 Inbox」按项目的 `inbox_id` 规则算：群 Inbox、主 Inbox、`proj:<p>:sde` 等子队列的审批都只认 `approvers`。
- Kun 自己在群里说的话也只作用于这个项目（同 C1），不当成单聊里的请求。
- SDE 遇到拿不准的实现取舍先问派活的 Steward。Steward 按原需求回答后，开发继续；需要原派单上下文时，沿转交链问上一跳。改需求、花钱、对外、删除、牵扯别人时，由 Steward 补充查到的背景和推荐，卡片发给 Kun。合作方可在群里给 Steward 补充信息。
- 合并：`[projects.<p>.delivery] auto_merge = false`（默认），Kun 自己合；改成 `true` 等于 Kun 长期批准合并。

## 待定

- 合作方想直接回答 SDE 的问题（不经 Kun 的审批卡）时怎么做：合作方可在群里补充事实，由 Steward 判断是否在原派单范围内。超出范围由 Kun 审批。
