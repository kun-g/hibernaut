# 系统 Steward 需求

这份文档管系统 Steward：接入新项目、检查和补齐各项目的 Steward 配置，回答 hb 自己运转得怎样。怎么做见 [设计文档](../architecture.md)；用词以 [glossary.md](../glossary.md) 为准。每条都经用户认过，改之前先问。

## 要的结果

有一个系统级的 Steward 负责管理，比如新项目接入时帮它配置默认的 Steward。也能回答 hb 自己运转得怎样。一句话开新项目时，它负责中间的接入那一步，前后由 Ash 建仓库、运维 agent 配环境（R12–R15）。

不归这里：重启、升级和部署 Hibernaut 归运维；改服务器入口的路由归部署；密钥归用户；某件活派给哪个项目归全局 Steward，项目内派给谁归项目 Steward。

## 要求

### 什么算「接入时帮它配置」

**R1 用户在单聊里说「把 owner/repo 接进来」，之后这个项目能接活，主入口由 Steward 先看，子队列由 SDE 做，用户收到一份列明做了哪几步的答复。** 为什么：没有 Steward 的项目，一句提问也会直接开一个 SDE。

**R2 新项目默认开 PR、不自动合并，带一句说明，全局 Steward 随即能派活给它。** 为什么：合并不可撤回，默认留给人；缺派活名单的项目只能手工投递。

**R3 用户对同一个仓库再说一次接入，已有的不重复建、不覆盖。** 为什么：用户手改过的配置不能被默认值冲掉。

**R4 用户没说清仓库或要哪个名字，只问一句，不猜。** 为什么：猜错会在别人名下的仓库或错误的入口上动手。

### 什么算「管理」

**R5 用户问各项目缺什么，答复按项目列出缺的：Steward、说明、派活名单。** 为什么：缺哪项现在要逐段读配置才看得出。

**R6 用户说补上，直接改好并生效，不需要审批，答复列明改了什么、怎么退回。** 为什么：改动能一步退回，审批只增加等待。

**R7 要改服务器入口路由、或在不属于用户的仓库上建标签等，只列出来，不动手。** 为什么：影响用户以外的人或线上入口。

### 什么算「负责」

**R8 做不成时（仓库连不上、名字冲突、配置不合法）用户收到原因和停在哪一步，线上配置保持原样。** 为什么：半截配置会让所有项目停摆。

**R9 用户在单聊跟全局 Steward 说，或在绑定的飞书群里直接说；结果回到原来的单聊或群。** 为什么：Kun 建了 HB 群专门管 hb（2026-11-27）。

**R10 群里只有名单上的人（现在只有 Kun）的消息进 hb，别人的不进也不回；系统 Steward 的审批卡发到这个群，只有名单上的人在这个群里点了算，别人点了不生效，也不占掉名单上的人的那一次；别的聊天里的点击不算。** 为什么：群里有别人，别人的话不能当成 Kun 的指令。

### 什么算「答得出运转如何」

**R11 用户问 hb 运转得怎样、某个 hb 定时任务执行得如何、有什么可优化的，答复给出失败和挂起的任务（挂起带原因：等审批、等用户离开电脑、等人回答）、交付结果（合并、没改动、失败）、发不出去的消息、定时任务最近的触发和结果，说明查了哪段时间、哪些看不到；优化建议只列出，不动手。单聊问 Ash（全局 Steward）时，Ash 用同样的只读工具直接答，不必转交，也不只凭事件和会话作答；它只多这一个只读工具，没有系统 Steward 的接入、补配置工具，也没有 hb MCP 控制面的写操作（投事件、批审批、关会话、回收工作区）。** 为什么：2026-11-27 Ash 只看事件和会话，把等空闲的任务说成卡住。

### 什么算「一句话开新项目」

**R12 用户在单聊对 Ash 说一句「新建项目 X，从 Drive 下最新版本作初始提交，再配好预发布和生产（都先放 Dokploy）」，Ash 依次：建仓库、转交系统 Steward 接入 hb、转交运维 agent 配环境；每一步的结果回到同一个单聊，最后一条列出仓库、hb 接入、两个环境的地址和状态。** 为什么：Kun 2026-11-27 要一句话开完新项目，不在三处分别说。

**R13 新仓库默认建在 `kun-g` 下、私有。人点名账号或组织时按名单选择（可选 `LambdaTheory`），名单外拒绝并列出可选项；首次提交是 Drive 里该项目文件夹中最新修改的文件，压缩包先解开；仓库已存在就停下说明，不覆盖。** 为什么：覆盖别人或旧仓库不可撤回。

**R14 预发布环境建好并部署；生产环境配好，第一次上线前发审批卡，Kun 批了才上线。** 为什么：生产影响用户，上线要人拍板；预发布可随时重来。

**R15 哪一步失败就停在那一步，答复说明停在哪一步、为什么；后面的步骤不做。** 为什么：仓库没建好就配环境、接入失败还去部署，都会留下要人收拾的半截。

## 约束

**C1 系统 Steward 没有命令行，也不能任意编辑文件，只能做上面这些事。** 来自：系统安全。
为什么：它读得到外来文字，能任意执行就等于把主机交出去；代价是新能力要先开发（看运行状态也是开发出来的只读工具）。

**C2 密钥和令牌的值不进入它的上下文、答复和日志。** 来自：零真实密钥契约。

**C3 它不能改执行器、启动器、权限、交付检查命令、凭据，也不能改自己和别的系统入口的绑定。** 来自：系统安全。
为什么：这些键能让它给自己加权限或执行任意命令；代价是这些仍由人改。

**C4 管聊天的全局 Steward 没有改系统配置的能力，只能转交。** 来自：系统安全。
为什么：聊天的上下文最杂，权限分开后一处被带偏不等于配置被改；代价是多一次转手。

**C5 写配置前整份校验，有备份，写入不会留下半份；人同时改了就放弃并说明。** 来自：运行稳定。

**C6 能到系统 Steward 的只有三种：单聊经全局 Steward 转来的、绑定群里名单上的人发的、本机运营者投的。** 来自：系统安全。

**C7 Ash 建仓库只用专门的 `create_repo` 工具，仍然没有命令行；GitHub 和 Drive 的凭据不进它的上下文。** 来自：系统安全。
为什么：Ash 读的外来文字最多，给它命令行等于给每段外来文字命令行；代价是建仓库的方式固定，别的做法要先开发。

**C8 运维 agent 只有一个 `dokploy` 工具，没有通用命令行；生产上线（含开自动部署、重新部署、启动）和删除一律等人批准，看不出是哪个环境的按生产算。这由代码判定，不靠 agent 自觉。** 来自：系统安全。
为什么：通用命令行能读到钥匙串里的 Dokploy 令牌、绕过审批直接上线；代价是 Dokploy 的新操作要先登记分类。

**C9 链条里的下一步只能接在一个只收人请求的 Inbox（系统、运维）成功完成的结果后面，且须是同一个会话还在等的那件；失败的结果、项目的结果、别人的事件都不能把活带进系统或运维 Inbox。系统和运维 Inbox 自己仍不能转投。** 来自：系统安全（放宽 C6 的最小范围）。
为什么：Ash 要在接入完成后接着找运维，但不能让外来结果驱动系统操作；代价是每一步都由 Ash 编排，不能由系统 Steward 直接交给运维。

## 按默认定

- 系统 Steward 的入口是 `sys:ops`，agent 名 `hibernaut-ops`。
- 默认 Steward 由接入脚本写入，不靠 agent 判断。
- 群和名单写在 `hibernaut.toml` 的 `[[feishu_groups]]`（`chat_id`、`inbox_id`、`members`），只能绑到带 `system_tools` 的 Inbox；系统 Steward 改不了它（C3）。
- 「定时任务」只算 hb 自己的 `[[timers]]`；「最近」默认 24 小时，每个定时任务列最近 5 次。
- 运维 agent 的入口是 `sys:infra`，agent 名 `infra`，绑定写 `ops_tools = true`；与 `sys:ops`（系统 Steward）分开，名字不混。
- 用户给了 Drive 项目文件夹链接，Ash 从中取最新修改的直接文件。代理默认仅允许 `sources_folder_id` 的直接子目录，管理员显式开启 `allow_any_source_folder` 后可用服务账号可读的任意文件夹链接。省略链接时仍按项目名在 `sources_folder_id` 下查找；未配置该目录则提示给出文件夹链接并共享给服务账号，附可用的服务账号邮箱。
- 「预发布」是 Dokploy 里名为 `staging` 的环境（`[ops_tools] staging_environments` 可改），别的环境都按生产。
- 生产的审批卡发到 Switchboard 配的审批聊天，与其他审批相同。
