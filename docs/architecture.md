# Hibernaut 架构设计文档（Git 版本化最新基线）

本文档整合原基准设计方案与已落地的全部架构演进，作为 `kun-g/hibernaut` 仓库内唯一随代码同步演进的最新架构说明（Google Drive 原基准文档《Always-on Agent 整洁架构设计方案（Task 交接文档）》保持只读存档）。参考原文：[Building always-on agents (Anthropic)](https://claude.com/resources/articles/building-always-on-agents)。

术语（Event Inbox、Inbox、`inbox_id`、Session、`work_key`、Runner、Executor 等）以 [`docs/glossary.md`](glossary.md) 为唯一基准。

## 1. 核心运行心智：休眠—唤醒周期

常驻型 Agent 绝大多数时间处于休眠状态（**Asleep, no tokens spent**），仅在外部事件或到期定时器到达时短暂唤醒执行一轮工作（**Run**），结束后状态落盘（**Stored state**）继续休眠。

单轮 Run 四步循环：

1. **An event arrives**：外部事件（用户消息、Switchboard 转入的 GitHub 和飞书事件、Drive 队列任务、MCP 控制面调用、定时触发、审批回复）写入全局 Event Inbox 并快速 ACK。
2. **A session starts**：按 4 级优先级解析会话（`approval_request_id` → 显式 `session_id` → `(inbox_id, correlation_key)` → 新建），加载跨 Run 持久化状态（基线 Memory + Session 断点/历史及绑定的 `executor_id` / `executor_session_id`），并按 5 级选路（`resolve_agent_id()`，§3）选定目标 Agent 的 `ExecutorPort`。
3. **The agent loop runs**：在 `PermissionPort` 门禁下执行推理、工具调用或本地 CLI 子进程，按需读取记忆与设置后续定时器。
4. **The run writes back**：持久化新状态、记忆、`(inbox_id, correlation_key) → session_id` 映射以及执行器绑定（`selected_executor.executor_id`、`outcome.executor_session_id`），产出强类型终态 `RunOutcome = Silent | Emit | Suspend` 后释放租约重新休眠。

## 2. 整洁架构分层与依赖方向（L0–L3）

依赖箭头严格由外向内单向指向：**`L2 engine/`（调用方）与 `L3 adapters/`（实现方）并列指向 `L1 core/ports.py` 与 `L0 core/models.py`**，`app/bootstrap.py` 与 `app/main.py` 为唯一依赖注入组装根（Composition Root）。

| 层级 | 路径 | 职责定位 | 依赖规则 |
| :--- | :--- | :--- | :--- |
| **L0 领域契约层** | `core/models.py` | 不可变领域数据结构（含 `Event.correlation_key`、`SessionRef.correlation_key / executor_id / executor_session_id / parent_session_id`；`Event` 只承载事件事实与 `status`，认领次数与失败原因属 L3 存储内部）、强类型终态 `RunOutcome`（携带 `executor_session_id`，以及只供执行账本使用、不参与相等比较的 `RunTelemetry`）、执行账本条目 `RunLedgerEntry` 与失败路由 `FailureRoute`、`NewEventPolicy`，Inbox 绑定与转投契约（`InboxBinding`、`InboxMatchRule`、`InboxRoute`、`ForwardSpec`、`MAX_FORWARD_HOPS`）与 5 级选路纯函数 `resolve_agent_id()`（不带绑定的旧函数 `resolve_executor_id()` 保留） | 零外部依赖，仅 Python 标准库 |
| **L1 核心端口层** | `core/ports.py` | 定义纯抽象 `Protocol` 端口（含 `ExecutorPort.executor_id`、可选的 `RunStartListener`、`RunLedgerPort` 与可接回的 `ResumableExecutorPort`）及 `RunCapabilities` / `RunContext` 控制钩子 | 仅依赖 Python 标准库 + L0 |
| **L2 生命周期编排层** | `engine/` | `EventHandler`、`AgentWorker`（支持 `executors: Mapping[str, ExecutorPort]` 查表路由）、`TimerScheduler`、`OutboxDispatcher`、转投规则 `forwarding.py` | 仅依赖 L0 + L1，严禁 `import adapters/` 或 `app/` |
| **L3 基础设施与组装层** | `adapters/` + `app/` | SQLite 存储（含 `workspaces` 表与旧库兼容迁移）、按项目分区的 Memory（委托 Memory Hub，§14）、Auto Mode + Credential Proxy、外置 Drive 队列凭据代理（独立进程）、SDE 交付步骤 `PRDelivery`、白盒执行器、`LocalCLIExecutor` + `OrcaWorktreeManager`、Switchboard 入站桥、Drive 轮询、`MCPServerAdapter`、Switchboard 出站桥、`config.py`、`bootstrap.py`、`main.py` | 实现 L1 端口或驱动 L2 `EventHandler`，仅在 `app/` 组装注入 |

### L1 核心端口与 RunCapabilities

| 端口 / 契约 | 职责 |
| :--- | :--- |
| `InboxPort` | 统一事件缓冲与事实源（4 态生命周期 `pending` / `processing` / `done` / `failed`，重复幂等标 `dropped`）；支持 `claim_pending`、`fetch_processing`、`bind_session`、`requeue_processing`、`mark_done`、`mark_failed`；`has_open_event(inbox_id, source, external_id)` 判断同一去重键是否还有 `pending` / `processing` 事件（轮询方据此跳过，不写 `dropped` 行）；控制面重放 `replay(event_id, *, executor_id_override, force, replay_of_run_id)` 见 §11 |
| `TimerPort` | 持久化定时器存储（单次 `follow_up` 与周期 `schedule`） |
| `MemoryPort` | 跨 Run 目录记忆（必载基线 `instructions.md` / `index.md` / `reported.md` + 按需 `notes/*` / `progress/*`）；daemon 的实现委托 Memory Hub，按项目分区（§14） |
| `PermissionPort` | 每次工具调用前置三态门禁（`allow` / `block` / `defer`） |
| `OutboxPort` | 待发消息持久队列，解耦推理与外部通道投递；`fetch_pending(limit, *, now_iso)` 只返回 `next_retry_at` 为空或已到期的 `pending` 消息，`schedule_retry()` 记一次失败并排期，`mark_failed()` 为终态 |
| `LockPort` | 以 `inbox_id` 为主键的单活租约锁（`acquire` / `renew` / `release`），支持进程崩溃后租约到期自动接管 |
| `SessionStorePort` | 跨 Run 会话元数据（4 态 `active` / `suspended` / `archived` / `closed`、`work_key`）、执行器绑定（`executor_id` / `executor_session_id`）、`Suspend` 审批断点（`find_by_request_id`）、活跃引用计数（`count_active_by_work_key`）、按 `inbox_id` / `status` / `parent_session_id` 过滤的 `list_sessions`、`archive_session` / `close_session` 及外部关联键映射（`find_by_correlation_key` 仅命中 `active`/`suspended`） |
| `ChannelPort` | 外部投递通道（`SwitchboardChannelAdapter`、`ConsoleChannelAdapter`、`WebhookChannelAdapter`；`FileOutboxChannel` 包在最外层） |
| `ExecutorPort` | Agent 单轮推理边界（声明只读属性 `executor_id`；白盒 `WhiteboxExecutor` 或黑盒 `LocalCLIExecutor`），输入批次事件与 `RunCapabilities`，输出 `RunOutcome` |
| `RunLedgerPort` | 可选的执行账本：`route_failure(executor_id, *, error, telemetry)` 把一次失败的尝试分类为 `FailureRoute(error_kind, category, retry_delays)`，`record_run(RunLedgerEntry)` 在每个结束的 Run 后记账一次。`AgentWorker(run_ledger=...)` 调用它，两个方法抛错只记 `WARNING`、不影响 Run；不注入时不记账、失败按 `max_retries` 重试。组装根注入 `adapters/ledger_bridge.LedgerRunRecorder`（见 §11） |
| `RunStartListener` | 可选的 Run 开始通知 `on_run_started(inbox_id, events, correlation_key)`：`AgentWorker(run_start_listener=...)` 对每个执行批次，在认领、绑定会话之后、调用执行器之前，在线程里调用一次（关闭会话批次和被 `hold` 的事件不触发）；抛错只记 `WARNING` 日志，不让 Run 失败、不阻塞执行。可返回按 `event_id` 的替换 payload（`Mapping[str, Mapping[str, Any]] | None`）：执行器在本次 Run 里收到替换后的事件（id 与顺序不变），库里的事件 payload 不变，被中断重跑时重新调用。组装根注入 `DriveResultWriter` |
| `OpenRunPort` | 进行中 Run 的登记（SQLite `open_runs`：`session_id`、`inbox_id`、`executor_id`、`run_dir`、事件 ID、`started_at`、`code_version`），只存通用信息。`open()` 在 Run 开始时登记并建 0700 的 `<state_dir>/runs/<session_id>/<run_id>/`；`add_events()` 记 `fold` 并入的事件；`finish()` 在同一事务里把事件标 `done` 并删登记，再删目录；`discard()` 删登记与目录（失败、中断、无法接回时） |
| `ResumableExecutorPort` | 可选（`runtime_checkable`）：在 `ExecutorPort` 之外提供 `execute_resumable(events, session, caps, run)` 与 `resume(...)`。配置了 `OpenRunPort` 且执行器实现它时，`AgentWorker` 走这条路径；其余执行器不变 |
| `RunContext` | 给可接回执行器的 Run 句柄：`run_dir`（执行器私有状态，如 `state.json`）、`detachable()`（包住可脱离的等待段）、`should_detach()`（阻塞线程工作的检查点）、`detached()` |
| `RunCapabilities` | 注入单轮 Run 的受控能力集合：`memory`、`timers`、`permissions`、`poll_folded_events()`、`is_interrupted()`、`forward_to_inbox()`（受控转投，§3） |

### 配置定时器的生命周期

配置生效时按 `name` 对账。SQLite 的 `config:<name>` 主键专属配置定时器，白盒工具继续使用独立 ID。新增、重新启用或修改间隔后从生效时刻算一个间隔。其余更新和重启沿用持久化的 `due_at`。删除或停用只撤销后续触发，已经投出的事件按原流程处理。

所有周期定时器错过多个周期只补跑一次，下次对齐原相位的第一个未来间隔。配置定时器在一个事务中推进到期时间、检查自己的未完成事件、按需入队。已有 `pending` 或 `processing` 时直接跳过，重启和热加载中的旧 Run 也算在内。每个配置定时器在目标 Inbox 内沿用固定会话键，复用会话以保留连续记录，避免每轮新建一个 `active` 会话。

## 3. 外部关联键 `correlation_key`、多执行器粘滞路由与 L3 通道

- **4 级会话解析优先级**（`AgentWorker._resolve_session()`）：`approval_request_id` → 显式 `session_id` → `(inbox_id, correlation_key)` → 新建 `session_id`。
- **同键批处理与会话轮换重绑**：`_group_into_batches()` 按解析后的键（`session_id` → `correlation_key`）稳定分组，同键全部 `pending` 事件并入一批（批内保持 `seq` 顺序），批次按各组首条事件的 `seq` 执行。无键事件彼此无关，`defer`/`fold` 下各自单独成批且不被 `fold` 注入，仅 `interrupt` 重启时合并。本键当前批次遇到两种情况会结束：带 `approval_request_id` 的审批事件（同键更早的事件与它同批，挂起会话会把不含审批结果的 Run 视为拒绝），或执行目标（payload 的 `executor_id`、`explicit_workdir`、`executor`）与本批不同的事件。同键后续事件留到下一轮重新解析会话后再执行。快照里某键有待处理的审批时，该键的第一批必须带上审批：审批前执行目标不兼容的事件暂缓到审批之后，不提前结束批次。`AgentWorker._select_executor()` 选择执行器、`LocalCLIExecutor` 选择工作目录和模板，都取自批内普通事件，只有审批单独成批时才用审批自带的目标。审批命中挂起会话的 `pending_request_id` 时，该批固定交给会话绑定的 `executor_id`（持有断点的执行器）处理；执行器绑定上线前挂起的旧会话没有 `executor_id`，当前默认执行器不能证明归属（旧版 CLI 已可按事件选模板），只接受审批事件显式指定的 `executor_id`（唯一注册的执行器也可能是替代者，不作为依据）；无法判定或持有者未注册时本批报 `ExecutorFailed`，不确认事件、不清断点，补写 `sessions.executor_id` 后原审批即可恢复；审批待处理期间，同会话里指定其他 `executor_id` 的普通事件留到审批之后执行。`fold` 只注入同键、同执行目标的事件，遇到同键审批事件即停止，含审批的批次不注入；`interrupt` 以本轮调度快照判断新事件，含审批的批次不可中断（避免重复执行已批准的工具）；重置开新 Session 时向 `SessionStorePort.save()` 写入同一 `(inbox_id, correlation_key)` 自动解绑旧会话并指向新活跃会话。
- **跨 Agent 委派与 `parent_session_id` 留痕**（异步事件接力，不新增表）：主会话的 Run 入队一条委派事件后照常结束，不等待子会话。委派事件的 payload 携带 `parent_session_id`（可选 `work_key`、`executor_id`、`readonly`），应投递到父会话同一 `inbox_id`（同分区串行单活，遵守禁止跨 `inbox_id` 挂载同一目录的红线），并使用与父会话不同的 `correlation_key`（或不带），否则会解析回父会话或在保存时把父会话轮换归档。Worker 在执行前新建子 `SessionRef` 时写入 `parent_session_id`，`work_key` 依次取 payload 的 `work_key` → 父会话的 `work_key` → `correlation_key`，因此子会话默认复用父会话的 worktree，不另开目录；子会话持久化为 `active` 后即计入 `count_active_by_work_key()`。之后 `Silent` / `Emit` / `Suspend` 回写与会话轮换都保留 `parent_session_id`。主会话先 `closed` 时引用计数仍为 1，拒绝回收；子会话 `closed` 后归零才触发回收。`readonly` 原样透传给执行器，由执行器自行约束；`hibernaut_list_sessions` 可按 `parent_session_id` 查出全部子会话。
- **三层边界与 M:N 绑定**（术语见 [`docs/glossary.md`](glossary.md)）：Runner（工位与 worktree 隔离）→ Executor（`[executors.*]`，无业务含义的驱动）→ Agent（`[agents.*]`，角色、Skill、模型、权限边界）。Inbox 绑定 Agent：`[[projects.<name>.inbox_bindings]]` 每条写 `pattern`（正则，整串匹配，第一个匹配的生效）、`default_agent`、可选的 `agents` 白名单（省略即不限）与 `rules`（`source` / `event_type` / `tags` 写几项须同时满足，`tags` 须全部包含；至少写一项）。解析时即拒绝：未声明或不在白名单里的 agent、未知键、重复 `pattern`、不属于本项目的精确 inbox、匹配到别的项目精确 inbox 的 `pattern`（`app/projects.py` 的 `parse_inbox_bindings()`、`validate_project_bindings()`）。
  - **N:1**（多个 Agent 共用一个 Inbox）：仍是一把 `worker_leases` 租约、一条串行队列；同 Inbox 内的转投带 `work_key` / `review_of`，SDE 与 CLI 执行器据此进入同一 worktree 接力，评审者据此找到开发者的 worktree（`process.relayed_work_key()` 只认 `agent:forward` 事件上的 `work_key`）。
  - **1:N**（一个项目多个子 Inbox）：各自持有租约与 worktree，互相并发；`isolate_inboxes` 让同一 `work_key` 在不同 Inbox 落到不同目录。
  - **配置兼容**：`[executors.<id>]` 写 `role` 或 `command` 仍同时是同名 Agent；`[agents.<id>]` 引用一个不写 `role` / `command` 的 Claude Code 执行器（取其 `launcher`、`billing`、`timeout_seconds` 等，自己写 `role`、`model`、`effort`、`skills` 与该角色的选项），或引用一个 CLI 模板（只能改名、写 `description` 与 `max_concurrency`）。`default_agent` 是 `[runtime] default_executor` 与 `[projects.*] executor` 的新名，两个都写且不同则报错。
- **受控转投 `forward_to_inbox`**（`engine/forwarding.py` 的 `ForwardStage`，经 `RunCapabilities` 提供给所有执行器）：异步，不等结果。
  - **门禁**，任何一条不过都抛 `ForwardRefused`，调用方绕不开：主动转投次数已达 `MAX_FORWARD_HOPS = 3`（`hop_count` 缺失或格式不对按已用完算；回投不计，所以「派单 → 回投 → 派复审 → 回投」只用两跳）；目标不属于同一项目（非项目绑定 `forward_to` 列出的项目主 Inbox 除外，见下「跨范围转投」），或项目写了绑定而目标没有绑定覆盖；inbox_id 不能作 Memory 分区名（含 `/`、`\`、`..`）；指定的 agent 未注册或不在目标白名单；同 Inbox 转给自己；`PermissionPort.check("inbox.forward", …)` 返回 `block`，或 `defer` 而没有本会话的已批准请求（`approved_request_id` 须与本批审批事件一致）。默认策略放行，想逐次审批就把 `inbox.forward` 移到 defer 列表。
  - **落库时机**：Run 里只暂存，Run 有了结果（`Silent` / `Suspend` / `status = "done"` 的 `Emit`）才写入 Inbox 并唤醒目标；失败、中断的 Run 一条也不写。`external_id = "forward:<首个事件>:<序号>"`，崩溃重跑按 `(inbox_id, source, external_id)` 去重。
  - **事件**：`source = "agent:forward"`，payload 带 `text`、`title`、`tags`、`agent_id`、`hop_count`、`forwarded_from`、`forwarded_by`、`parent_session_id`、`trace_id`、`parent_event_id`、`reply_channel` / `reply_target`、`return_to`、`delegation_id`、`origin_key`，并继承 `activities`、`base_ref` 与 `attempt_notes`；调用方给不了其他键，路由键无法夹带。同 Inbox 接力用 `forward:<agent>:<原键>`，一个 Run 投同一 Inbox 的多件活用 `forward:<n>:<原键>`，各有会话与 worktree。同 Inbox 接力的会话把 `work_key` 记在 `ForwardSpec`，之后没有转投事件的跟进、审批与定时器（CLI、SDE、code-reviewer）都回到这个 worktree。外部的新消息重新从 0 计跳；欠着上级回投的链不重置，回投事件原样带回所答转投的 `hop_count`，收到回投后再转投从它继续计，所以反复「转投 → 回投」的循环仍在第 3 次之后被拒。会话还欠着或等着时，来件跳数与会话里的取大；两头都结清后，同一会话接的新委派只按来件计跳。
  - **血缘**（`run_lineage()`）：转投事件的 `trace_id` 取本 Run 的 trace（§7.2），`parent_event_id` 是本 Run 主事件的 `event_id`；`agent:return` 与 `agent:return_cancelled` 原样带上子会话这条链的 `trace_id`，`parent_event_id` 是子 Run 主事件的 `event_id`（首轮即转投事件）。只写在新事件上（新指旧），触发它的旧事件在 `event_inbox` 里一个字节也不改。`ForwardSpec` 存 `trace_id` 与 `parent_event_id`：这个会话再往外发时写的就是它们；没有 `ForwardSpec` 的会话在 `Suspend` 时也存一份，所以审批后才发出的转投仍接在原事件上。Taskboard 任务自己的 trace 随 `hand_over()` 另放 `task_trace_id`（与 `task_hop_count` 同理），不与链的 `trace_id` 混用；升级前排队、没有这个键的转投仍按 `trace_id` 读。
  - **混合回信**：不带 `return_to` 时目标 Agent 直接按 `reply_channel` / `reply_target` 答复外部（Outbox 元数据的 `correlation_key` 用 `origin_key`），Drive / Taskboard 的结案随之归它；带 `return_to` 时结果（含失败与拒绝）以 `agent:return` 事件回到该 Inbox 里上级会话（沿 `parent_session_id` 找仍开着的那个），由它答复，`pending_returns` 清空前 Drive 文件与 Taskboard 任务保持打开。**每项委派有自己的标识**：`delegation_id` 取首次转出它的 `agent:forward` 的 `external_id`，随转投、回投、取消三种事件走。**一项委派只有一个责任方**：欠着结果的会话要么把一部分发出去、要求回到本 Inbox（另立标识），要么把整件交给别人（不带 `return_to`，或 `return_to` 与自己欠的相同）；指向第三个 Inbox 的 `return_to`、投给正等这份结果的 Inbox 都被拒。转投带原 `return_to`、`delegation_id` 与等结果的上级会话（`parent_session_id`），一个 Run 只能交一次，也不能接力给等这份结果的会话本身；随转投一起落库，交出方清掉 `return_to` 并记 `ForwardSpec.handed_on`：它之后关闭、失败都不影响接手者，关闭上级则连接手的会话一起关闭；它在外部新消息到来之前说的话与失败只留在 Run 记录里，不外发，除要求回到本 Inbox 的以外也不能再转投。上级的 `pending_returns` 记未结清的标识，回投、取消、拒绝、关闭各按标识结清一次，别的标识不影响它；处理过的回投记在 `settled_returns`（标识与事件），同一标识的另一份回投、取消之后才到的回投直接标记完成，不运行 Agent，也不 fold；回投与取消谁先入队谁算数，按 Event Inbox 的入队序号 `Event.seq` 比，不看 `occurred_at`，正被并发上限扣着的回投也算在内。操作员重放转投事件得到的结果带 `replayed`，不受此限。子 Inbox 里两项不同的委派不进同一批、也不 fold 到一起；同一会话键上的会话还欠着另一项、或还等着自己转出的部分时，新的一项另起会话与 worktree（键 `forward:<external_id>:<原键>`，`own_task()`），两样都没有时照旧续接原会话。同一 Inbox 内不带 `return_to` 的接力是同一件工作，不另立标识。`forward_to_inbox` 还给执行器的是深拷贝回执，改它不影响已过门禁、待投的事件。回投不计跳，但同样过 `inbox.forward`，与首次转投各自判定；用完最后一跳的转投照样能回投，只有 `hop_count` 超过上限（正常转投产生不了）的回投才算跳数用完。**回投被拒时结果不外发**：连同原因存进子 Inbox 里一个单独的会话（`held:<external_id>`，`ForwardSpec.held`，决定后仍留在那里），Outbox 发一条审批请求，只写目标、状态、原因、请求号与会话号，正文用控制面的 `hibernaut_get_held_return` 读；子 Agent 自己的会话照常可用，父任务保持打开。批准后再判一次门禁并入队，不再运行 Agent：`defer` 可由人放行；`block` 与跨项目批准也不放行，换新请求继续挂起。拒绝则只告诉上级结果被扣下，不带内容。跳数用完的回投谁也放行不了：批准表示就地了结、拒绝表示丢弃，都不再入队。什么都不能回去时（跳数用完，或拒绝后连扣留状态也被 `block`），以及欠回投或扣着结果的子会话被关闭时，改排一条 `agent:return_cancelled` 控制事件：不带结果、不计跳、不运行 Agent，父 Inbox 的 Worker 在自己的租约下核对会话属于本 Inbox、且这项委派还没结清，才把它从 `pending_returns` 移到 `cancelled_returns`，其余的取消事件不改任何状态（不参与 fold，也不打断 Run）。清空而会话没有挂起时由 Worker 收尾：写一条 `kind = "return_withheld"` 通知、Taskboard `release`、Drive 进 `失败/`；会话自己还欠回投的改为回投 `refused`。还有别的回投在等时，Steward 下一轮的提示带一行计数（还等几份、几份不会回来），不另唤醒。失败的 Run 与被拒的委派同样处理，**欠上级的失败与拒绝不在外面留细节**：不写 `run_failed` / `agent_refused`，事件记在 `owed_failures`，Drive 也不回写，细节只在回投、事件的 `last_error` 与运行账本里。只有载有委派的 `agent:forward` 被拒才算结清（`return_to` 随即从会话清掉）；会话还欠着或等着时，一条跟进消息被拒只答复它自己的来处（`agent_refused`），委派与 Drive 任务都不受影响。结果关联的 Taskboard 任务由这次决定收尾。关闭会话由 `engine/closing.close_session()` 一处完成（Worker 与 MCP 共用，调用方持有该 Inbox 的租约）：先排取消事件再关，一并关闭它扣住的回投并作废其审批请求；取消各按标识只生效一次。**关闭连带它发出的工作**：关闭记在被关会话的 `ForwardSpec.closed`，还在等的标识移进 `cancelled_returns`；还没起会话的转投在领取时、会话登记后执行前各核对一次（`withdrawn_forward()`），直接标记完成，不运行 Agent；已起的会话（其他 Inbox 的全部，本 Inbox 的只限欠着它结果的）各收到一条带 `closed_parent` 的 `agent:close`，由持有该 Inbox 租约的 Worker 再核对归属后关闭；在途 Run 的结果、待批的回投、已排进来的回投都不再往外走。操作员重放的不受此限。归属看 `owner_session_id()`：会话当前这件工作的发出方（`ForwardSpec.parent_session_id`，Run 开始时就落库），不是它最初的 `parent_session_id`，所以复用给别的上级的会话不随旧上级关闭；换了会话号的上级经 `continued_in` 找到续接的会话。关闭批次里还没开始的转投不算在内，另起会话执行。会话自己的 Run 以 `close_session` 结束不算这种关闭，发出去的工作照常进行。**Worker 只动自己持有租约的 Inbox**：事件（显式会话号、审批请求号、关闭请求 payload 里的会话号）指向别的 Inbox 的会话时标记失败，什么也不改；只有 Hibernaut 自己的关闭请求（`agent:close`）改排到目标 Inbox，由那边的 Worker 执行。同一次领取里排在前面的批次可能已关闭会话或决定了请求，所以每批执行前重读会话：审批的请求号已不在挂起中的会话上就标记失败，关闭批次里的审批也一样。`ForwardSpec` 存在 `sessions.forward` 列（旧库自动补列）。
  - **跨范围转投**：`InboxRoute.forward_to` 非空的 Inbox（只有非项目绑定）可投给其中的主 Inbox，其余项目与 Inbox 照旧拒绝。此时不许指定 `target_agent`，`return_to` 只能是来源 Inbox 自己；反方向只放行结果回投（`return_refusal()` 与把欠的结果在项目内转交时，等结果的 Inbox 当前的 `forward_to` 须仍含本项目的主 Inbox，`_sent_from()`）。`app/main.py` 的 `ForwardTargets` 由各配置代共用，热加载生效后指向新配置：已退役那一代的 Run 按「自己的白名单 ∩ 当前白名单」判。Run 收尾入队前 `drop_refused()` 再判一次，不再放行的转投丢弃，不计入 `pending_returns`，Outbox 发 `kind = "forward_refused"` 到原对话。

    - **任务键**：跨范围转投的会话键是 `forward:<来源 inbox>:<external_id>:<原键>`，写进 payload 与 `ForwardSpec.task_key`；项目内再转投、接力、回投都以它代替 `origin_key` 作键（`return_key` 记等结果的那件活的键，上级会话已不在时回投按它找），所以同一外部对话的两件活一路各有会话与 worktree。`origin_key` 不变，仍用于对外答复。没有 `task_key` 的链行为与以前相同。

- **Steward**（`StewardExecutor`，`adapters/executor_cli/steward.py`）：`role = "steward"` 的 Agent，复用 `ClaudeCodeProfile` 与 `claude_code.py` 启动器，默认 `checkout_access = "readonly"`（目前唯一取值），总是非交互运行。
  - **运行方式**：每轮在工作目录的 Orca 终端里一次性跑 `claude -p --output-format json --json-schema …`，不作 daemon 的子进程（daemon 重启、崩溃或被杀不连带它，它也不继承 daemon 的环境）。复用评审 CLI 的 `OrcaCommandTerminal` 与 `cli_terminal.py`（见下文「可旁观终端」）：提示词经轮次目录里的 `stdin` 文件送进去（不进命令行，不受单个参数长度限制），结果从包装脚本写的文件读（`print_result()` 认单个结果对象，也认用户开了 verbose 时的消息数组），读完立即关终端；失败、超时、中断同样先关终端，关闭没送到时由包装脚本结束 `claude` 进程组。`json` 输出没有 `init` 消息，所以包装脚本里先跑 `claude_gate.py` 的一次性模式（spec `"once"`）：按 `env_overrides()` 剥离并设置环境变量，以同一探测校验账号与模型，通过后 `exec` 成 `claude`，不通过则不启动，按失败答复。`--resume`、`--mcp-config`（同一 Unix socket）、`--append-system-prompt`、`--json-schema` 原样传入。标题 `terminal_title(<agent>, "steward", <inbox_id>)`。

  - **MCP 工具**（`steward_tools.py`，在 hb 进程里执行；`steward_mcp.py` 是 `python -I` 起的无状态 stdio 中继，经 0700 临时目录里的 Unix socket 转发，Run 结束即关）：`forward_to_inbox`、`read_file`、`search_files`、`list_files`、`read_memory`、`write_memory`、`memory_search`、`memory_read`、`memory_propose_write`（§14，没有批准工具）、`list_sessions`、`list_events`、`git`，除转投外各以自己的名字（`git` 为 `git_read`）逐次过 `PermissionPort`。读文件只限 Git 跟踪或会跟踪的文件（`.git` 与被忽略的文件不可读），门禁收到的 `path` 是解开符号链接后的检出内路径；`search_files` 会显示文件内容，命中的每个文件另按 `read_file` 判一次，不放行的不显示也不计数；Git 输出按字节、以 NUL 为界解析，文件名含换行也按完整路径判，解析不了就整条不给。会话与事件只限本项目的 Inbox（全局 Steward 见下），事件只给元数据、标题与至多 500 字符的正文。`git`（`steward_git.py`）只有 `status`、`diff`、`log`、`show`、`blame`、`rev-parse`、`merge-base`，选项按命令列白名单、只认全称，路径写在 `--` 之后，拒绝越界路径与以 `:` 开头的参数，以 `GIT_OPTIONAL_LOCKS=0`、`GIT_NO_LAZY_FETCH=1`、`--no-ext-diff --no-textconv`（`blame` 用 `--no-textconv`）运行，读检出的命令另以环境变量清空全部 `filter.*` 驱动，`status` 与 `diff` 加 `--ignore-submodules=dirty` 不进子模块，配置里的程序都不会执行。**会显示文件正文的 git 操作按同一条 `read_file` 判定**：只有 `show <commit>`、`show <rev>:<path>`、`diff`、`blame` 给正文，版本先解析成 commit ID，先以不识别改名的 `--name-only` 列出涉及的文件（合并提交取与各父提交的差异并集），逐个过 `read_file`，有一个不放行就整条拒绝，放行后也只输出列出的这些文件；`show <rev>:<path>` 先用 `ls-tree` 核对条目，只有普通文件（不含子模块、目录、符号链接）才用 `cat-file blob` 输出原始内容；`--stat`、`--name-only` 等只给名称与计数的不需要。`log` 只给元数据，`-p`、`-S`、`-G`、`-L` 与按 blob 读内容一律没有。

  - **群入口**（`SwitchboardInboundBridge(groups=GroupEntrances(...))`，配置 `[[feishu_groups]]`：`chat_id`、`inbox_id`、`members`）：飞书事件进 Event Inbox 前由桥按 `chat_id` 重定向，不管 Switchboard 把它路由到哪个 scope（默认 `unmatched_policy = "fallback"` 时落在 `default_scope`，所以远端不用改路由）。绑定群里名单上的人发的消息改投到绑定的系统 Inbox，`correlation_key` 仍是 `feishu:thread:<消息>`，答复经 Switchboard 回同一话题；名单外的人（含没有 `actor` 的）的消息回 `acked` 丢弃，只在 stderr 记一行，不回复。一个系统 Inbox 最多绑一个群。它的挂起报告（`execution.reported`，`outcome_kind = suspend`）由 `SwitchboardChannelAdapter(card_group=GroupEntrances.card_group)` 加上 `approval_channel = "feishu"`、`approval_target = <群 chat_id>` 和 `deciders`（该群名单），所以审批卡发到这个群，不发到 Switchboard 自己配的审批聊天；Switchboard 在存下点击之前就拒掉名单外的人（见下「无关联键的审批回执」），否则名单外的人先点会占掉这张卡唯一的一次决定。落到这个 Inbox 的 `approval.decided` 只有 `metadata.chat_id` 是它绑的群、点击人在该群名单上才放行，别的聊天（含同一人在单聊里点）和缺 `chat_id` 的回 `acked` 丢弃。没绑定的群和单聊照旧。只有 Switchboard 校验过的飞书 Webhook 产生 `source = "feishu"`，`chat_id`、`actor` 由飞书填；远端 `POST /events` 自称 `sb:feishu` 的事件带 `REMOTE_KEY`，进不了系统 Inbox，也不算人。加载时 `inbox_id` 须是一条带 `system_tools` 的 `[[runtime.inbox_bindings]]` 的精确 pattern，`chat_id` 不重复，`members` 非空。
  - **项目群**（需求见 [`requirements/project-group.md`](requirements/project-group.md)）：`[[feishu_groups]]` 的 `inbox_id` 也可以是项目的一个精确 Inbox（`FeishuGroup.project` 记下项目名），另须 `approvers`。加载时这个 Inbox 须被项目的一条绑定覆盖，且该绑定的 `default_agent` 与 `agents`（非空）全是 `steward` 角色，所以群里的原话只到没有 Shell 的项目 Steward；`approvers` 只用于项目群；一个 Inbox 仍只绑一个群。名单上的人（含合作方）的消息照上面改投到这个 Inbox；落到这个 Inbox 的别的飞书消息（别的群、单聊，不管 Switchboard 怎么路由）回 `acked` 丢弃。出不了项目靠的是现有的转投规则：项目 Inbox 的 `InboxRoute.forward_to` 为空，`ForwardStage._check_inbox()` 只放行同一项目的 Inbox，所以群 Inbox 和它转去的主 Inbox、子队列都到不了别的项目、`sys:*`、`user:*`；回投只回等结果的 Inbox，而群里来的活不带 `return_to`。`event_origin()` 对项目群的消息返回 `None`（不是 `group`），所以它也不算人对系统 Inbox 的请求。审批：`GroupEntrances(projects_of=...)` 由组装根的 `group_entrances(config)` 按 `ProjectRouter.matching()` 给出每个 Inbox 匹配的全部项目；`GroupEntrances.deciders(inbox_id)` 给出谁能决定这个 Inbox 的审批：绑了项目群的 Inbox 是该群的 `approvers`，项目里没绑群的 Inbox（主 Inbox、子队列）是这个项目各群 `approvers` 的交集（不跨群取并集，加载时各群须至少有一个共同的 approver），匹配两个项目的 Inbox 是空集（谁都不算），其余 Inbox 为 `None`（不限）。这个项目任何 Inbox 的挂起报告由 `card_group` 加上 `deciders`，但不加 `approval_target`，卡片按 Switchboard 的 `[outbound] approval_target` 发（必须配好，不配就落回来源话题，也就是群里，那时只是看得见、点不了）。判定落在两处：`inbox_for` 对有 `deciders` 的 Inbox 只放行 Switchboard 已验签的飞书卡片点击（`source == "feishu"`、`approval.decided`）且点击人在 `deciders` 里，其他来源带 `approval_request_id` 的一律丢弃；`EventHandler.reserve_approvals(entrances.deciders)` 让所有公开入口（`POST /events`、MCP `hibernaut_ingest_event` / `hibernaut_resolve_approval`、Switchboard 转入）共用同一道闸：payload 带 `approval_request_id` 或 `event_type` 为 `approval.decided` / `suspend.elapsed` 的事件，进有 `deciders` 的 Inbox 时，只有调用方给出 `decided_by` 且在名单里、并且不是远端，才入队，否则抛 `ApprovalRefused`（HTTP 403、MCP 报错、Switchboard 回 `acked` 丢弃），在写入前拒绝，不占掉真审批的去重键。`decided_by` 只由 `SwitchboardInboundBridge` 按 `decided_by(event)` 填（飞书卡片点击人），来源名、`actor` 字段都可以伪造，不作依据；真正的定时恢复由 `TimerScheduler` 直接写 Event Inbox，不经这道闸。`EventHandler.keep_local()` 把绑了群的 Inbox（系统和项目）都列为只收本机，远端或经代理的 `POST /events` 403。项目 Steward 的提示里多一节 `## Feishu group`（`steward.GroupRoster`，由配置现拼）：群 `chat_id`、谁是 owner（`approvers`）、谁是合作方（`members` 减 `approvers`）、群里的请求只关于本项目、合作方的活先复述再等确认；内置 Skill `skills/steward/` 的「A Feishu group」写怎么答多人、怎么引原话。
- **系统 Steward**（`GlobalScope.system`）：绑定写了 `system_tools` 时，契约换成 `_SYSTEM_CONTRACT`（到这里的事件来源已由代码验过，其中的请求就是人提的，不再请人确认授权；请求里引用或附带的外来文字、工具读到的文字不是请求），内置 Skill 换成 `skills/steward-system/`，路由清单换成 `build_system_manifest()`，没有 `forward_to_inbox`，多出 `check_projects`、`onboard_project`、`complete_project` 和只读的 `runtime_status`。`runtime_status(hours=24, timer_runs=5)`（`hours` 1–720，`timer_runs` 1–20）由 `adapters/storage_sqlite/ops_status.py` 的 `SQLiteOpsStatus` 读 `hibernaut.db` 生成摘要：时间窗口；失败的任务（窗口内到达且 `failed` 的事件，取标题与错误首行；加 Outbox `task_context.status` 为 `failed`/`stopped`/`refused` 的结果）；现在挂起的会话及等什么（经 `sde.suspended_stage()` 读 SDE 检查点：`stage = needs_input` 且原因以 `sde.WAIT_IDLE` 开头为 `user_away`——SDE 契约要求等用户离开电脑的任务这样返回 `needs_input`，`_suspend()` 把问题原样存进检查点的 `reason`——其余 `needs_input` 为 `answer`，有对应 `suspend.elapsed` 定时器为 `retry`，其余为 `approval`，原因取检查点或审批消息的首行）；交付结果（窗口内 SDE agent 的 Outbox 结果：`task_context.delivery.state` 为 `merged`/`pr_open`/`local`，失败结束为 `failed`/`stopped`，没有交付结果的在有交付步骤的项目里为 `no_change`，否则 `no_delivery_step`）；发不出去的 Outbox 消息（窗口内 `failed` 和所有重试中的）；每个 `[[timers]]` 的下次到点与最近几次触发（`timer:<name>` 事件的状态、错误，有运行账本时加该事件最近一次 Run 的结束方式与耗时）；以及看不到的范围（`not_covered`）。只取标题、状态和错误首行，不带事件 payload、消息正文和日志；`SystemToolbox.status()` 再用 `scrub()` 去掉环境变量和配置里的密钥值与令牌样式的字符串。四个工具的定义和逐次门禁在 `steward_tools.py`（各以自己的名字过 `PermissionPort`，未知参数拒绝），实现是组装根注入的 `SystemTools` 协议（`app/system_tools.py` 的 `SystemToolbox`），每次调用前按当前配置重判绑定是否还有 `system_tools`；`hides()` 让 `read_file`、`search_files` 与 `git` 都看不到配置及其备份的内容。全局 Steward 的清单由 `build_global_manifest(systems=…)` 多列出它能转到的系统 Inbox：固定写明它接入和补齐项目、说 Hibernaut 运转得怎样与可优化处（`_SYSTEM_PURPOSE`），绑定 Agent 的说明附在后面；全局 Steward 自己也有只读的 `runtime_status`：`GlobalScope.status` 是组装根建的同一个 `RuntimeStatus`（`app/system_tools.py`，读 `SQLiteOpsStatus` 再 `scrub()`；`SystemToolbox.status()` 先判绑定还有系统工具再调它），`StewardTools.definitions(status=True)` 只多出这一个工具，不带 `check_projects`、`onboard_project`、`complete_project`；`skills/steward-global/` 让它用这个工具直接答运转问题，不转交，也不只凭 `list_events`、`list_sessions`。
- **一句话开新项目**（需求 R12–R15、C7–C9）：由全局 Steward 编排，`skills/steward-global/` 写明顺序：① `create_repo` → ② 转给系统 Inbox 接入（`return_to` 自己）→ ③ 回信 `done` 后转给运维 Inbox 配环境 → ④ 汇总回单聊；任何一步失败就停下说停在哪一步。系统和运维 Steward 的答复可带 `status: failed`（`STEWARD_SCHEMA` 的可选字段，`_answer()` 把它变成 `Emit` 的失败状态），回信据此带 `status`，`_carries_request()` 只放行 `done`。
  - **建仓库**（绑定 `repo_tools = true`，`[repo_tools] owner, allowed_owners, max_bytes`）：全局 Steward 多一个 `create_repo(name, drive_folder?, description?, owner?)`，仍没有命令行（`StewardTools.definitions(repo=True)` 只多这一项，`_REFUSED_TOOLS` 照旧）；每次以 `create_repo` 过 `PermissionPort`，实现是组装根注入的 `RepoTools`（`app/repo_tools.py` 的 `RepoCreator`），调用时按当前配置重判绑定和名单。省略 `owner` 用配置的默认账号，指定时按 GitHub 账号名忽略大小写匹配，名单外立即拒绝并列出可选项。旧配置只允许默认账号。步骤：`gh api repos/<owner>/<name>` 存在即停（不覆盖），答不清（非 404）也停；经凭据代理的 `source_folder` 取项目文件夹（默认与仓库同名、在 `sources_folder_id` 下一层；给了链接或 ID 就使用指定文件夹。代理默认仍限来源文件夹下一层，管理员开启 `allow_any_source_folder` 后可取其他共享文件夹，但代理按 Drive ID 排除四个任务队列文件夹、附件文件夹及其直接文件），空则停；取 `(modifiedTime, name)` 最大的文件经 `source_download` 下载。按链接下载时，代理重查所选目录与文件的直接父目录；zip / tar 在临时目录里安全解开（拒绝绝对路径、`..`、链接和非普通文件，跳过 `__MACOSX`、`.DS_Store`、`.git`，按 `max_bytes` 限总量；顶层只有一个目录时以它为根），其余文件原样放入；`git init -b main`、提交、`gh repo create --private --source … --push`。推送失败时再查一次，答复说明仓库已建（私有）但停在推送。gh / git 用本机登录（`remote_env()`），Drive 只经代理（Hibernaut 不持 Google 凭据），输出经 `scrub()`。
  - **运维 Inbox**（绑定 `ops_tools = true`，`[ops_tools] dokploy_script, staging_environments, timeout_seconds`）：`GlobalScope.ops`，契约 `_OPS_CONTRACT`，内置 Skill `skills/steward-ops/`，清单 `build_system_manifest(ops=True)`；工具只有 `dokploy(action, args)` 与只读的文件、Memory、会话查询，没有 `forward_to_inbox`、`runtime_status`、系统工具。`app/ops_tools.py` 的 `DokployTools` 在绑定的 `workdir` 里跑 `bash <dokploy_script> <action> <args…>`（令牌由脚本从钥匙串取，输出默认打码；`--reveal`、带引号或花括号的参数、未登记的 action 拒绝），输出再经 `scrub()`。每次先 `plan()` 分类再以分类名过 `PermissionPort`：读为 `dokploy.read`、预发布的改动为 `dokploy.change`（放行）；部署、启动、重新部署，及 `post` 到名字含 `deploy`、`start`、`reload`、`rollback`、`duplicate`、`import`、`restore`（`_GOES_LIVE`）的端点或带 `autoDeploy: true`、`save*Provider` 未写 `autoDeploy: false` 的，先经 `<service>.one` 与 `environment.one` 查环境名：在 `staging_environments` 里为 `dokploy.deploy`（放行），否则或查不出为 `deploy_production`；`remove` / `delete` 为 `delete_resource`；`post` 到未登记的服务为 `dokploy.admin`。后三者在 `DEFAULT_DEFER_TOOLS` 里或属未知工具，一律 `defer`：调用不执行，记进 `deferred`（`kind = "dokploy"`），本轮挂起，审批提示列出每个扣住的调用（带环境）和 Steward 扣住的答复（预发布的状态）；批准后由 Hibernaut 按原参数重新分类、过门禁再执行（`StewardTools.run_held()`），然后重开一轮 Steward（提示里有「Decision on your held calls」），由它报告结果；拒绝则只重开一轮。批准号只来自审批事件，Steward 传不进来。
  - **结果与审批**：`--json-schema` 要求 `{action: reply|silent, message}`，对应 `Emit` / `Silent`。转投被 `defer` 时挂起，审批提示列出目标与全文；批准后由 Hibernaut 带 `approved_request_id` 补发并送出扣住的答复，不再调用模型（期间有新事件、或补发被拒时才再跑一轮）；拒绝则告诉 Steward 再答一轮。批准号只来自审批事件，agent 传不进来。
- **5 级选路与原生会话续接闭环**：
  - `resolve_agent_id()` 按 5 级优先级决定目标 Agent：① 事件显式指定 `payload.agent_id`（兼容 `executor_id`；允许主动切换，但须在 Inbox 绑定的白名单里）→ ② `active` / `suspended` 会话绑定的 Agent（默认粘滞）→ ③ 绑定的 `rules`，先匹配者优先 → ④ 绑定的 `default_agent` → ⑤ 项目 `default_agent`，未设则全局 `runtime.default_agent`。事件的来源、类型与标签取自 `source`、`payload.event_type`、`payload.tags` / `labels`（含 GitHub Issue / PR 的标签）；payload 带 `timer_name` 的定时器来源为 `timer:<name>`。
  - 指定的 Agent 不在白名单时整批明确失败，不回退到别的 Agent：事件标 `failed`，不建会话、不起执行器，Outbox 发一条 `kind = "agent_refused"`（Drive 任务进 `失败/`，会话还欠着或等着委派的留在原处；带 `return_to` 的转投不发这条，改为把拒绝回投，任务留在原处）。
  - `AgentWorker` 持有全量注册的 `executors: Mapping[str, ExecutorPort]`，每轮查表执行后统一将 `selected_executor.executor_id` 与 `outcome.executor_session_id` 写入 `SessionStorePort`；`RunOutcome` 保持简洁不携带 `executor_id`。
  - `LocalCLIExecutor` 仅在 `session.executor_id == template.name` 且 `session.executor_session_id` 非空并配置了 `resume_args` 时启用原生会话续接；切换执行器时自动回退全新 `args`，绝不跨执行器错传原生会话 ID。
- **L3 入站驱动适配器**（直接调用 `EventHandler.ingest()`）：
  - `POST /events`：通用 JSON 事件接入（202 ACK）。内部来源名 `agent:forward`、`agent:return`、`agent:return_cancelled`、`agent:close`（`INTERNAL_SOURCES`）只由 Hibernaut 自己入队：`EventHandler.ingest()` 一律拒绝（HTTP 400，MCP `-32602`），运行时自己的事件走 `EventHandler.queue()` 或 Worker 直接入队。
  - GitHub Webhook 由 Switchboard 的 `/webhooks/github` 验签、按标签过滤并路由（见 §7）。Hibernaut 经同进程桥或 Relay 接收 `CanonicalEvent`，以 `scope` 为 `inbox_id`、`sb:github` 为来源、`event_id` 为去重键。Issue 标题与正文经桥接写入 payload 顶层 `title`、`body`，供 SDE 取需求与 PR 标题。
  - `MCPServerAdapter`（`adapters/channels/mcp_server.py`）：纯标准库 MCP JSON-RPC 2.0 入站控制面（`initialize`、`notifications/initialized`、`ping`、`tools/list`、`tools/call`），暴露 8 个核心 Tool（`hibernaut_ingest_event`、`hibernaut_list_sessions`（含 `status` / `work_key` / `executor_id` / `executor_session_id` / `parent_session_id`，可按 `parent_session_id` 过滤子会话）、`hibernaut_list_events`（含 `session_id` / `status`，以及取自 `SQLiteInboxAdapter.diagnostics()` 的 `attempts` / `last_error`，取自 payload 的 `trace_id`（或 `_trace_id`）与 `parent_event_id`，没有则为 `null`）、`hibernaut_list_workspaces`、`hibernaut_get_held_return`（按 `approval_request_id` 或 `session_id` 读被扣住的回投全文）、`hibernaut_resolve_approval`（没有等着的请求时该事件直接失败，不运行 Agent）、`hibernaut_reclaim_workspace`、`hibernaut_close_session`（取到该 Inbox 的租约才就地关闭，返回 `status: closed`；有 Run 占着时排一条 `agent:close`，返回 `status: closing`，由 Worker 在那个 Run 之后关闭）），同时支持本机 `--mcp-stdio` 行帧直连与远程 `POST /mcp` Streamable HTTP（强制 `Authorization: Bearer <HIBERNAUT_MCP_TOKEN>` 校验，未配置 token 时默认禁用返回 404）。

  - **任务附件**（`DriveAttachmentStore`，`adapters/channels/gdrive_attachments.py`）：队列根下可选的 `附件/` 目录与四个队列目录一样按名发现（`gdrive.attachments_folder_id` 可显式覆盖；没有时附件不可用，文本任务照常）。任务引用附件的方式取并集、每个文件一次：frontmatter `attachments`（Drive 文件 ID，或 `附件/` 内文件的原名，同名多个时要求改用 ID；写法见上，元素可带引号），以及正文里以完整 token 出现（前后不是 `[A-Za-z0-9_-]`，链接 `/d/<ID>/` 也算）且确实直接位于 `附件/` 的文件 ID；正文里其他目录文件的 ID 不算附件。`on_run_started()` 在挪动之后，对批内每个任务文件的最新修订列出 `附件/`、经代理 `download` 下载到 `gdrive.attachments_dir/<任务文件 ID>/<附件文件 ID>/<文件名>`（worktree 之外，目录 0700、文件 0600，先写临时文件再改名；Google Doc 存为 `.md`），并返回替换 payload：正文末尾追加 `## 附件` 段，列出每个附件的原名、本地绝对路径、字节数与 sha256。引用了但不在 `附件/`、超限、代理拒绝或下载出错的，在同一段「没有拿到」下逐条写明原因，任务照常开始；不认识的写法（如没闭合的 `[a, b`）不猜，按逗号切开照常匹配，带方括号或引号而没找到的那项在原因里附上引用原文和支持的写法；一个没找到的引用去掉方括号、引号后与本次已下载的某个附件的 ID 或原名相同（如正文里也写了同一个 ID），不再列为失败；列不出 `附件/` 时每个 frontmatter 引用各写一条，另写一条「正文里的 Drive 文件 ID」说明正文引用未能识别。`gdrive.attachments_dir` 默认是 `runtime.db_path` 所在目录下的 `attachments/`。清理：`handle_run_report()` 每次 Run 后调用 `sweep_attachments()`，删除没有 `active` / `suspended` 会话持有 `gdrive:<file_id>` 的任务目录（先列目录再查会话：Run 在下载前已保存 active 会话，因此正在用的目录不会被当成孤儿）；会话经 `Emit(close_session=True)` 或 MCP 结案后，下一次 Run 报告即清掉；`write_failure()` 把文件挪进 `失败/` 时直接删除该任务的附件目录。`DriveResultWriter` 按执行终态回写 `## 执行结果（Hibernaut）` 并流转至 `已完成/`（`Emit`）、留在 `执行中/` 并同步走飞书/终端通知（`Suspend`）或移至 `失败/`（`failed`）；开始时没挪成、仍在 `待执行/` 的文件，`Emit` / `failed` 直接挪到结果目录，`Suspend` 先挪进 `执行中/` 再追加（追加会改 `modifiedTime`，留在 `待执行/` 会被当成新修订重新入队）。用户补充内容并移回 `待执行/` 时产生新事件，开始执行时再挪到 `执行中/`，按同一 `correlation_key` 续接原 Session 与 `hb-*` worktree。
- **外置 Drive 队列凭据代理**（`adapters/credential_proxy/gdrive_queue.py`，部署见 `deploy/gdrive-proxy/`）：独立进程，以独立系统用户（macOS `_hbdriveproxy` LaunchDaemon / Linux `hb-drive-proxy` systemd）运行，代码装在 root 所有的 `/opt/hibernaut-drive-proxy`，密钥 `/etc/hibernaut-drive-proxy/sa.json` 仅该用户可读（0400）。代理与 Drive 通道共用 `adapters/gdrive_contract.py` 中的类型和目录解析函数，该模块仅依赖 Python 标准库。代理代码变更后用 `install.sh --upgrade` 升级：只替换 `/opt` 下的代码与启动器，沿用 `/etc/hibernaut-drive-proxy/` 下的密钥、client token 与配置，新代码通过只读 `--check` 后才重启服务，失败则换回旧代码。它用 Service Account 签 RS256 JWT 换取并缓存 Access Token（多线程共用一把锁），自行调用 Drive。`DriveQueueGuard` 只开放 7 个操作：`subfolders`（仅队列根，返回四个队列目录及存在时的 `附件`）、`list`（四个队列目录或 `附件/`；跟随 `nextPageToken` 取完所有页，每页 100）、`meta` / `read` / `append`（仅直接位于四个队列目录内的 Markdown、文本或 Google Doc 文件；读上限 2 MiB、追加上限 256 KiB）、`move`（两端都是队列目录、互不相同、文件确在源目录；`附件/` 不在其列）、只读的 `download`（仅直接位于 `附件/` 的非目录文件：二进制原样返回 `application/octet-stream`，文件名（百分号编码）、类型与导出类型放在 `X-Drive-File-Name` / `X-Drive-Mime-Type` / `X-Drive-Export-Mime-Type` 头；Google Doc 导出，其他 Google 文件 415；大小上限 `max_download_bytes`，默认 100 MiB，先按 Drive 元数据的 `size` 拒绝、不取内容，导出内容取回后再查，超限 413）。`read` 与 `download` 对 Google Doc 先按 `text/markdown` 导出，Drive 拒绝时回退 `text/plain`；`append` 仍以纯文本读回再写回。Hibernaut 侧 `CredentialProxyClient.call_service_bytes()` 取原始字节与响应头，`ProxiedDriveClient.download()` 据此组 `DriveDownload`。HTTP 层只收 `POST /proxy/<service_name>/<op>`，要求 `Authorization: Bearer <client token>`（常量时间比较），带 `Origin` 的浏览器请求 403，其他路径或操作 404，非 POST 405，请求体超 1 MiB 413；ID 须为 `[A-Za-z0-9_-]`，防止注入 Drive 查询；不转发上游响应体，只回 `Drive returned HTTP <status>`。只能监听回环地址；密钥或 token 文件对组或其他用户可读、或属主不是当前用户时拒绝启动。`--check` 只读解析四个队列目录与 `附件/` 并计数（没有 `附件/` 时注明）。
- **L3 文件 Outbox**（`FileOutboxChannel`，`adapters/channels/file_outbox.py`）：`[channels] outbox_dir` 设置后（相对路径以 `hibernaut.toml` 所在目录为准，支持 `~`；不设置时不建目录、不写文件，行为不变），`build_daemon` 把它包在通道链最外层：先写文件，再把原样的 `(inbox_id, content, metadata)` 交给内层（Drive 回写 → Switchboard 或控制台）。
  - **文件**：每条消息一个 Markdown 文件，文件名是本地时间到毫秒（`20261122-181305.123.md`），按名排序即时间顺序；同一写入者在同一毫秒内的下一条会等时钟走过这一毫秒（最多约 5 ms），与目录里已有文件重名则加 `-2`、`-3` 后缀，从不覆盖。目录不存在时自动创建。先写入隐藏临时文件并 `fsync`，再用 `os.link()` 原子地以最终名发布（目标已存在即失败，不覆盖），最后删除临时名，读到的 `.md` 总是完整的。
  - **失败与重试**：写文件失败记 ERROR 日志并抛出，`OutboxDispatcher` 照常按退避排期重试（`schedule_retry`，见 7.3「上行退避」），内层通道这次不投递，消息不丢。文件写成但内层投递失败时，重试复用已写的文件，不重复写。
  - **控制台**：启用时 `ConsoleChannelAdapter(echo=False)` 不再打印全文，`FileOutboxChannel` 每条打一行摘要 `[OUTBOX] <时间> <状态> | <任务标题> | <文件路径>`。文件路径相对 `hibernaut.toml` 所在目录显示（如 `outbox/20261122-193129.358.md`）；`outbox_dir` 在配置目录外时，在 home 下显示 `~/...`，否则显示绝对路径；直接构造 `FileOutboxChannel` 而未传 `display_base`（测试、demo）时保持绝对路径。只影响控制台摘要，文件名与文件内容不变。
- **Outbox 上下文头**（`outbox_context()` 读出 `OutboxContext`，`render_header()` / `render_summary()` 渲染，文件与控制台摘要共用）：任务标题、来源（事件 `source`，加可读名：GitHub / Drive / MCP / 飞书 / Switchboard / 定时器 / `/events`）、`inbox_id`、`correlation_key`、会话 ID、执行器、状态、需要人做什么、时间，之后是 `## 正文` 与原文。缺的字段写「无」（如 worktree 回收告警这类非 Worker 消息）。**状态与需要人做什么**按 `task_context.status` 取：完成、失败、已停止、已拒绝、等待审批；状态为完成且 `task_context.delivery` 的交付停在 `pr_open` 时另看 `auto_merge`：为 true（本该合并却没合并，如评审不通过、CI 失败、合并被权限挡住或审批被拒）显示「待合并」，需要人做什么写「查看 PR <链接>，未合并原因：<评审不通过 / CI 失败 / 其他>（<交付记录里的原文>）；处理后手动合并或重新提交任务」，原因缺失写「未记录」；为 false（PR 即预期终点）仍显示「完成」，需要人做什么写「审阅并合并 PR <链接>」。`merged`、`local` 与无交付的结果显示不变。控制台摘要的状态与文件头同源。Outbox 不查 GitHub，只读交付步骤写下的结果。等待审批的消息另有 `## 审批`：审批请求 ID、可直接执行的批准 / 拒绝 `curl`（POST 到本机 `/events`，地址取 `[channels] host/port`，通配地址换成回环；body 为 `inbox_id`、`source = "events:approval"`、`external_id = approval:<id>:approve|reject`、`payload.approval_request_id`、`payload.approved`，可加 `payload.comment`）与 MCP `hibernaut_resolve_approval` 的参数。飞书与 Switchboard 出站正文不变。
- **状态来源**：执行器在 L0 `Emit.status`（`EmitStatus = done | failed | stopped | refused`，缺省 `done`，旧代码不传即为完成）上明确标注结束方式，不解析正文：SDE `development failed` 为 `failed`、`stopped:` 为 `stopped`；评审者 `review failed` 为 `failed`、权限 `block` 为 `refused`；`LocalCLIExecutor` 无检出 / 未知模板 / 非零退出为 `failed`、工作区隔离拒绝为 `refused`；Orca 启动被 `block` 为 `refused`、续接被拒为 `stopped`。`Suspend` 的消息状态为 `awaiting_approval`。

## 4. 本机自举闭环：`OrcaWorktreeManager`、`LocalCLIExecutor` 与声明式配置

- **极简可读 Worktree 命名**（不含 repo 名与哈希）：GitHub Issue `#N` → `hb-issue-<N>` / `hb/issue-<N>`；PR `#N` → `hb-pr-<N>` / `hb/pr-<N>`；其他任务 → `hb-task-<seq>` / `hb/task-<seq>`；同仓库重名自动顺延 `-2`。
- **工作区决策优先级**：`explicit_workdir`（只读覆盖口）→ SQLite `workspaces` 表已落盘路径（按 `correlation_key` 复用）→ 动态创建（默认 `orca worktree create`，可选 `orca terminal create`，支持切换纯 `git worktree add` 后端）。命名与 `creating` 占位在同一把进程内锁下完成，同一 `work_key` 的并发请求拿到不同目录名。`workspaces.inbox_id` 记录创建该行的 inbox（新增列，旧行为 `NULL`）。
- **一个项目服务多个 inbox**（`app/projects.py`）：`[projects.<name>] inbox_id` 为字符串（单个精确 ID，原写法，原样比较、不当正则）或数组（每项直接是正则，`fullmatch` 整串匹配，如 `proj:hibernaut:.+` 匹配 `proj:hibernaut:drive`、不匹配 `proj:hibernaut:`）。数组里不含正则语法的项（只允许 `\.` 这类转义标点）只能匹配一个 ID，即精确 ID（`InboxRule.literal`，去掉转义后的原文）；只有精确 ID 能当投递地址，表达式本身从不作为投递地址。第一个精确 ID 是主 inbox。飞书和 GitHub 由 Switchboard 的群聊或仓库路由选定 `scope`，该值须匹配项目的一条 inbox 规则；其他渠道自配的投递目标（如 `gdrive.default_inbox_id`）不经项目规则，行为不变。旧写法的 `re:` 前缀仍接受：去掉前缀后同样按正则匹配，且该项从不算精确 ID（与旧语义一致）。加载时拒绝：空数组、非字符串或空项、空或非法正则、同项目重复项（`re:x` 与 `x` 算重复）、无精确 ID 的数组（含未转义 `.` 的 ID 算正则，报错提示写成 `\.`）、以 `re:` 开头的字符串、同一精确 ID 分属两个项目、一个项目的精确 ID 被另一项目的正则匹配、两个项目的正则有共同能匹配的 ID（`app/inbox_patterns.py` 求两个正则的交集，报错给出一个共同 ID）。为能判定交集，两个项目都写正则时只支持字面字符、`.`、ASCII 范围的字符类、`\d` `\w` `\s` 及其反义、分组、`|`、量词、开头的 `^` 与结尾的 `$`；环视、反向引用、`\b`、占有量词与原子组、行内标志、非 ASCII 范围或过大的正则在加载时拒绝。热加载被拒时沿用原配置。分发时仍查一次：`ProjectRouter.resolve(inbox_id)` 收集匹配的不同项目（同项目多条规则算一个），多于一个抛 `AmbiguousProjectMatch`（继承 `ExecutorFailed`）；组装根的 Worker 工厂在建 Worker 前解析项目，因此歧义在拿租约、选执行器、分配工作区之前抛出，`AsyncWorkerPool` 记录异常，事件保持 `pending`。检出路径等按 inbox 查的设置用 `ProjectInboxMap`（惰性 `Mapping`，正则匹配的 inbox 也能查到），执行器、默认执行器、worktree/终端后端、回收（含 MCP `hibernaut_close_session` / `hibernaut_reclaim_workspace` 经 `worktree_manager_for` 选项目的管理器）都按解析出的项目取。队列、租约、会话、记忆分区仍按 `inbox_id` 各自独立。
- **未匹配项目的 Inbox**：解析结果为空时，工厂给 `AgentWorker` 传 `hold`（`UnmatchedProjectHold`，每代配置一个实例）；需要项目检出的事件（无 `explicit_workdir`/`review_of`，不是审批回复或关闭请求，也不是挂起会话的跟进）被判为等待：Worker 只用 `InboxPort.claim_pending(inbox_id, event_ids)` 领取其余事件，等待事件不领取、不增加 `attempts`、不绑定会话，也不参与 `fold` 合并和 `interrupt` 判定；全部等待时 Worker 立即释放租约返回，不轮询、不占池位。每个事件进入等待时记一条 `WARNING`（`agent_runtime.app.projects`，含 `event_id`、source、`external_id`、`inbox_id` 与原因），同代内不重复。`AsyncWorkerPool(pending_inboxes=SQLiteInboxAdapter.pending_inbox_ids)` 在每次启动（含热加载后的新池）唤醒一次所有有 `pending` 事件的 Inbox，规则补齐后原事件按原串行与幂等语义只处理一次。
- **非项目 Inbox 的显式 `workdir`**（`[[runtime.inbox_bindings]]`，`app/projects.py` 的 `WorkdirBinding`；使用规范见 [`inbox-conventions.md`](inbox-conventions.md)）：`sys:*` / `user:*` 等不属于项目的 Inbox 在部署文件里绑定 agent 与启动目录。键与项目绑定相同，另有必填的 `workdir`（`~`、相对配置文件目录均可，不自动创建）与可选的 `checkout_access`（`readwrite` 默认 / `readonly`）；第一个整串匹配的生效。
  - **解析**：先按项目匹配，没有项目再看 `RuntimeConfig.workdir_binding()`，都没有才由 `UnmatchedProjectHold` 挡住。有绑定时不再等项目，白名单、规则、默认 agent 与项目绑定走同一条 `InboxRoute` / `LimitRoute`；`LocalCLIExecutor(bound_workdir=…)` 直接以该目录为 `cwd`，不建 worktree；事件里的 `explicit_workdir` 与它不同（同样按 `directory_key()` 比较）则拒绝。目录不存在时由 `MissingWorkdirHold` 让事件保持 `pending` 并记 `WARNING`，下一个事件、重启或热加载时重判；`UnmatchedProjectHold` 放行的 `review_of`、审批、关闭与挂起会话的后续在这里也等，只有 `explicit_workdir` 指向别的目录的事件放行，由执行器拒绝。
  - **不可用的 `inbox_id`**：正则绑定（或项目规则）可能匹配到含 `/`、`\`、`..` 或过长、建不出 Memory 目录的 ID。Worker 工厂先 `check_inbox_id()`，工厂的 `ValueError` / `OSError` 由池转成 `InboxRefused`：记一条 `WARNING`，事件保持 `pending`，不重新入队，Worker 协程继续服务别的 Inbox。
  - **可用的 agent**：不带 `role` 的 CLI agent；`checkout_access = "readonly"` 的绑定还可用 `steward`（目录即绑定的 `workdir`，agent 自己写的 `workdir` 与它不是同一目录则拒绝加载），注册给该绑定的只有它列出的 steward。`sde`、`code-reviewer` 依赖项目检出或其 worktree，写进绑定即拒绝加载，也不注册给这些 Inbox；`agents` 省略时指所有不带 `role` 的 agent 加上绑定点名的 steward。
  - **加载与热加载校验**（`parse_workdir_bindings()`、`validate_workdir_bindings()`）：缺 `workdir`；`forward_to` 有一项既不是某个项目的主 Inbox、也不是系统 Inbox（报错点名）；`system_tools` 绑定不是单个精确 `sys:<name>`、不是 readonly、有不是 `steward` 的 agent 或写了 `forward_to`，列出系统 Inbox 的来源绑定不是精确 ID、readonly、全 `steward`（`_check_system_binding()`）；`ops_tools` 绑定受同样的限制，且不能与 `system_tools` 写在同一条；`repo_tools` 绑定不是精确 ID、不是 readonly、有不是 `steward` 的 agent、是 `sys:` 或带系统工具（`_check_repo_binding()`）；有 `repo_tools` 而缺 `[repo_tools] owner` 或 `[gdrive] proxy_url` / `proxy_token_file`，有 `ops_tools` 而缺 `[ops_tools] dokploy_script`；定时器与群入口不能指向 `ops_tools` 的 Inbox；两条绑定指向同一个可写目录（`directory_key()`：已存在的目录按 inode，尚不存在的部分按最近的已存在父目录加不分大小写、Unicode 归一后的名字；`WorkspacePartitionRegistry.register()` 用同一个键，每次重算）；可写绑定的 `pattern` 能匹配多个 Inbox；可写目录等于或位于某个项目的检出、或某个 Steward 自己的 `workdir` 之内；`pattern` 与任何项目的 `inbox_id` 规则（精确或正则）有交集。`readonly` 可共享目录；它是部署方的声明，运行时在提示里写明不改文件，不拦 CLI 的写操作。
  - **转投范围**：每条绑定自成一个范围（`WorkdirBinding.route()`），在本绑定内接力，不与别的绑定互投；出绑定只有 `forward_to` 列出的项目主 Inbox 与系统 Inbox 这一个方向（见上「跨范围转投」）。
- **接入项目与补配置**（`app/onboarding.py`，命令行 `scripts/onboard_project.py` 与系统工具共用）：
  - **步骤**：`Onboarding.onboard()` 先按将要写的整份配置试解析，再核对仓库可达、克隆、`orca repo show` / `repo add` 登记（`orca worktree create` 只认已登记的仓库）、建标签（系统工具只在 `[onboarding] label_owners` 的 owner 上建），最后才写配置，所以前面失败时配置原样，报错写明留下了什么；本次建到一半的克隆会删掉。`complete()` 只补缺的键，`check()` 只读。外部命令是固定参数列表，不经 Shell，仓库名与项目名严格校验，每条有超时，超时杀整个进程组。
  - **改 TOML**（`app/config_edit.py`）：`TomlEdit` 只插入文本（表里加键、数组加元素、追加表），不重写；插入后核对 `tomllib` 的结果恰好等于在原结果上做同样的改动，所以原有注释与未涉及内容逐字不变，写不进去的形状（如点键、跨行的内联表）拒绝并列为待人做。
  - **写入**（`ConfigFile`）：进程内锁加目录 `flock` 覆盖整次调用；写前比对原文件，变了就放弃；备份 0600；临时文件 `fsync` 后原子替换。系统工具写完由 `ReloadStatus.wait()`（`app/reload.py`，`serve_configured()` 每处理一个版本就 `settle()`）等这份内容被采用；被拒或超时且文件还是这份内容时恢复原文件，再等恢复的版本，错误里说明。编辑器不参与锁，所以 `config_changes()` 解析后重读文件，字节变了就不用、也不结算这一版；`serve_configured()` 停完旧服务（发布前最后一次 await）后再比一次磁盘，不是这一版就丢弃新组装的代、恢复旧服务、不结算，没被结算的版本由 `config_changes()` 重读；比过之后到 `settle()` 之间没有 await，新代在这时才接管 Switchboard 订阅、转投白名单与 HTTP 入口，旧监听在结算之后才关。`settle()` 带所结算版本的摘要，`wait()` 只认同一摘要；等到之后再读一次文件，已不是这份内容就保留对方的版本、说明备份在哪，不报已生效。命令行写完不等。
- **共享项目的写隔离**（`OrcaWorktreeManager(isolate_inboxes=True, primary_inbox_id=...)`）：服务多个 inbox（多条规则，或唯一一条不是精确 ID）的项目，每个写任务（`LocalCLIExecutor`、`SDEExecutor`）只能在 `(inbox_id, work_key)` 自己的受管 `hb-*` worktree 里运行。`workspace_key()`：主 inbox 用裸 `work_key`（与旧数据兼容），其他 inbox 用 `<inbox_id>/<work_key>`，同一 `correlation_key` 的两个 inbox 因此得到两个 worktree；`CoderReviewerExecutor` 与 SDE 的 `task_metadata` 也按这个键查写。启动前拒绝：主检出、`explicit_workdir` 不是该任务自己的 worktree（含另一个 inbox 的）、非 `hb-` 目录、归属其他 inbox 的记录；SDE 从检查点恢复时用 `assert_writable()` 复核检查点里的 workdir。拒绝时抛 `WorkspaceIsolationError`，`LocalCLIExecutor` 回 `refused: ...`，SDE 回 `development failed: ...`，不启动进程。`inbox_id` 为 `NULL` 的旧行，只有当引用它的会话全部来自请求方 inbox 时才被认领（写入 `inbox_id`），否则拒绝。字符串 `inbox_id` 的项目不启用隔离，行为不变。
- **三道安全保险**：
  1. **意图占位与对账**：创建前先在 SQLite `workspaces` 表写入 `creating` 占位，崩溃重入时先对账本地目录再决定复用或清理。
  2. **路径落盘**：分配名称时检查所有本地 `hb/` 分支，包括未挂载的分支。Orca 创建时可能再加数字后缀，执行器读取 `--json` 回执里的实际分支和路径，与主仓库的 `git worktree list --porcelain -z` 核对，确认是唯一且可用的独立工作区后登记为 `ready`。复用时用同一登记表校正 SQLite 的旧路径。执行器重试耗尽后，批次标记为 `failed`，失败原因写入 `event_inbox.last_error`（与认领计数 `attempts` 一样只在 L3 内部，经 `diagnostics()` 读取，不回填 L0 `Event`），Worker 池记录异常后继续处理其他 inbox。
  3. **引用计数前置门禁 + 三关安全回收**（`reclaim()`）：Worker 与 MCP 在会话结案后按同一 inbox 计数（`count_active_by_work_key(work_key, inbox_id) == 0`）才发起回收；`reclaim()` 再校验一次（共享项目的 worktree 只数归属 inbox 的会话，其他受管 worktree 数所有 inbox 的会话；若有 `active`/`suspended` 会话仍引用则拒绝回收并返回占用会话 ID），再执行双重归属校验（`hb-` 前缀 + `workspaces` 表记录）+ 证据关（`SQLiteWorkUsage.blockers()`：无 `review:<work_key>` 评审会话、无该任务排队或执行中的事件、该任务会话无 `open_runs` 登记（未结束的可接回 Run）、无未完成的交付；GitHub 明确答复无开着的 PR，`gh` 失败即视为缺证据；无暂存/未暂存/未跟踪改动；`HEAD` 的提交都在远端，或有已合并 PR 的 `headRefOid` 正是本地 `HEAD` 且其合并提交在远端分支上，即 squash 合并），认领 `reclaiming` 后立即再查一遍，任一不通过即释放认领、保留目录并经 Outbox 告警。关闭终端从不触发回收。Orca 后端使用 `orca worktree rm --worktree path:<workdir>` 移除工作区并保留分支。**目录已不在**（被人手、Orca 或旧流程删掉）时 `reclaim()` 不再走删除流程（`_forget_removed()`）：目录上已没有要保护的东西，第 0 关与第 2–4 关、合并证据都不再适用，仍须 `hb-` 前缀与第 1 关（`blockers()`）通过；再核对登记：`git worktree list` 仍列出该路径时先 `git worktree prune`，prune 后仍在（如被 `lock`）或列不出则保留记录并说明原因；Orca 后端再用 `orca worktree list --repo path:<主检出> --json` 核对，Orca 仍列出、列不出或结果被截断都保留。全部通过后认领 `reclaiming`、复查第 1 关且目录仍不在，在持有认领时把引用该 `work_key` 的 `active`/`suspended` 会话按 `close_session()` 结案（共享项目只关归属 inbox 的），再按认领删除记录；有 `merged_head` 时本地分支按同样规则删除。随后向归属 inbox（调用方给的 inbox，否则记录的归属 inbox）发一条 `reclaim_alert`，写明目录已不存在、记录已清理、关闭了哪些会话。交付时的回收、MCP `hibernaut_reclaim_workspace` 与后台清扫都走这条路径，不报错。
  4. **合并后自动结案与删分支**：执行器返回 `Emit(close_session=True)` 表示任务已完成（SDE 仅在交付状态为 `merged` 且无待开发跟进时这样做）。Worker 先照常写回结果（Outbox 消息、会话、事件 `done`、`RunReport`），再按 close-session 的同一路径 `_close_and_reclaim()` 关闭会话并发起回收；这一步在线程里执行并续租，异常只记日志，不让 Run 失败、不重试、不丢结果。会话关闭会清空其 `correlation_key`，因此 `RunReport.correlation_key` 保留写回时的值，Drive 结果回写（`DriveResultWriter.handle_run_report()`）优先用它。回收沿用上述全部门禁，被拒时只经 Outbox 发一条告警说明原因（如 `uncommitted changes present`），交付结果仍为 `merged`。CLI daemon 的回收回调（`worktree_reclaimer()`）从 `deliveries` 取合并证据 `merged_head()`（状态 `merged` 时的推送 head，`delivery.delete_branch = false` 时为空），有证据时：Orca 后端加 `--delete-branch`；git 后端在 `git worktree remove` 后删除本地任务分支；分支仍在（Orca 无法证明已合并而保留，或 squash 合并使 `git branch -d` 拒绝）时，仅当分支恰在该 head 才 `git branch -D`，否则保留并告警。远端分支删除后本地远端跟踪分支随之消失，第四关改由「squash 合并于该 head」（`_squash_merged()`：合并 PR 的 `headRefOid` 等于本地 `HEAD`，合并提交在远端）放行。
  5. **后台回收清扫（兜底）**（`adapters/executor_cli/reclaim_sweep.py` `WorktreeReclaimSweeper`）：交付时那一次回收保留不变；它若因排队事件、在线会话等被跳过，之后不会再有人触发，清扫负责重试。CLI daemon（`--config` 且配置了执行器）在服务里跑它：启动时立即一轮，之后每 `[runtime] worktree_sweep_interval_seconds` 秒一轮（默认 300：事件结束后几分钟内回收，每轮每个空闲受管 worktree 至多两次 `gh pr list`，远低于 GitHub 限额；`0` 关闭）。每轮只看 `workspaces` 表里 `ready` 状态、检出属于某个已配置项目、目录名带 `hb-` 前缀的记录，人手建的 worktree（无记录）、`creating` 中的记录、其他检出一律不碰。目录已不存在的记录不看会话引用与合并证据（读不到 `HEAD`，复用过的分支名也无从判断），直接交给 `reclaim()` 的「目录已不在」路径（见第 3 条）：第 1 关不通过、git/Orca 仍登记时保留记录，原因同样只记一次；通过则删除记录、关闭引用它的会话，并由清扫向归属 inbox 发一条 `reclaim_alert`（内容即 `reclaim()` 的说明）。目录仍在的记录照旧：对每条记录依次检查：任务有未记为已合并、带自己提交的任务记录时先查一次该分支的合并 PR 并更新记录（§14，会话还占着 worktree 也查）；再只读数据库的门禁（`in_use()`：第 0 关会话引用、第 1 关 `SQLiteWorkUsage.blockers()`，即无 `active`/`suspended` 会话、无 `pending`/`processing` 事件、无评审、无 `open_runs` 登记、无未完成交付），忙则不发任何 git / gh 调用；再要合并证据：`deliveries` 记录为 `merged`，或 GitHub 有该分支的已合并 PR 且其 `headRefOid` 等于 worktree 的 `HEAD`（`merged_at_head()`，防止复用同名分支的新任务被误认）；最后交给 `reclaim()` 走全部门禁与认领流程，回收方式与分支规则和交付时一致（Orca 后端 `orca worktree rm`，否则 `git worktree remove`；`merged_head()` 有证据时删本地分支；远端分支删除仍只在交付步骤里）。跳过不发 Outbox，只在 stderr 记一行，同一 worktree 原因不变时不重复记；只有最终回收（或清理目录已不在的记录）时向归属 inbox（无归属记录时为项目主 inbox）发一条 `reclaim_alert`。停机遵守排空顺序：收到第一次停机信号（`halt`）后不再开始新一轮，进行中的一轮做完当前这条记录即停；热加载时旧代清扫随旧代服务停止，新代启动时立即清扫一轮。

  - **可用表**（`[availability] file`，`read_availability()`）：`{"version": 1, "generated_at": …, "executors": {"<id>": {"available": bool, "reason": str}}}`，由外面的程序写，建议写临时文件再改名。没列到的算可用，多余的键忽略，不看 `generated_at`。缺失、不是普通文件、超过 1 MiB、不是 JSON、`version` 不是 1、`executors` 或某项的 `available` 类型不对：整张表不用，全部算可用，记一条 warning。Hibernaut 不认识任何额度接口（C2）。
  - **选一次，记住**：任务第一次评审前读一次表，取列表里第一个没被表、额度标记排除的。结果存 `reviewer_choices`（`SQLiteReviewerStore`，主键是会话与 SDE agent；记评审者、任务自己的候选列表、每次选择的原因），不放检查点或 `state.json`，所以后续轮次、挂起恢复、状态文件坏了的重启、PR 打开后的跟进都是同一个评审者；之后的表、标记和热加载改的列表都不影响它。新会话重新选。已选的执行器从配置里删了，才按任务的列表换下一个，也算换人并通知。任务开始时是单个名字、后来改成列表的，保留原来那个；仍是单个名字的，跟配置走（原行为）。同一会话改派给另一个 SDE agent，它按自己的列表选。
  - **额度报错**（`quota_errors`，正则列表，`quota.py`）：写在 `[executors.<id>]`，CLI 模板与 Claude Code 驱动都可以，用它的 agent 沿用；不合法或能匹配空串的正则拒绝加载。`CLIReviewer` 在非零退出且完整 stderr 或 stdout 命中时抛 `ReviewQuotaExhausted`（文字与普通失败相同）；`CoderReviewerExecutor` 非交互时看 stderr、`result` 消息与非 JSON 行，不看对话内容，交互会话没有退出码，不判断。退出码 0、超时、起不来都不算。只有内置 `grok` 模板带默认正则（2026-11-23 的 402 原文）。
  - **换人**：命中后写 `reviewer_quota_marks`（到期时间取较晚的，默认 60 分钟，`quota_cooldown_seconds`），到期前所有任务都不选它，重启仍在；当前任务按自己的候选列表换下一个，重跑这一轮（不再发给开发者，轮次不加），后续轮次用新的。同一轮里报过额度的不再试。非额度失败照旧 `review pending`，不换。评审者报错前改过 worktree 的不自动换，挂起等人看过；批准后由下一个接手。单个名字的 SDE 命中时也记标记，任务照旧挂起。独立派单的评审不换也不记。恢复时 `state.json` 里登记的评审轮次带评审者名，别的评审者不会接它。
  - **全不可用**：检查点阶段 `no_reviewer`，`Suspend` 列出每个候选不可用的原因，走审批请求的通知路径。批准后按当时的配置列表和表重选，只重跑评审（有跟进先开发）；额度标记批准后仍有效，到期时间写在消息里。拒绝则标注未评审交付。
  - **说明**：列表部署的评审历史每轮带 `by <评审者>`，交付、停止与评审挂起的消息和 PR 正文「Review」小节有一行 `Reviewers:`，写选了谁、跳过谁、哪轮换成谁和原因，没换写 `not switched`。换人时发一条 Outbox 消息（`kind = "reviewer_switch"`，`outcome_kind = "emit"`，回到任务的来源），与选择记录同一事务，只发一次；被可用表排除不发，由写表的一方通知。
  - **`peer_reviewer`**：独立派单的评审总来自 `code-reviewer` 角色。`reviewer` 是列表时取列表里第一个这种角色的执行器，没有则取配置里第一个；不看可用表。接入项目时取列表里第一个是 agent 的。
  - **测试**：`tests/unit/test_reviewer_candidates.py`、`tests/integration/test_reviewer_candidates.py`。
- **SDE 执行器**（`SDEExecutor`，`adapters/executor_cli/sde.py`）：`[executors.<id>]` 写 `role = "sde"` 时注册，派单用 `payload.executor_id = "<id>"`。启动配置同共用适配器，默认 `claude-code / claude / subscription / claude-opus-5-5 / high`；另有 `review`（布尔，默认 `true`，非布尔报错）、`reviewer`（默认 `code-reviewer`；`review = true` 时必须是已声明的评审角色执行器或普通 CLI 模板（含内置模板），指向 sde 角色、指向自己或不存在的名字解析时报错并列出可选项；未显式写 `reviewer`、没有名为 `code-reviewer` 的执行器但有名为 `coder-reviewer` 的评审角色执行器时回退用它）、`max_review_rounds`（正整数，默认 3）。热加载重建执行器，下一次运行使用新值。
  - **工作区**：同 `LocalCLIExecutor`：`explicit_workdir` → `workspaces` 表按 `correlation_key` 复用 → 动态创建。
  - **开发**：`--permission-mode dontAsk`，放行 Read/Grep/Glob/Edit/Write/MultiEdit/NotebookEdit/Bash 与只读的记忆工具（§14「SDE 的记忆工具」），禁止 `git push`、`gh pr create/merge`；在任务分支提交。系统提示为 SDE 契约 + 角色 Skill（默认 `builtin:sde`：先写失败测试并保存原始输出、最小修改、跑项目规定的全套检查），任务消息为需求 + 按 `activities`/`tags`/`labels` 选出的项目规范（见「项目规范」）。`--json-schema` 约束报告（`status = done | needs_input`、`summary`、`test_evidence`、`question`、`decision`（开发提问卡）、`change_kind = breaking | feature | fix | test_docs`、`change_rationale`），`done` 缺测试证据、缺合法 `change_kind` 或缺理由均视为无效；契约要求按整个分支归类并说明理由，版本由 Hibernaut 据此决定。需求取 `requirements` / `text`，都没有时取顶层 `title` + `body`，拼成 `# <title>\n\n<body>`（Drive 任务；GitHub Issue 的标题与正文由 Switchboard 桥写入这两项，SDE 不读嵌套的 `issue`），正文为空时只用 `# <title>`；`title` 另作 PR 标题。可选的 `attempt_notes = "<目标名>"` 把任务的结局记进项目记忆（§14「任务记录」）。旧版入库的 `github:issue_comment` 事件不带需求：有等人的挂起会话时按跟进处理（内容为空则忽略，原请求保持挂起），没有时返回 `Silent`，不开新任务也不报失败。`needs_input` 返回 `Suspend`，回答可来自同任务的跟进消息或批准时的 `comment`，经 `--resume` 回到同一开发会话；拒绝则输出 `[sde] stopped: question declined`（含问题、工作区与已有进展），不算交付。权限门禁 `sde.launch` 在每次开发启动前检查（含修复轮）：`defer` 以 `launch_pending` 挂起并把完整状态与待执行提示词写入检查点，批准即执行该次启动，拒绝输出 `stopped: launch declined`；`block` 输出 `stopped: launch blocked`。
    项目配置 delivery 时由 HB 按部署授权发布；缺省时沿用 0.7.1 的 SDE 自行推分支和开 PR 流程，合并 PR 时通过 `--delete-branch` 一并删除源分支（若 worktree 占用导致本地删分支失败，确保删掉远端分支且不碰其他 worktree）。
  - **挂起期间的跟进**：同 `correlation_key` 的非审批事件记入检查点 `followups`，以原请求 ID 重新挂起；与审批决定同批到达的非审批事件同样计入；拒绝评审重试时交付消息列出未处理的跟进；恢复时并入需求，先交开发会话处理，再送评审者。引擎规则：`Suspend` 沿用会话当前 `pending_request_id` 时只更新检查点，不重发审批卡（`AgentWorker._apply_outcome`）。
  - **评审回路**（`review = true`）：SDE 在进程内调用同一配置代生成的评审者（`Reviewer`）的 `review()`：评审角色为 `CoderReviewerExecutor`（独立只读会话，保留评审者自己的启动器、计费、模型），CLI 模板为 `CLIReviewer`；两者门禁都是 `code_reviewer.launch`，给出的 `pass` 对 `PRDelivery` 的 `require_review` 同样算数，输入为需求、执行器自算的实际 diff 与测试证据；复审额外附上轮阻塞项和上次评审以来开发者自己的改动（增量 diff，剔除主干带进来的改动，见「剔除主干」），并只做增量复核（见下条）。`changes_requested` 把阻塞项经 `--resume` 交回同一开发会话修复后再送审；`pass` 交付。评审无法完成（评审者报错、结论无效、门禁未放行）或超过 `max_review_rounds` 时返回 `Suspend`，检查点 `{"sde": {...}}` 保存工作区、需求、证据、轮次历史与阻塞项；批准则重试（有阻塞项时再修一轮），拒绝则以 `review=pending` 交付，不标为已评审。
  - **增量复核**（`review_scope.py`，`ReviewScope`）：第 1 轮通审；有上一轮阻断项或交付步骤交回（`recheck`）、且有 `reviewed_snapshot` 时，阻断只能是上一轮某条没修好（`basis = "unfixed_previous"`，`previous_item` 写它在上一轮的序号），或上一轮之后的改动引入的新问题（`basis = "introduced_since_previous"`，`location` 落在改动的文件里）；完整 diff 仍作上下文，其余只能进 `notes`。规则写在评审契约和任务消息的 `## Incremental review` 小节（含改动文件清单与已记录的跟进），`basis` / `previous_item` 是 `REVIEW_SCHEMA` 的可选字段。**程序判定**：SDE 拿到任一 `Reviewer` 的结论后都调用 `ReviewScope.narrow()`，角色评审与 CLI 评审同一处判定：
    - `location` 落在改动的文件里（`git diff --name-only --no-renames <起点树> <本轮树>`，起点见「剔除主干」，含删除和改名前后两个路径）：保留。按文件而不按行判：改一处常在同文件没改的行上出错，按行会误降。
    - 标 `introduced_since_previous` 但不在改动文件里：降级。
    - 改动文件之外的其余阻断必须对应上一轮的某一条，且上一轮每条最多对应一条，多出来的降级；所以复审对未改动代码的阻断数不会超过上一轮。`previous_item` 有效时位置可以不同（缺测试、代码搬走，不因位置对不上就放过没修好的项），先按有效序号各取一条，再让没写序号的去匹配剩下的旧项（尽量多匹配，不互相挤掉）；同一序号有多条时取最贴近的：同触发条件、同位置、同文件、其他；改动文件里已有一条对应该序号时，只再接受同触发条件或同位置的。
    - 没有有效 `previous_item`：只接受能指认原问题的证据——`trigger` 文字相同且在同一文件（或 `location` 文字相同），或 `location` 的起始行落在上一轮那条的行范围里（改动文件之外行号不会移动）；只是同一文件不算，降级。
    - 降级项连同「已降级：原因」写进 `notes`，评审记录另有一行 `Downgraded to notes: ...`，历史写 `round <n> ... (<k> downgraded)`；一条阻断都不剩时结论为 `pass`。
    - 挂起期间人发来的跟进照常并入需求、先交开发，下一轮仍是增量复核；新增需求只作评审上下文，能指出是哪处改动引入问题的才按第二类阻断，否则保留真实位置写进 `notes`。
  - **剔除主干**（`base_merge.py`，`without_base()`）：普通修复轮与检查失败交回的复审中，上次评审之后合入过主干时，增量的起点不是上次评审的树，而是用 `git merge-tree --write-tree`（git ≥ 2.38）把主干合进上次评审的提交得到的树，冲突文件里是 git 的冲突块；起点到当前树的差就只剩开发者自己的改动（含怎么解的冲突），主干带进来的文件不在增量 diff 与改动文件清单里，落在那里的「新问题」按规则降级。主干取 HEAD 已含的最新一个主干提交；有交付步骤时用 `<remote>/<base>`，交付交回后的复核先由 Hibernaut 重新 fetch（失败则用交回时记下的基线 SHA）；不开 PR（`open_pr = false`）或没有交付步骤时，只认一条基线分支，即完整 diff 所用的那条（任务的 `base_ref`，缺省依次取第一个可用的 `origin/HEAD`、`main`），在它和它的上游（本地分支才有，没设上游则 `origin/<同名分支>`）里取 HEAD 已含的最新提交，本地 `main` 落后不影响识别，合入别的分支照常算增量；配了交付而 `<remote>/<base>` 不在其中时，以交付配置的为准。复审的完整 diff 在本地基准落后时也改从该主干提交算起。交付步骤自己留下的合并与版本提交同样不算增量：交回时核对上次评审以来只有主干合并与版本号一处变化，（文件类型与模式不变、文本只差版本号）才把起点移到交回处；混有别的提交则照常给评审者看。
  - **跟进汇总**：各轮 `notes`（含降级项）按文字去重（忽略空白、大小写与降级原因）记入检查点 `review_notes`，交付时写进 PR 正文的 `## 跟进` 小节与 Outbox 消息的「跟进：」（没开 PR、停止、无代码改动的消息同样列出）。PR 小节每条一行，`@`、`#` 后插零宽空格以免误提醒人或关 Issue，整篇正文放得下（GitHub 上限 65536 字符）就完整列出，放不下时先把测试证据（再到摘要等）裁到能给跟进留出至多 2000 字符，再按剩余空间截断并写明未列条数，正文不因这一节超限；Outbox 始终是全文。
  - **关闭评审**（`review = false`）：开发完成即交付（`review=off`），不启动评审者。
  - **交付**：一条 `Emit`，含状态、五项启动设置、工作区、摘要、`Change: <kind> (<理由>)`、测试证据、评审历史与最后一次评审结论；项目配置了交付步骤时追加其状态、PR 链接、版本决定、检查、CI 与合并 SHA。`executor_session_id` 回填开发会话 ID。中断沿用 `supervise()`，不写半成品。
- **SDE 交付步骤**（`PRDelivery`，`adapters/delivery/pr_delivery.py`；状态表 `deliveries`，`SQLiteDeliveryStore`）：SDE 只负责开发、测试与本地提交（`git push`、`gh pr create/merge` 仍被禁用）；发布由 Hibernaut 在 SDE 报告 `done` 且评审通过（或 `review = false`、或拒绝评审重试后以 `review=pending`）后执行。配置只来自部署文件的 `[projects.<name>.delivery]`（`parse_delivery()`，未知键、`auto_merge` 无 `open_pr`、越出仓库的 `version_file`、无 `version` 命名组的 `version_pattern` 等均报 `ValueError`），被改动的仓库无法授予发布权限；不配置则任务以本地提交结束。`SDEExecutor` 的 `delivery` 由组装根按项目注入，未匹配项目的兜底执行器没有交付步骤。
- **交付证据、终端退出与回收**：事件处理与交付分开完成。SDE 每次报告 `done` 后，`inspect_worktree()` 对照任务起点钉住的提交检查 worktree（`git status --porcelain --untracked-files=all`、`git rev-list --count <base>..HEAD`）：有未提交改动（测试与文档同样算）或没有新提交时，自动打回开发者一次，仍未完成则 `Suspend` 为 `incomplete`，保留会话、终端与 worktree；报告 `code_change: false` 且无提交、树干净时以「无代码改动」结束，不评审不交付。`PRDelivery._confirm()` 要求远端分支与 `gh pr view` 的 `headRefOid` 都等于推送并通过检查的提交；`PRDelivery.unverified()` 列出尚缺的证据（授权合并时还要求已合并）。仅当 `close_terminal = true`、证据齐全、无待人回答的问题、无 `SQLiteWorkUsage.peers()` 报告的在线评审交流时，先把 SHA、PR URL 与可恢复会话 ID 写入 `deliveries`，再由 `OrcaVisibleRunner.release()` 关闭终端（绑定保留 native ID 供 `--resume`；关闭失败则保留 handle）。CLI 评审者的评审终端（检查点 `review_terminals`）在每次评审命令的结果读回后就已关闭，与 `close_terminal` 无关；`close_terminal = true` 时交付仍逐个再关一次（已关闭的不报错），不看交付证据，也不受开发会话的待答问题或在线评审交流影响。
  - **两项授权**：`open_pr`（推任务分支并创建或复用 PR）与 `auto_merge`（合并，须先有 `open_pr`）分开配置，并分别经 `PermissionPort.check("delivery.open_pr" | "delivery.merge")` 门禁：`defer` 以 `delivery_pending` 挂起，批准后带该授权重试；`block` 记为说明，按当前状态交付。Auto Mode 默认放行这两项（项目配置即明确授权），部署可移入 defer 名单逐次确认。
  - **准备**：工作区须干净、在任务分支上；在仓库级进程内锁下 `git fetch <remote> +refs/heads/<base>:refs/remotes/<remote>/<base>`，基线不是祖先时 `git merge --no-ff` 进任务分支（只有 `version_file` 冲突时用 `git merge-file --theirs` 取基线一侧，其余冲突 `merge --abort`，记录冲突文件、基线 SHA 与基线上触及这些文件的提交，交回开发，见「交回开发」）；从基线读版本，按 `change_kind` 定 `major` / `minor` / `patch` / 跳过（`bump_version()`），写入 `version_file` 并提交，分支自改的版本一律以此覆盖。随后按序运行 `checks`（同一 commit 已全部通过则不重跑），任一失败不推送，附输出交回开发（全部失败项都是退出码 127、即命令不存在时属于宿主机问题，直接挂起）。
  - **发布**：`git ls-remote` 与本地 HEAD 不同时才 `git push <remote> HEAD:refs/heads/<branch>`，从不强推；`gh pr list --head <branch> --state all` 找到同 head 已合并的 PR 则直接记为 `merged`，有开着的 PR 则复用并更新标题与正文，否则 `gh pr create`。所有 `gh` 调用带 `-R <projects.<name>.repo>`。标题按 `title_template`（`{title}`、`{version}`，版本未变时只用标题），正文含摘要、类别与理由、版本决定、检查结果、评审状态、跟进（评审 `notes`，有才写）与测试证据。
  - **关联来源 Issue**（`issue_link`，`closes` | `refs` | `none`，默认 `refs`，其他值解析时报错并列出可选值；热加载随执行器重建生效）：`SDEExecutor` 建任务时用 `source_issue()` 从任务事件识别来源 Issue（兼容已入库的旧事件：`source` 为 `github:issue_poll`、`github:issues`、`github:issue_comment` 时取 `payload.issue.number` 与 `repository.full_name`；其他来源看 `correlation_key` 或会话键是否形如 `github:<owner>/<repo>#<n>`；关于 PR 的事件的同形键指 PR，批次中有任一这类事件就不写、也不回退读键：`github:pull_request*` 来源、`payload.issue.pull_request` 存在（GitHub 对 PR 也发 `issues` / `issue_comment`）、Switchboard 转来的 `payload.metadata.work_kind = "pull_request"` 或 `metadata.github_event` 以 `pull_request` 开头；Switchboard 的 GitHub 评论事件为此在 `metadata.work_kind` 记 `issue` 或 `pull_request`，PR 上的 `issue_comment` 记 `pull_request`），记入检查点 `issue`，经 `DeliveryRequest.issue` 交给 `PRDelivery`。有来源 Issue 时 PR 正文第一行写 `Closes #<n>`（`closes`，GitHub 在合并进默认分支后关闭 Issue）或 `Refs #<n>`（`refs`，Issue 保持打开），`none` 不写；Issue 不在 `repo` 所指仓库（或未配 `repo`）时写 `<owner>/<repo>#<n>`。取不到编号时不写、不报错；`/events`、Drive、飞书、MCP 来源不受影响。复用已有 PR 时 `gh pr edit` 写回的正文同样带这一行。
  - **合并**（仅 `auto_merge = true`）：要求独立评审 `pass`（`require_review`）→ 门禁 `delivery.merge` → 轮询 `gh pr checks --json name,state,bucket,link` 直至全部 `pass`/`skipping`（超时挂起，批准再查；可被 `interrupt` 中止）。有检查 `fail` / `cancel` 时不合并：先判断是否抖动，同一 head 只重跑一次，从检查的 `link` 取 GitHub Actions run ID，用 hb 自己的 gh 身份 `gh run rerun <run> --failed`，记下被替换的失败链接（GitHub 登记新一次运行前仍显示旧的失败，旧链接按进行中处理），给重跑一段完整的 `ci_timeout_seconds`，重跑通过照常合并；没有重跑权限（HTTP 403、admin rights 等）、`gh run rerun` 报错或失败检查不属于 Actions 时跳过重跑并写进历史。重跑仍失败或跳过重跑时，用 `gh run view <run> --log-failed` 取失败日志（去掉每行的 job / step / 时间前缀），摘出 pytest 的 `FAILED` / `ERROR` 用例与 `FAILURES` 段，抛 `_Handback`（种类 `ci`）交回开发（见「交回开发」）；`DeliveryRecord` 的 `ci_rerun_head` / `ci_rerun_links` / `ci_rerun` 记住这个 head 重跑过，重启或批准重试不会再重跑。交付不会以 `pr_open` 加 CI 失败结束而无人跟进；每次轮询另查 `gh pr view --json mergeable,mergeStateStatus`，PR 为 `DIRTY` / `CONFLICTING`（GitHub 不为冲突的 PR 跑 `pull_request` CI）时不再空等，或检查持续为空达 `min(300s, ci_timeout_seconds/2)` 且基线已不是任务分支的祖先时，记一条历史后直接回到准备步骤 → 锁内重新 fetch 基线：若基线版本已变（并发 PR 先合并）或上一步判定 PR 已与基线冲突，回到准备步骤重新合入基线、重算版本、跑检查、推送、更新 PR 并再等 CI（至多 3 次）；否则 `gh pr merge <n> --<method> --match-head-commit <已测 SHA>`，再以 `gh pr view` 记录实际合并 SHA。
  - **删除远端源分支**（`delete_branch`，默认 `true`）：交付状态为 `merged`（本次合并，或确认 PR 已在别处合并）后，`git ls-remote` 查远端分支：已不存在记为成功；仍指向推送的 head 时 `git push <remote> --delete <branch>`（从不强推），失败后再查一次，已消失仍算成功；指向其他提交（合并后又有人推送）则保留。删除失败或保留只写入交付 `notes`，在回执中以 `Note: branch kept: ...` 列出，不影响合并结果。`delete_branch = false` 时远端与本地分支都保留，与此前行为一致。未合并（`pr_open`）或只留本地提交（`open_pr = false`）时不删分支、不结案、不回收。
  - **交回开发**（`max_handbacks`，非负整数，默认 2）：准备步骤里的非版本号冲突与检查失败、合并阶段重跑后仍失败的 CI 抛 `_Handback`，`DeliveryRecord.handback` 记下种类（`conflict` / `checks` / `ci`）、基线、分支、冲突文件与相关提交或失败输出；`ci` 另记 PR 链接、失败的检查与日志链接、失败用例、是否重跑过及原因。`SDEExecutor` 收到带 `handback` 的问题且本轮交回次数未达上限时，不挂起，经修复轮同样的续接方式（存活终端或 `--resume`，同 worktree、同分支，照常过 `sde.launch` 门禁）把问题交回同一开发会话：冲突时要求自行 `git merge <remote>/<base>` 并解决、提交合并；检查失败时要求在分支上修复；CI 失败时附失败的检查、日志链接、失败用例和日志摘录，要求查明原因修好，偶发失败要改成确定的而不是重试；两者都要求重跑项目检查并按原报告契约（含 `change_kind`）返回。之后若评审开启且上次评审已 `pass`：手工解冲突后一律复审，直接比较上次通过的工作区快照与当前快照，包含主干带来的差异。交回记录里的冲突文件也在复审范围内，即使保留任务侧内容导致快照间没有文本差异，评审者仍可对照合并提交的两个父提交检查取舍。检查失败与 CI 失败后的修复仍按剔除主干后的增量复审。评审通过后自动重试交付，从合入基线一步续接（交付步骤本身幂等）。合并阶段因 PR 冲突重新准备时同样适用。每次交回在交付消息与挂起提示（开发提问卡除外）里各列一行 `Delivery hand-back <n> of <limit>: <原因>; handed back to the developer`；达到上限后照旧以 `delivery_pending` 挂起，原因追加「Handed back to the developer <n> time(s) already (limit <limit>); a person decides now.」；CI 失败的审批卡首句为「合并前的 CI 检查未通过」，详情里逐行写失败的检查（附日志链接）、失败的用例、重跑结果（已在同一提交上重跑一次仍失败，或没有重跑及原因）与已交回次数，人批准（重试或带跟进）后计数清零；开发者返回 `needs_input` 照常挂起。没有交付步骤的 SDE（自行推送开 PR）不涉及。
  - **状态与恢复**：`local`（本地开发完成）→ `pr_open`（PR 已创建）→ `merged`（已合并），连同分支、基线 SHA 与版本、推送 head、PR、检查、CI、合并 SHA、尝试次数与历史按任务 `correlation_key` 存入 `deliveries`，每完成一步即落盘。远端 git / gh 报 DNS 解析失败、连接超时、重置或中断（包括 HTTP 请求以 EOF 结束、unexpected EOF、connection closed、broken pipe 和 TLS 握手报 `SSL_ERROR_SYSCALL`）、GitHub GraphQL 返回带时间戳的查询执行内部错误、HTTP 5xx 或限流时，SDE 保存 `delivery_retry` 断点。Worker 登记指向该会话和本次请求的一次性定时器，写回断点后释放 Inbox 租约。定时器依次延迟 1、5、15 分钟唤醒交付，每次从交付记录续接并照常过权限门禁。三次重试仍失败时，人工提示列出次数、间隔和最后一次错误。其余可恢复失败（包括普通 401/403、交回次数用尽的冲突、检查失败与 CI 失败、CI 超时和 `defer`）按原路径返回 `Suspend`（检查点 `stage = delivery_pending`，飞书卡片与 Outbox 共用中文正文：首句说明任务、步骤和原因，接着写批准和拒绝的后果，路径与原始错误等放在「详情」里），批准只重试交付步骤并从已记录状态续接（不重复推送、复用 PR、采纳他人已合并的 PR 且不再加版本）；拒绝则按当前状态交付并注明 `delivery declined`；挂起期间到达的跟进与批准一起触发重新开发、评审与交付。交付中被中断抛 `DeliveryInterrupted`，SDE 转为 `CancelledError`，不写 Outbox。
  - **认证**：`git`、`gh` 与检查命令的环境剥离 `GH_TOKEN`、`GITHUB_TOKEN`、`GH_ENTERPRISE_TOKEN`、`GITHUB_ENTERPRISE_TOKEN` 并关闭交互提示，由宿主机自身的凭据（`gh auth login`、git credential helper、SSH agent）或部署配置的可信包装命令（`git_command` / `gh_command`）在进程外认证，daemon 不持有 GitHub token。
  - **版本规则**：本仓库的规则在 `docs/process/versioning.md`，经 `guidance.toml` 按 `versioning` / `release` 活动（或评审 diff 触及版本文件）选取；纯测试任务不加载其正文。开发派单模板在 `docs/dispatch/`（`sde-task.json`、`sde-task.drive.md` 显式 `executor_id = sde`；`review-task.json` 用 `code-reviewer`；三者都投 `proj:hibernaut:sde`，评审与开发同一 inbox 才找得到 worktree）。
- **Orca 可见执行**：模板的 `orca_agent` 指定 Orca 管理的 agent。项目使用 Orca worktree 时，同一 Hibernaut 会话的后续事件回到已绑定的对话（`OrcaVisibleRunner`，`adapters/executor_cli/orca.py`）。绑定存在 SQLite `terminal_bindings` 表（键为 `session_id`，记录 `executor_id`、`agent`、`workdir`、终端 `handle`、进程 `incarnation_id` 与原生会话 ID），原生会话 ID 同时写入 `sessions.executor_session_id`，会话换了 `session_id` 也能按它找回绑定。每轮按顺序选择：
  1. **新开**：会话没有本执行器的绑定（且未带原生会话 ID）时 `orca agent launch --surface terminal` 在后台标签页提交，按回执记录终端句柄与 `incarnationId`。
  2. **复用**：绑定终端仍在 `orca terminal list` 中、`incarnationId` 与 `agentIdentity` 都一致时，用 `orca terminal send --enter` 投递到原对话（`terminal show` 的 `orphaned` 只表示尚无可见窗格，不作存活依据；同句柄换了进程视为另一个对话）。
  3. **恢复**：终端已关闭但有原生会话 ID 时，`orca terminal create --command "<command> --resume <id>"` 新开终端，等 `tui-idle` 并确认 `agentIdentity` 后再投递。
  4. **无法确认**：会话有绑定却既无存活终端也无原生会话 ID、工作目录变了、恢复没能启动 agent 或终端拒收时，什么都不发送，返回 `Suspend`（检查点 `{"orca_continuation": "unconfirmed"}`）说明原因；批准后才新开对话，拒绝则跳过本轮。建表迁移时，已有执行器的旧会话各补一条无终端、无原生 ID 的绑定，因此升级前跑过的会话走这一步而不会被当成新会话。
  原生会话 ID 不靠 agent 自报：每轮结果文件所在的临时目录名唯一且写在投递的 prompt 里，执行器在 Claude Code 转录目录（模板 `env.CLAUDE_CONFIG_DIR`、daemon 的 `CLAUDE_CONFIG_DIR` / `ORCA_CLAUDE_CONFIG_DIR`、`~/.claude` 下的 `projects/*/<uuid>.jsonl`）里找含该标记的会话，恰好一个（或与已绑定 ID 相同）才确认，否则不写入并记警告。完成以每轮唯一的临时结果文件为准。投递后中断或超时则先确认原生会话 ID、再关闭本轮终端，下一轮走恢复；启动回执或投递回执不确定时转为 `Suspend` 供人工确认，不重复投递。
- **角色交互会话**（`OrcaVisibleRunner.converse()`，`adapters/executor_cli/orca.py`）：角色执行器的 `interactive`（默认 `true`；旧名 `visible` 仍可读，同一执行器两键都写则配置报错）只表示每次运行需要人可接入的交互会话；`false` 走非交互（headless）。会话由项目的 `terminal_backend` 打开，与 `worktree_backend` 解耦：取值 `orca | none`，`worktree_backend = "orca"` 的项目默认 `orca`（行为不变），`git` 项目默认 `none`，可显式设 `orca` 在 git worktree 里开 Orca 终端；目前只有 Orca 一种实现。组装根（`app/main.py`）按项目给角色执行器传 `terminal`：非交互为 `None`，有后端为共享的 `OrcaVisibleRunner`，缺后端为 `TerminalUnavailable(reason)`（`terminal_backend = "none"` 的项目，或未匹配任何 `[projects]` 的 Inbox 所用的兜底执行器）。交互角色绝不静默改走后台：缺后端时 SDE 以 `terminal_pending` 挂起（检查点存完整状态与待发提示词，什么都不启动），配置改好热加载后批准即重试（权限门禁照常再跑），拒绝输出 `stopped: interactive session declined`；独立评审输出 `review failed: interactive review not started: <原因>`，内置评审使 SDE 进入 `review pending`。后端挂接失败（无 `orca` 命令、Orca 不认识该 worktree、会话检查失败）以 `ClaudeCodeError` 报告 Orca 的原因，同样不回退 headless。标题标明角色与任务：`sde · <task>`、`code-reviewer · review of <task> round <n>`（内置评审）、`code-reviewer · review of <task>`（独立 `review_of` 事件）；执行器名与角色名不同时写作 `<id> (code-reviewer) · ...`。
  - **启动**：`orca terminal create --command "exec python -I claude_gate.py <spec>"`。`claude_gate.py` 在终端内按角色计费剥离或注入环境变量，先以 headless 探针（`-p`、无工具）读 `init` 做与 headless 相同的 `check_init` 校验（订阅无配置以外的付费来源、api 只走代理、模型一致），结果写入本轮 `gate-status.json`，通过后以子进程启动交互式 Claude Code：同一组 `--model --effort --permission-mode dontAsk` 与角色工具参数，指令放在 `--` 之后。门禁脚本不再 `execvpe`，而是留在终端里监管：探针在独立会话里运行，交互式 Claude Code 在独立进程组里运行并接管终端前台（`tcsetpgrp`，同 shell 交出前台作业）；Claude Code 退出时门禁结束其进程组残留并以同一退出码退出，终端随之结束。Orca 的关闭可能报告成功却没送到信号，所以每个门禁终端有一个租约文件（`<tmp>/hibernaut-terminal-leases/lease-*`，`spec.json` 的 `lease`；按 handle 建索引）：Hibernaut 每次关闭该终端（`_close_quietly`、`release()`）都先删租约，门禁每 0.1 秒检查一次，租约消失、收到 SIGHUP / SIGTERM / SIGINT 或探针超时，就结束探针或 Claude Code 的整个进程组后退出。这些进程仍挂在 Orca 终端下，不是 hb 的子进程。
  - **结果回传**：启动器经 `--mcp-config` 挂上 stdio MCP 服务 `hibernaut_handoff`（`handoff_mcp.py`，`python -I`，仅标准库），`--allowedTools` 追加 `get_task` 与 `submit_result`。每轮在会话的 handoff 目录下建 `turn-*` 子目录，放提示词；终端只收到「调 `get_task(turn)`、完成后调 `submit_result(turn, …)`」的短指令。`submit_result` 的输入 schema 即角色 schema（另加 `turn`），服务端按 schema 校验，不合格返回错误让 agent 重交，合格则原子写入 `result.json`，`OrcaVisibleRunner` 轮询读取。`turn` 只接受 handoff 根目录下直接存在的 `turn-*` 名，无法指向别处。agent 不读写 handoff 目录，不需要 `--add-dir`：新加目录会弹出阻塞的信任对话框，而 worktree 本身的信任机制不受影响。
  - **peer 交接**（项目 `handoff = "peer"`，默认 `"mcp"` 即上一条；`adapters/executor_cli/peer_handoff.py`）：任务、返工与跟进都以 ccpeer 消息发给会话，结果由会话 `SendMessage` 发回常驻接收端，hb 从接收端收件箱按游标读取，交接不再依赖 hb 进程内的轮次目录。
    - **接收端**：`[peer] receiver`（默认 `hibernaut`）是 launchd 管理的 `python -m ccpeer serve --as <名字>`（`deploy/ccpeer/`），不随 hb 启停；hb 只读它的 `~/.ccpeer/<名字>/`（`[peer] state_dir` 可改），从不启动它。有项目设了 `handoff = "peer"` 而接收端不在时，`build_daemon_from_config` 直接抛错（`handoff = "peer" for <项目>, but the ccpeer receiver '<名字>' is not running ...`），hb 启动失败、热加载保留旧配置；不降级为 MCP 交接，以免同一任务在两种通道间漂移。运行中接收端消失，该轮以 `ClaudeCodeError` 报告，不起终端。
    - **起会话**：与 MCP 交接同一个门禁与参数（`--permission-mode dontAsk`、角色工具），区别是不挂 `hibernaut_handoff`、`--allowedTools` 追加 `SendMessage`、不带初始指令（会话空闲启动，任务随后以消息送达），门禁的 `unset` 加上 `CLAUDE_CONFIG_DIR`（设了它的会话会登记到别的配置目录，接收端找不到）。`--name` 仍是终端标题；新会话用 `--session-id <自选 UUID>`，续接用 `--resume <原生 ID>`。
    - **找到会话**：门禁通过后在 `[peer] config_dirs`（默认 `~/.claude`）的 `sessions/*.json` 里等登记（`register_timeout_seconds`，默认 120）：`sessionId` 等于该 UUID、非 standalone、cwd 是本 worktree；找不到时退而按 `--name`（含 Claude Code 加的 `-<words>` 后缀）与启动后的 `startedAt` 唯一匹配，并以登记里的 `sessionId` 为准。会话名、pid、socket 与本轮 `attempt_id` 写入 `terminal_bindings`（新增列 `peer_name`、`peer_pid`、`peer_socket`、`peer_attempt`）。

    - **收件箱与游标**：`SQLitePeerMailbox`（`storage_sqlite/peer_mailbox.py`）把接收端 `inbox.jsonl` / `control.jsonl` 的新记录写入 `peer_messages`（`msg_id` 主键去重），并在同一事务里把字节偏移写入 `peer_cursors`；记录要么仍在游标之后、要么已入库，hb 重启期间到达的结果重启后照样读到。偏移失效（日志被替换或截断）时从头重读，靠 `msg_id` 去重。被某轮取走的记录标 `consumed_at`，不会被下一轮再读。

    - **返工与跟进**：同一会话存活时直接发新任务消息（新 `attempt_id`，`task_id` 不变），不再 `orca terminal send`；终端存活但会话找不到登记时先关终端再 `--resume`，不会两个进程跑同一会话。MCP 模式遇到 peer 模式留下的存活终端同样先关再 `--resume`。
    - **结束会话**：`release()` 对 peer 会话先 `orca terminal send --text /exit --enter` 让 Claude Code 正常退出，等终端从 `terminal list` 消失且登记的 pid 退出（`exit_timeout_seconds`，默认 30）；未退出才删租约并 `orca terminal close`。

socket（`socketpair()`），一端经 `pass_fds` 与环境变量 `HIBERNAUT_HANDOVER_FD` 交给 daemon；daemon 停止 `serve_forever()` 后（`_close_server(release=…)`，在关闭监听之前）由 `ListenerHandover.release()` 以 `SCM_RIGHTS` 把监听 socket 发回，并等监督进程回 ack 再关闭自己那份（macOS 上只在传输途中的 socket 会随发送方关闭最后一份而连同 backlog 一起关闭；等 ack 至多 10 秒，超时则放弃交接）；监督进程在 `stop()` 里用 `select` 等这条消息并 ack（`Handback`），快进后把它设为可继承、写进 `HIBERNAUT_LISTEN_FD` 再 `execv`，新一代监督进程再经 `pass_fds` 与同名变量交给新 daemon，随即关闭自己那份。新 daemon 启动时 `ListenerHandover.from_environ()` 取走两个变量（执行器子进程看不到，fd 设为不可继承），监听地址与配置一致时用 `WebhookHTTPServer.adopt()` 直接在该 socket 上服务、不再 `bind`，不一致（停机期间改了端口）则关掉它、自己绑定新地址。交接全程总有一个进程持有监听 socket，期间的连接在内核 backlog（`request_queue_size = 128`）排队，新 daemon 开始 `serve_forever()` 后处理；排队时长即旧 daemon 停止接收到新 daemon 开始监听的间隔，生产上主要取决于新进程导入与组装耗时。daemon 运行期间只有它持有监听 socket，热加载换端口照旧关闭旧端口（之后拒绝连接）；不经监督进程运行、或监督进程启动的第一代 daemon，没有继承的 socket，照旧自己 `bind`；`--mcp-stdio` 关闭继承来的 fd。Switchboard 中继无需额外处理：旧 daemon 退出前 `RelayAgent.stop()` 发 close 帧断开，新 daemon 组装时订阅即发起首次连接（退避只用于连接失败后的重试）；进程内 Switchboard 自己的 HTTP 端口不在交接范围内。监督进程的信号处理器只给停机信号计数（处理器在主线程任意两条字节码之间运行，可能正处在主循环持有的锁里，如 `threading.Event` 的 `Condition`，在处理器里取锁会永久死锁），主循环以 `child.wait(timeout=…)`（停机等待阶段在等到交还的 socket 之前用 `select` 等这对 socket）有界轮询子进程与计数，收到第二次信号时把 SIGTERM 转发给 daemon；等待 daemon 退出不设上限，每 `--wait-log-interval` 秒记录监督进程 PID、daemon PID 与已等待时长；daemon 在独立会话中运行，监督进程把 SIGHUP 也当停机信号，SIGKILL 下 daemon 无法随之退出。Orca 终端里仍在运行的任务不会在重启后接回。

## 5. 多 `inbox_id` Actor 分区并发与 `NewEventPolicy`

- **多 `inbox_id` 并发**：`AsyncWorkerPool` 跨 `inbox_id` 并行、同 `inbox_id` 单活互斥（`worker_leases` 主键即 `inbox_id`）、`Suspend` 立即放锁；`WorkspacePartitionRegistry` 强制禁止不同 `inbox_id` 挂载同一本地代码目录，全局 `global/instructions.md` 只读共享。队列、会话、租约和工作区按 `inbox_id` 分，项目记忆按 `project_key` 分，同一项目的 Inbox 共用（§14）。
- **分级并发上限**（`app/concurrency.py` + `AsyncWorkerPool`）：计量单位是同时在跑的 Inbox（一次派发占一个名额）。全局 `[runtime] max_concurrency` 之外，`[projects.<name>]` 与 `[executors.<id>]`（CLI、角色执行器，以及只供 `[agents.*]` 引用的 Claude Code 执行器）、`[agents.<id>]` 可各写可选的 `max_concurrency`：`[agents.<id>]` 只限这个 agent，共用同一驱动的别的 agent 不受影响；`[executors.<id>]` 是该驱动上各 agent 合计的上限，旧写法里执行器即同名 agent，两者等价。正整数，`0`、负数、布尔、字符串在加载时拒绝并指明配置路径；大于全局值时照常加载，记一条 `WARNING`，实际受全局值封顶。
  - **准入**：`ConcurrencyLimiter.try_acquire(inbox_id, project_key=…, executor_key=…, agent_key=…)` 全局、项目、驱动、agent 四个维度都有余量才一起扣减，否则什么都不扣、立即返回 `False`；`release(inbox_id)` 按实际占用归还，幂等。只在池的事件循环上调用，检查与扣减之间没有 await，因此是原子的。
  - **调度（无队头阻塞）**：待调度队列是 FIFO 的 `deque`。Worker 协程从队头扫描，取第一条各维度都有余量的 Inbox；满额的留在原位，不占 Worker 协程。没有可派发的就等 `_changed` 事件，它在唤醒、归还名额、退役与停机时置位，没有轮询。归还后从队头重扫，等得最久的先得到名额。排队 Inbox 的限流键缓存到它下次被唤醒，只用来跳过仍然满额的 Inbox（重扫不读库）；放行前一律重新解析，因此别的线程刚写库、唤醒还没到事件循环的变更（如换执行器重放）不会按旧键派发，也不丢队列位置。
  - **限流键**：项目键来自 `ProjectRouter.resolve()`（未匹配项目为 `None`，不占项目名额；歧义不占项目与执行器名额，照旧由 Worker 工厂抛 `AmbiguousProjectMatch`，事件保持 `pending`）。agent 键是该 Inbox 下一步要跑的 agent：先是被停机脱离、等待接回的 Run，否则是第一条可领取的事件，按与 Worker 相同的规则选出 agent（`AgentWorker.expected_executor_id()`：挂起会话的持有者，否则 5 级选路 `resolve_agent_id()`，含 Inbox 绑定；与欠着另一项委派的会话分开的转投按新会话算），驱动键是它引用的 `[executors.<id>]`（旧写法即自身），只有给驱动写了上限时，引用它的各 agent 才合计受限。关闭请求、取消回投、等人批准的 held return、被绑定白名单拒绝的事件和被 `UnmatchedProjectHold` 挡住的事件不跑 agent，不占 agent 与驱动名额；解析失败记 `WARNING` 并退回 `None`，只受其余维度限制。执行器 ID 以 Worker 的路由为准：SDE 内置评审算在 SDE 的名额里，payload 的 `executor`（只换 CLI 模板）不改变计数。
  - **一个 Inbox 内有多种执行器**：一次派发只持有一个 agent（及其驱动）的名额。配置了 agent 或执行器上限时，Worker 的 `hold` 包一层 `ExecutorQuotaHold`：从第一条需要另一个受限 agent 或驱动名额的事件起，本次派发不再领取后面的事件（保持 Inbox 内顺序，也不参与 `fold` 合并与 `interrupt` 判定），派发结束后该 Inbox 自动重新排队，按那条事件的执行器准入；期间只重判挡路的那条（例如前一批改了会话粘滞的执行器），其后的事件不越过它。`hibernaut_replay_event` 重放的事件（可换执行器）按重放后的执行器重新判定，即使它在本次派发里已跑过。派发以 `ExecutorFailed` 结束时，失败批次已标记 `failed`（`batch_settled`）则照样重排；失败批次仍是 `pending`（执行器未注册、项目歧义）则等下一次唤醒，否则会原地反复失败。
  - **生命周期**：`retire()` 把所有排队的 Inbox（含等名额的）按序转交 `handoff`；`drain()` 丢弃排队的唤醒，事件留在 `pending`；`stop_event` 置位后已排队的仍跑完才退出；`wait_until_idle()` 要求队列（含等名额的）与活跃集合都为空。名额在 `finally` 归还，`ExecutorFailed`、歧义与取消都不泄漏；瞬时失败的退避重试属于同一个 Run，期间继续占用名额。热加载时新旧池共享同一 `ConcurrencyLimiter`：新配置校验并激活后原地更新全局、项目、执行器与 agent 上限，旧池仍在跑的 Run 继续计入占用（没有配置 agent 或执行器上限时也照样解析并计数；同一派发里后来换了 agent 的批次由 `AgentWorker(on_batch_start=…)` 在开跑前补计，到派发结束一并归还），所以热加载第一次写入的上限也算上它们，直至结束归还并唤醒新池，不会在热加载过渡期突破并发上限；非法配置或启动失败不改动当前限流器。
- **HTTP 入站与 SQLite 并发**：`WebhookHTTPServer`（`ThreadingHTTPServer`，`request_queue_size=128`）每请求一线程；`shutdown()` 等待在途请求全部写完 Inbox 后返回，停机（Worker 排空之后）与热加载换端口时关闭旧监听据此排空。`SQLiteDatabase` 只有一条连接，所有语句经同一把可重入锁串行；写操作走 `transaction()`（`BEGIN IMMEDIATE`），去重、租约等先读后写在线程间和共享同一文件的进程间保持原子；租约时钟在拿到写锁后读取，等锁时间不计入 TTL；`mark_done()` 按 SQLite 参数上限分段更新；文件库开启 WAL 与 `busy_timeout`。回收 worktree 时，`claim_for_reclaim()` 以读到的 `updated_at` 做比较并交换：进行中的 `reclaiming` 认领是排他的，只有超过 `reclaim_stale_after_seconds`（默认 600 秒，认领方已崩溃）的认领才可被接管；删除期间心跳线程定期续期认领（遇到临时的 `SQLITE_BUSY`/`SQLITE_LOCKED` 缩短间隔重试，不退出），慢删除不会被当作过期而被接管；删除成功后 `finish_reclaim()` 同样按认领做比较并交换，认领已失效时不删除被他人重新登记的记录；删除失败时 `release_reclaim()` 恢复原状态，可直接重试。
- **停机脱离与重启接回**（#26）：选用独立的 `ResumableExecutorPort` 而非给 `execute()` 加 `run_dir` 参数，旧执行器和测试替身无需改动，Worker 用 `isinstance` 判断能否接回。
  - **登记**：可接回执行器的 Run 开始时 `OpenRunPort.open()`；正常结束 `finish()`（事件 `done` 与删登记同一事务，随后删目录）；失败、`interrupt` 中断或无法接回时 `discard()` 并按原规则处理事件。启动时 `sweep()` 删除没有登记、超过 7 天的孤儿 run 目录，只删 `runs` 根目录之内的路径。
  - **停机**：`AsyncWorkerPool.drain()` 先 `retire()` 停止认领，再对每个在跑的 Worker 调 `detach()`。正停在 `detachable()` 段里的 Run（等 Orca 终端里 Claude Code 的 peer 结果、等 `terminal = "orca"` 的 CLI 评审命令）立即取消：不关终端、不删 run 目录、不写 Outbox，事件留在 `processing`，登记保留，租约照常释放，旧进程马上退出。阻塞的子进程步骤不打断，等到下一个检查点：交付的检查命令最长 `check_timeout_seconds`（默认 1800 秒），单条 git / gh 命令最长 300 秒，CI 等待按 1 秒切片检查 `should_detach()` 后抛 `DeliveryDetached`。MCP 交接模式与子进程 CLI 评审不可脱离，停机照旧等它结束。再发一次停机信号仍按中断处理，登记随之删除、事件回 `pending`。
  - **接回**：启动时 `startup_inboxes()` 把有登记的 `inbox_id` 一并唤醒。拿到租约后，Worker 先对该 Inbox 的每个登记调 `resume()`（不重排其事件、`code_version` 变化不阻止接回），其余孤儿 `processing` 事件照旧重排，新事件随后按 `NewEventPolicy` 处理。登记的执行器已不存在时，事件回 `pending`、删登记，并写一条 Outbox 说明。
  - **执行器状态**：`run_state.py` 原子写 `run_dir/state.json`（临时文件 + `fsync` + `os.replace`，带 `format`）。`TurnSlot` 在发任务前记下当前一轮（peer：`task_id`、`attempt_id`、终端句柄与代次、收件地址、开始时刻、截止时刻；CLI：终端句柄、命令目录、截止时刻），轮次文件放在 `run_dir/turns/`。SDE 在每次阶段切换（`develop` / `review` / `deliver`）写 `state.json`；`resume()` 按阶段续跑：终端还活着就继续等同一 `attempt_id` 的结果（不重发，超时仍按原截止时刻）；结果已在接收端收件箱里就直接用；终端已不在且没有结果则重跑这一轮并在结果里注明；`state.json` 缺失、损坏或格式未知时从开发阶段重新开始，Outbox 消息带 `Restart:` 说明原因。
  - **交付**：`DeliveryRecord` 记 `ci_head` 与 `ci_since`（墙钟），同一 head 的 CI 等待接回后沿用原起点计超时；推送、开 PR 等步骤本就按记录幂等，不会重推或重开。
- **`NewEventPolicy` 三策略**：`defer`（默认，推迟到下一轮）、`fold`（回合间隙通过 `poll_folded_events()` 增量注入同会话/同关联键事件并统一 `mark_done()`）、`interrupt`（安全取消当前 Run/CLI 子进程，绝不向 Outbox 写半成品，原批次保持 `pending` 与新事件同租约合并重启）。

## 6. 三道防腐化门禁与术语基准

提交前与 `.github/workflows/ci.yml` 强制执行（CI 中四道并行）：`lint-imports`、`ruff check`（`pyproject.toml` 的 `[tool.ruff.lint]`，只查 bug 类规则、不查格式）、`pytest -n auto --dist worksteal -v`（全量覆盖 `tests/unit/` 与 `tests/integration/`）、`pyright`（strict，覆盖 `src/` 下全部包，`pythonPlatform` 固定为 Linux）。类型检查只用 pyright，不再保留 mypy。PR 上由 `scripts/select_tests.py` 按 Python AST 反向依赖图与资源映射仅跑受影响测试（加 `full-ci` 标签或合入 `main` 时跑全量兜底）。

全局与系统 Steward 的路由测试在终端接口处直接启动模拟 CLI，覆盖实际工作目录、提示、MCP 子进程和权限判定。需要观察 Orca 终端创建、账号不符或中断后子进程退出的用例使用真实 shell 包装进程。

术语定义以 [`docs/glossary.md`](glossary.md) 为唯一基准，本文不再重复定义。以下是术语在当前实现中的落地约束：

- **Inbox / `inbox_id`**：经项目的 `inbox_id` 规则（字符串为精确 ID；数组每项为整串匹配的正则）解析到至多一个项目；多个 inbox 可属同一项目，但各自持有 worktree。
- **Event**：认领计数 `attempts` 与 `last_error` 只存于 L3 `event_inbox` 内部列，跨重启保留，供毒丸止血与排障；执行前立即 `bind_session()`；抢锁先恢复孤儿 `processing`。
- **`session_id`**：委派出的子会话另记 `parent_session_id`；轮换标 `archived`（新会话继承 `parent_session_id`），结案标 `closed` 且引用归零触发回收。
- **`correlation_key`**：同时作为 `workspaces` 表动态 worktree 复用键。

## 7. Switchboard（Phase 1 + Phase 2 Relay + Stage A/B 接入）：外部事件归一化交换机

`src/switchboard/` 是与 `agent_runtime` 并列的独立包（过渡期单仓多包）。`.importlinter` 的 `switchboard-zero-business-deps` 契约禁止它导入 `taskboard`、`agent_runtime`、`runner`、`memory_hub`，`tests/unit/test_switchboard_core.py` 另用 AST 检查它只依赖标准库与自身。

- **纯被动入站（Pure Push-in）**：只接收推送（GitHub Webhook、飞书事件与卡片回调、MCP 工具调用），不内置 Poller 或 Cron；定时任务由外部 Cron 调 MCP `submit_work(source="timer")`。命名统一为 Inbound / Outbound。
- **统一信封 `CanonicalEvent`**（`envelope.py`）：`@dataclass(frozen=True, slots=True)`，`event_id = "evt_" + ULID`，`metadata` 构造期冻结为 `MappingProxyType`（浅层只读，必须可 JSON 序列化）。`validate_envelope()` 按 `event_type` 校验必填顶层字段与 metadata 键；`execution.reported` 的 `outcome_kind` 只允许 `emit/suspend/error/done`（Silent 不上报）。
- **去重键是业务指纹**：`inbound_events` 的 `UNIQUE(source, external_id)`。GitHub 用 `issue:{repo}#{num}:{action}:{updated_at}` / `pr:...` / `comment:{id}`（PR review 为 `review:{id}`，review comment 为 `review_comment:{id}`），不用 `X-GitHub-Delivery`，所以 Redeliver 换新 UUID 仍判重；飞书卡片审批用 `approval:{approval_request_id}`（不含 decision），二次点击（即使改点拒绝）被丢弃并返回首个决定的只读卡片。
- **GitHub 入站过滤**（`inbound/github.py`）：`[github] require_label` 设定后，只有带该标签（忽略大小写）的 Issue/PR 事件及其上的评论、review 入站，其余返回 `ignored`，公开仓库的陌生人开 Issue 不会触发 Run；标签被移除后的事件同样忽略。防回环：Bot 作者的评论丢弃；`GitHubOutboundAdapter` 在每条出站评论末尾附 `GITHUB_OUTBOUND_MARKER`（`<!-- switchboard:outbound -->`，`addressing.py`），入站评论含该标记即丢弃，因为用用户令牌发出的评论回流时作者类型是 User。
- **GitHub App 令牌**（`github_app.py`、`rs256.py`）：设置 `SWITCHBOARD_GITHUB_APP_ID` 与 `SWITCHBOARD_GITHUB_APP_PRIVATE_KEY`（PEM 或 base64 PEM，`credentials.github_app_credentials`）后，`GitHubOutboundAdapter` 经 `GitHubAppTokenSource.token_for(repo)` 取令牌：标准库实现的 RS256 签 App JWT，查 `/repos/{repo}/installation`，再签只含 `issues`/`pull_requests` 写权限、只覆盖该仓库的安装令牌，按仓库缓存到过期前 10 分钟；仓库所有者不在 `[outbound] github_app_owners` 时不调 GitHub 直接失败（不重试），安装不存在同样不重试，429/5xx 可重试。未设置时仍用 `SWITCHBOARD_GITHUB_TOKEN`。设置了 App 却没列 `github_app_owners` 则启动失败。
- **飞书应用令牌**（`feishu_auth.py`）：设置 `SWITCHBOARD_FEISHU_APP_ID` 与 `SWITCHBOARD_FEISHU_APP_SECRET`（`credentials.feishu_app_credentials`）后，`FeishuOutboundAdapter` 经 `FeishuTenantTokenSource` 调 `/open-apis/auth/v3/tenant_access_token/internal` 取 `tenant_access_token`，缓存到过期前 10 分钟；飞书回 99991661/99991663/99991668（令牌无效）时丢弃缓存并按可重试失败处理，下次重试重新换取；App ID/Secret 错误不重试，429/5xx 与 HTTP 400 的限频码（`99991400`）可重试。未设置时仍用固定的 `SWITCHBOARD_FEISHU_TOKEN`（约 2 小时过期，仅适合临时验证）。
- **按账号路由**：`[routing.github_owners]` 把某账号下 `github_repos` 未列出的仓库映射到模板 scope（`{repo}` 换成小写仓库名，如 `proj:{repo}`），之后才轮到 `unmatched_policy`。
- **入站管道**（`pipeline.InboundPipeline`）：校验信封 → 同一事务内 `INSERT OR IGNORE` 入 `inbound_events` 并按路由表写 `delivery_log` → 唤醒投递线程。401（验签失败）、400（缺字段/信封不合法）、413（超过 `max_body_bytes`）只写旁路审计与 stderr，不落表。`AuditSinkPort` 异常降级为 stderr，不中断主链路。
- **声明式路由**（`router.py`）：`work.opened/updated → taskboard`；`work.closed → taskboard + hibernaut`；`work.ready / conversation.message / approval.decided → hibernaut`；`execution.reported → taskboard + switchboard.outbound`。`[routing.event_consumers]` 按事件类型整体替换默认消费方，未列出的类型不变（`Router.from_config`）；容器模板在没有 Taskboard 时把 `work.*` 直接投给 `hibernaut`、`execution.reported` 只投 `switchboard.outbound`。scope 由 `[routing]` 的 `github_repos` / `feishu_chats` 映射，未命中按 `unmatched_policy` 回落 `default_scope` 或忽略。
- **投递**（`DeliveryWorker` + `ConsumerTransport`：Phase 1 的 `InProcessTransport`、Phase 2 的 `WebSocketRelayTransport`，或二者组合的 `CompositeTransport`）：同 `(consumer_id, scope)` 严格队头保序，队头处于 `retry`/`dead_letter` 时只阻塞该队列。`nack`/`timeout`/异常按 `retry_backoff_seconds`（默认 5/15/45/135/405 秒）退避，重试次数等于退避表长度，最后一次重试仍失败（默认共 6 次尝试）转 `dead_letter`，并经出站网关向 `dead_letter_alert_channel/target` 发告警；`offline` 保持 `pending` 且不计次数。`replay_delivery(event_id, consumer_id)` 只接受 `dead_letter`/`retry`，重置为 `pending, attempts=0, next_retry_at=now`。
- **出站网关**（`outbound/gateway.py`）：`outbound_messages` 的 `UNIQUE(idempotency_key)` 防重发；每个 `(channel, target)` 一个令牌桶（`rate_limit_per_target_rpm`），限流只推迟不计次数；可重试失败（5xx/429/网络，以及飞书以 HTTP 400 返回的限频码 `230020`、`99991400`）退避，超过 `max_retry_attempts` 或其他 4xx 标 `failed`。飞书发消息或换令牌被限频时，`feishu_rate_limit.py` 读响应头 `x-ogw-ratelimit-reset`（秒），经 `SendResult.retry_after_seconds` 交给网关：从收到响应起算，重发时间取它与当前退避档中较晚的一个；没有该头或值不是有效正数时只用退避表。重发沿用同一 `uuid`（即 `msg_id`），`last_error` 保留飞书的 code 和 msg。`execution.reported` 自动转换：`suspend` → `approval_channel`（默认飞书 `approval_target`）审批卡，按钮 value 打包 `approval_request_id/decision/correlation_key/scope/session_id`；其余发往报告里显式的 `reply_channel` + `reply_target`（任务事件带上、Worker 原样透传到 Outbox 元数据；GitHub 评论支持 `add_labels`/`remove_labels`）；没有显式目标时，只有来源渠道在 `[outbound] reply_to_origin`（默认 `["feishu"]`，即飞书单聊或话题回复）里才回复到 `correlation_key` 的来源，GitHub Issue 发起的任务默认不回帖，结果只留在 Hibernaut 本机 Outbox。审批卡的来源回落同样受此限制。Taskboard 状态同步不对外发消息（`is_internal_task_sync`）：`outcome_kind = "done"` 的报告一律不发；`task_action` 为 `claim / update_stage / release` 且 `outcome_kind` 不是 `emit` / `suspend` 的报告（如执行异常的 `release`）也不发；`emit` 带 `task_action` 的报告（如失败 Emit 附带 `release`、开 PR 的 Emit 附带 `update_stage`）照原规则投递，`suspend` 照常发审批卡。`source = "taskboard"` 且带 `notify_kind`（`human_todo`、`upstream_cancelled`、`dependency_invalidated`）的通知按 ① 显式 `reply_channel` + `reply_target`、② `correlation_key` 的来源（受 `reply_to_origin` 限制）、③ `[outbound] notify_channel`（缺省取 `approval_channel`）+ `notify_target`、④ `approval_channel` + `approval_target` 的顺序找目标，所以来源是 GitHub Issue 或没有来源的人工待办也能发到飞书；四者都没有时不发。其他报告不使用 ③ ④。渠道插件经 `CredentialBrokerPort.issue_ephemeral()` 取短期令牌，HTTP client 可注入。
- **出站消息格式**由 Switchboard 的渠道适配器决定。飞书文字和 GitHub 评论只显示正文，即使报告提供了标题。GitHub 评论末尾附带用于过滤 Webhook 回流的隐藏标记。飞书审批卡在卡头显示报告的 `subject`。Hibernaut 发起审批时，缺省标题为「待审批」。
- **SQLite**（`store_sqlite.py`）：WAL、`busy_timeout=5000`、`foreign_keys=ON`；一条连接在一把进程内锁下串行，写入用 `BEGIN IMMEDIATE`。三张表 `inbound_events`、`delivery_log`、`outbound_messages` 及索引 `idx_inbound_corr`、`idx_delivery_sched`、`idx_delivery_order`、`idx_outbound_sched`。
- **MCP 工具**（`inbound/mcp.py`，`Authorization: Bearer` 对 `get_webhook_secret("mcp")` 常量时间比较）：`submit_work`、`post_message`、`decide_approval`、`report_execution`、`replay_delivery`。`report_execution` 供远程 Hibernaut 节点上报运行结果、Taskboard 上报通知：`event_type="execution.reported"`，可选参数 `source` 取 `hibernaut`（缺省，向后兼容）或 `taskboard`，其余值返回工具错误；Taskboard 的通知保留 `source="taskboard"`，回流时 Taskboard 据此识别为自己发出的事件；`actor` 缺省为 `source`，`occurred_at` 归一为 UTC（缺省或无法解析时取服务端时钟），`event_id` 由服务端生成；`scope` 不回落 `default_scope`（报告属于节点自己的 inbox），缺 `scope`、`correlation_key`、`subject` 或 `metadata.run_id/session_id/outcome_kind` 时按信封校验返回 `invalid`（`isError=true`、不入表）。随后走标准 `InboundPipeline`：按 `(source, external_id)` 幂等去重，重复上报返回 `duplicate` 与首个 `event_id`，新事件扇出到 `taskboard` 与 `switchboard.outbound`。
- **HTTP**（`http_server.py`）：单端口 `ThreadingHTTPServer` 挂 `/webhooks/github`、`/webhooks/feishu`、`/mcp`、`/healthz`；按 `Content-Length` 先拒超限请求，入库后立即返回，不等下游。`[http] base_path`（默认空；规范化与 Taskboard 相同：去掉首尾空白与尾部 `/`，缺前导 `/` 时补上，含空白、`?`、`#` 或 `//` 报错）非空时（如 `/switchboard`），上述路径与 Relay 升级路径（`<base_path><relay.path>`，含单独的 `listen_port` 监听）同时在带前缀和不带前缀两处可用：保留前缀的反代（Traefik `PathPrefix(/switchboard)`）无需 StripPrefix，旧域名与容器内探活仍走裸路径。组装根是 `switchboard/app.py`（`python -m switchboard.app --config switchboard.toml`）。
- **配置校验**（`config.py`、`check.py`，`--check`）：启动与 `--check` 共用 `parse_config()`，错误都是带字段名的 `ConfigError`：端口 0–65535、`max_body_bytes ≥ 1`、`http.host` / `sqlite.path` / `default_scope` 非空（空 `sqlite.path` 会打开关闭即消失的临时库）、路由映射的值是非空 scope、`event_consumers` 每个列表里消费者不重复（投递表以事件和消费者为主键）、退避表每项是有限非负数、限流与重试次数 ≥ 1、出站 API 地址离线解析为带合法主机名的 http(s) URL（端口 1–65535，不含空白、query、fragment）、`sqlite.path` 不是目录或特殊文件且已存在的上级都是目录（只读文件状态，尚未创建的路径通过）；布尔不当数字，`"false"` 不当真值，`"8790"`、`0/1` 这类原本读得对的写法仍接受。`shutdown_timeout_seconds` 必须是顶层正数，写进任何表里都报错（TOML 会把表头之后的键归入该表，否则静默失效）。App 私钥与 `github_app_owners` 也在启动前校验，配置错误时启动同样只打一行原因并以 1 退出。`config_problems()` 只在 `--check` 下运行，拒绝启动时会静默忽略的半截配置（死信告警、`notify_channel`、`relay.listen_host`、App 凭据只填一半）、启用了 Relay 却没有 `SWITCHBOARD_RELAY_WEBHOOK_SECRET`、语法上不是 IPv4 地址或主机名的监听地址（`http.host` 与 `relay.listen_host` 同一规则 `is_ipv4_or_host_name()`，不查 DNS；服务只监听 IPv4，所以 IPv6 字面量也拒绝），以及与 `[http]` 同端口且地址重叠的 Relay 监听（`0.0.0.0` 与任何地址重叠，`localhost` 视作 `127.0.0.1`，其它主机名不解析、只比较文本）。`--check` 不构造 `SwitchboardStore` 与监听，通过时在 stdout 输出监听地址、路由规则数与已启用渠道（按环境变量里有没有凭据，只显示名字）。`tests/unit/test_switchboard_check.py`、`tests/integration/test_switchboard_check.py` 用 `sys.addaudithook` 断言没有 bind、connect、域名解析、`sqlite3.connect`、`mkdir` 与写打开。
- **优雅停机**（`Switchboard.stop(timeout=None) -> bool`，默认上限 `shutdown_timeout_seconds`）：① 关闭 HTTP（含 Relay 单独端口）监听，`DeliveryWorker` / `OutboundGateway` 不再领取（同一批已取出未开始的也不做，行保持 `pending`），`RelayHub.drain()` 起拒绝新连接与尚未发出的推送。② 等已接收的请求、在途投递（含等待 Relay ACK）与在途发送写完结果；已接受但还没发来请求头的连接另给 0.5 秒，之后切断，迟到的请求头回 503。到上限仍在处理的 HTTP 连接也切断：没收齐的请求体不处理；切断前先调 `SwitchboardStore.refuse_intake()`，它与语句在同一把锁下检查，之后新事件入库和 `replay_delivery` 都抛 `StoreClosedError`（MCP 在适配器 `handle()` 内入库，不能只靠 HTTP 层拦）。③ 给所有 Relay 连接发 Close 1001，用同一上限的剩余时间等对端回 Close，之后切断（没有剩余时间时只留 0.1 秒发出 Close）；被切断的推送记为 `offline`（`pending`、不计次数）。④ ②③ 任何一部分超时都经 `logging` 记一条 `WARNING` 列出没结束的部分（HTTP 请求、投递、出站、Relay 连接、SQLite 写），返回 `False`。⑤ 拿到 Store 锁（即没有进行中的语句或事务）后关闭 SQLite，最后一个连接关闭时 WAL 随之合并；拿不到锁则不关，交给进程退出；两种情况下 `close()` 一开始就拒绝尚未拿到锁的语句，停机返回后不再访问连接。强制收尾在上限之外最多再约 2 秒。并发投递用普通守护线程而不是 `ThreadPoolExecutor`：后者的线程会被解释器在退出时 join，一个卡住的投递就能拖住进程。信号经 `signal.set_wakeup_fd` 写进管道，主线程读这个管道：Linux 会把进程信号交给正在建线程的线程，而 Python 处理函数只在主线程运行，等锁或队列的主线程不会因此醒来，信号就丢了。排空在单独线程里跑，结束时写同一管道：排空结束退出码 0，期间再来信号则 `os._exit(128 + signum)`（容器里 PID 1 会忽略默认动作的信号，不能靠恢复 `SIG_DFL`）。Hibernaut 同进程模式走同一个 `stop()`。测试见 `tests/unit/test_switchboard_shutdown.py`、`tests/integration/test_switchboard_shutdown.py`。

### 7.1 Phase 2：RelayHub 与 Relay Agent 长连接推送

私网或本机（如合盖休眠的 Mac）上的消费方无法被公网回调，改由消费方主动外连 `wss://<host>/ws/relay`，Switchboard 经这条长连接推送事件。仍只用标准库：RFC 6455 握手与帧编解码在 `relay_protocol.py` 里手写，TLS 用标准库 `ssl`（Agent 侧）或由前置反代终结（Hub 侧）。

- **帧协议**（`relay_protocol.py`）：WebSocket 只走文本帧，每帧是一个带 `type` 与 ISO-8601 UTC `ts` 的 JSON 对象：`hello`（Agent → Hub：`consumer_id`、`token`、`agent_version`）、`welcome`（Hub → Agent：`consumer_id`、`conn_epoch`、`heartbeat_sec`、`ack_timeout_sec`）、`push`（`conn_epoch` + 完整 `CanonicalEvent`）、`ack` / `nack`（`conn_epoch`、`event_id`，`nack` 另带 `error`、`retryable`）、`ping` / `pong`（`conn_epoch`）。自定义 Close Code：4001 鉴权失败或首帧超时，4009 被同 `consumer_id` 的新连接取代。客户端帧必须掩码，控制帧不超过 125 字节，单消息上限沿用 `[http] max_body_bytes`。
- **鉴权**（`relay_hub.RelayHub`）：建连后 `auth_timeout_sec`（默认 5 秒）内必须收到 `hello`；Token 与 `CredentialBrokerPort.get_webhook_secret("relay")` 常量时间比较，未配置密钥一律拒绝。超时、首帧不是 `hello` 或 Token 不符都以 Close 4001 关闭，并经 `AuditSinkPort` 记 `relay/auth_timeout` 或 `relay/auth_failed`（不含 Token）。Agent 侧 Token 经 `CredentialBrokerPort.issue_ephemeral("relay")` 申领。
- **`conn_epoch` 防脑裂**：同一 `consumer_id` 每次握手成功在一把锁内递增 `conn_epoch` 并替换在线路由表，`welcome` 发出前该连接不接收任何推送或心跳。旧连接的未确认推送按 `offline` 交还 Worker（回 `pending`、不计次数），随后以 Close 4009 关闭；旧连接在 2 秒宽限期内发来的帧、以及新连接上携带旧 `conn_epoch` 的 `ack` / `nack` 一律丢弃并记 `relay/stale_frame`。
- **`WebSocketRelayTransport`**（实现 `ConsumerTransport`）：消费方不在线返回 `offline`；同一 `(scope, consumer_id)` 最多 1 条在途（队头保序），单连接在途上限 `max_in_flight`（默认 8），不同 scope 可并行；窗口占满等到 `ack_timeout_sec` 仍无空位时按 `offline` 返回（推送未发出，不算一次尝试）。推送后 `ack_timeout_sec`（默认 15 秒）内无 `ack` 判 `timeout`，记 `relay/ack_timeout` 并立即补发一次 `ping` 做健康检查。同一 `event_id` 的迟到 `ack` 可以结算下一次重试，因为事件确已被处理（At-Least-Once）。
- **心跳与离线摘除**：Hub 每 `heartbeat_sec`（默认 20 秒）向每条连接发 `ping`；任意入站帧都算存活，连续 2 次心跳间隔无入站（默认 40 秒）即摘除在线表（`relay/heartbeat_timeout`），未确认推送按 `offline` 回退 `pending` 等待重连。
- **离线不等于故障**：`offline` 保持 `pending`，不增加 `attempts`、不消耗死信重试额度；只有在线时的 `nack` / `timeout` 才进入 `retry_backoff_seconds` 退避与死信流程（含出站告警）。
- **重连零延迟补推**：`welcome` 发出后 Hub 回调 `on_consumer_connected(consumer_id)`，组装根把它接到 `DeliveryWorker.reset_offline_pending()`：`SwitchboardStore.reset_offline_pending(consumer_id, now)` 把该消费方因离线延后的 `pending` 行的 `next_retry_at` 置为现在（`retry` 行保持在线失败的退避），然后唤醒 Worker 按 `(scope, created_at)` 队头保序补推。若推送失败与重连同时发生，Worker 在写入离线延后之后会再执行一次重置。
- **Worker 并发**：每轮取出的待投递项各自是不同 `(consumer_id, scope)` 的队头，`[delivery] max_parallel` 个线程并发投递不破坏保序；未配置时 `in_process` 为 1（与 Phase 1 相同），`relay` / `hybrid` 为 `2 × max_in_flight`。
- **传输模式**（`[relay] transport`）：`in_process`（默认，Phase 1 行为）；`relay`：除内置 `switchboard.outbound` 外的消费方全部走长连接；`hybrid`：有进程内处理函数（内置或 `bus.subscribe`）的消费方走 `InProcessTransport`，其余（如 `hibernaut`、`taskboard`）走 `WebSocketRelayTransport`（`pipeline.CompositeTransport`）。`transport` 不是 `in_process` 时必须 `enabled = true`。
- **挂载**：默认与 `[http]` 同端口，`GET <path>` 带 `Upgrade: websocket` 时升级（不带返回 426）；配置 `listen_port`（可选 `listen_host`）则另起一个只服务该路径的监听。
- **Relay Agent**（`relay_agent.RelayAgent`，CLI `python -m switchboard.relay_agent`）：外连 `ws://` / `wss://` 后立即发 `hello`；收到 `push` 在线程池（默认 8）里调用注入的 `ConsumerHandler`，处理函数返回（即本地落盘完成）后才回 `ack`，返回 `nack` / `timeout` / `offline` 或抛异常则回 `nack(retryable=true)`；自动回应 `ping`；`3 × heartbeat_sec` 无任何入站帧视为半开连接主动断开。断线后按 1 → 2 → 4 → 8 → 16 → 30 秒（封顶）±20% 随机抖动退避重连，成功握手后退避归零；收到 4009 说明另一个同 `consumer_id` 的 Agent 接管，不再重连。

### 7.2 Stage A：Hibernaut 同进程桥接（`adapters/channels/switchboard_bridge.py`）

`hibernaut.toml` 的 `[switchboard]` 段默认 `enabled = false`，此时不启动 Switchboard，GitHub 和飞书事件须启用 Switchboard 才能自动入站，MCP / Drive 可继续使用 daemon 本地通道。开启后 `app/main.py` 启动时用 `load_config(config_path)` + `build_switchboard(..., credentials=EnvCredentialBroker(...))` 建同进程 Switchboard 并 `start()`，进程退出（SIGINT/SIGTERM）时 `stop()`。只有 L3 `adapters` 与 `app` 依赖 `switchboard`；L0/L1/L2 不导入它。

- **入站桥 `SwitchboardInboundBridge.handle_canonical_event`**（符合 `ConsumerHandler`，以 `consumer_id`（默认 `hibernaut`）`bus.subscribe`）：`CanonicalEvent` → `EventHandler.ingest(inbox_id=scope, source="sb:<source>", external_id=event_id, correlation_key=...)`。`external_id` 用 Switchboard 全局 `event_id`，At-Least-Once 重推命中 `(inbox_id, source, external_id)` 去重记为 `dropped`，仍回 `acked`；落库异常回 `nack`，由 `DeliveryWorker` 退避重试。payload 含 `event_type/subject/title/body/actor/external_id/occurred_at` 与原样 `metadata`，并把引擎读取的 `approval_request_id`、`decision`、`work_key`、`reply_channel`、`reply_target` 提到顶层（`approval.decided` 由此按 `approval_request_id` 恢复挂起会话）。Taskboard `work.ready` 的 `task_id`、`trace_id`、`hop_count`、`dispatch_seq`、`assignee`、`task_type`、`priority` 非空时同样提到顶层（`metadata` 里保留原样）；`metadata.preferred_executor` 非空且 payload 没有 `executor_id` 时映射为 `executor_id`，按 §3 的粘滞路由选执行器。
- **`work.closed` 联动**：入站桥给事件加 `action = "close_session"`，由 Worker 在 Inbox 租约内走既有的关闭流程：关闭该 `(inbox_id, correlation_key)` 会话，`count_active_by_work_key(work_key, inbox_id) == 0` 时触发 worktree 回收；找不到会话则只标记完成。不在投递线程里直接改会话，避免与正在运行的 Run 竞争（Run 结束时会把会话写回 active）。
- **出站桥 `SwitchboardChannelAdapter`**（实现 L1 `ChannelPort`）：Outbox 消息 → `execution.reported`（`source="hibernaut"`、`scope=inbox_id`、`actor="hibernaut"`、`subject` 取 metadata 的 `title`/`subject`，缺省 `Hibernaut update`，`body=content`），metadata 带 `run_id/session_id/outcome_kind`，并透传 `approval_request_id`、`reply_channel`、`reply_target`、`task_id`、`executor_id`、`error_kind`、`notify_channels`、`approval_channel`、`approval_target`、`task_action`、`stage`、`trace_id`、`hop_count`。`outcome_kind` 取 metadata 显式值，否则按 `kind`：`emit → emit`、`approval_request → suspend`、`task_sync → done`、`silent →` 不发布、其余 → `error`。带 `task_id` 的报告缺 `trace_id` / `hop_count` 时补 `trace_id = run_id`、`hop_count = 1`，满足 `schemas/taskboard/execution_reported.metadata.schema.json`。`external_id = outbox:<message_id>`，没有 `message_id` 时用 `(inbox_id, content, metadata)` 的确定性哈希，Outbox 重试不会重复发卡。发布回调 `publish: Callable[[CanonicalEvent], Any]` 由构造函数注入（Stage A 为 `switchboard.bus.publish`，Stage B 为 `SwitchboardMCPPublisher.publish`，翻译逻辑不变）；返回 `invalid` 时抛异常，由 `OutboxDispatcher` 记失败并重试。有 `session_id` 的 `suspend` 即使缺少 `correlation_key` 也上报。无来源的审批优先发往报告明确指定的目标，否则使用 `[outbound]` 的 `approval_channel` 和 `approval_target`。两处均未指定目标时，审批留在 Outbox，可经本地审批入口处理。其他缺少会话或关联键的消息走控制台 fallback。启用 `FileOutboxChannel` 时，文件仍在投递前写入。
- **无关联键的审批回执**：Switchboard 收到 `card.action.trigger` 后，通过已发送的卡片查找对应的 `execution.reported`。`approval.decided` 带回原任务的 `scope`、`session_id` 和 `approval_request_id`，Hibernaut 在持有 Inbox 租约时核对挂起请求，再按 `approve` 或 `reject` 恢复检查点。飞书按钮直接进入 webhook。一张卡只认第一次点击（`external_id = approval:<approval_request_id>`，再点回「已处理」）；报告的 `metadata.deciders` 是非空 open_id 列表时，列表外的人点击回错误提示、不改卡片、不入库，`approval_request_id` 留给列表里的人。没有 `deciders` 的卡照旧谁先点算谁。`approval.decided` 的 `metadata.chat_id` 是被点卡片所在的聊天。远端 Switchboard（如 hub）要更新到带这条检查的版本才生效，旧版忽略这个字段。MCP 的 `decide_approval` 工具仍要求关联键。
- **Outbox 元数据**：`AgentWorker` 写 Emit / Suspend 时补齐 `run_id`（每批一次）、`correlation_key`、`session_id`、`outcome_kind`，Suspend 另带 `approval_request_id`，并透传批内事件 payload 的 `reply_channel` / `reply_target`；原有 `kind`、`request_id` 不变。另写嵌套键 `task_context`（L0 `TASK_CONTEXT_KEY`）：`title`（批内 payload 的 `title`，否则 `drive_file_name`、`issue.title` / `pull_request.title`）、`source`（批内首个非审批事件的 `source`）、`executor_id`、`trace_id`、`status`（`Emit.status` 或 `awaiting_approval`），Emit 带 `delivery`（L0 `DeliveryOutcome`）时另有 `delivery`：`state`（`local` / `pr_open` / `merged`）、`pr_url`、`auto_merge`、`hold`（授权合并却未合并的原因类别：`review` / `ci` / `other`，否则为空）、`hold_detail`。SDE 交付后由 `PRDelivery.outcome()` 从交付记录生成：评审门与 CI 门在 `DeliveryRecord.merge_hold` / `merge_hold_detail` 记下原因，其余（合并被权限挡住、审批被拒时的 `problem`）归为 `other` 并附原文。嵌套而不放顶层，Switchboard 透传的顶层 `title` / `executor_id` 与 `subject` 不受影响。`DriveResultWriter` 对带 `run_id` 的 Emit 不再经通道写 Drive（已由 `handle_run_report` 写入），避免重复。
- **Run 的 `trace_id`**：L0 `resolve_trace_id(event)` 依次取 payload 的 `trace_id`、`_trace_id`，没有则用 `event_id`，不修改事件。一批事件由 `resolve_trigger_event()` 取主事件：最后一条带 trace 的，都没有则首条。主事件不带 trace 时沿用会话 `TaskLink.trace_id`，再没有才用主事件的 `event_id`。会话的工作还在原来那条链里时不看新事件：批内有带 `return_to` 的转投就以它为主事件；会话还欠着回投、批内有审批事件、或只有不带 trace 的定时器时，沿用 `ForwardSpec` 里的 trace，主事件是批内带同一 trace 的最后一条，没有则是 `ForwardSpec.parent_event_id`。结果写入 `RunReport.trace_id`、Outbox 元数据 `_trace_id`（L0 `TRACE_METADATA_KEY`）、`task_context.trace_id` 与账本的 `RunRecord.trace_id`；顶层 `trace_id` 仍只表示 Taskboard 任务的 trace（§10.2），Switchboard 回报不变。升级前挂起、没存 trace 的会话，审批恢复的 Run 以审批事件为自己的 trace。
- **Taskboard 任务回写**（`engine/worker.py`，详见 §10.2）：批次或会话关联了 Taskboard 任务（L0 `TaskLink`）时，`AgentWorker` 在 Outbox 元数据里附带 `task_action` / `stage` / `task_id` / `trace_id` / `hop_count`，或另写 `kind = "task_sync"` 的内部同步消息（`TASK_SYNC_KIND`）；`FileOutboxChannel` 对 `task_sync` 不写 Markdown 文件，只交给内层通道。无 `task_id` 的 Run 行为不变。
- **凭据**：Stage A 的 `EnvCredentialBroker` 让 Hibernaut 进程持有 `SWITCHBOARD_*` 令牌，与「零真实密钥」契约有缺口。启动时把这些变量从 `os.environ` 移到 broker 私有副本，执行器子进程继承不到；Stage B 的 `relay` 模式把 Switchboard 移出 Hibernaut 进程，GitHub / 飞书等渠道密钥只留在远程 Hub。
- **重载**：`[switchboard]` 段变化需重启；其它配置热重载时重新 `subscribe`，入站桥指向新的 daemon。

### 7.3 Stage B：跨网 Relay 模式（`adapters/channels/switchboard_relay.py`）

`[switchboard] mode = "relay"` 时 Hibernaut 不在进程内拉起 Switchboard，改连远程公网 Hub。配置 `relay_url`（`ws://` / `wss://.../ws/relay`）与 `mcp_url`（`http://` / `https://.../mcp`），`enabled = true` 时两者必填，scheme 不符或缺主机名在加载时报错；可选 `ca_file`（私有 CA，相对 `hibernaut.toml`）。`config_path` 只在 `in_process` 模式使用。`mode = "in_process"` 与 `enabled = false` 的行为与 Stage A 相同。MCP / Drive 也可通过各自的本地通道接入。

- **`SwitchboardRelayLink`**（L3，组合 `switchboard.relay_agent.RelayAgent` 与 `switchboard.mcp_publisher.SwitchboardMCPPublisher`）：对外与进程内 `InProcessEventBus` 同形（`SwitchboardBus` Protocol：`publish` / `subscribe`），组装根经 `switchboard_bus()` 统一取用，`SwitchboardInboundBridge` 与 `SwitchboardChannelAdapter` 两种模式共用、不改。
- **下行**：首次 `subscribe(consumer_id, handler)` 才启动 RelayAgent 外连，保证推送到达前入站桥已接好；热重载再次 `subscribe` 只在锁内替换处理函数，不重连（连接与 `conn_epoch` 不变）。`consumer_id` 与连接时不同则拒绝。处理函数返回（`event_inbox` 落库完成）后 Agent 才回 `ack`，落库失败回 `nack` 由 Hub 退避重推；重连、退避、4009 接管、半开检测沿用 7.1。
- **上行**：`SwitchboardMCPPublisher.publish(event)` 接受 `execution.reported`（`tools/call report_execution`，透传 `source`）与 `work.ready`（`tools/call submit_work`，传 `source`、`event_type="work.ready"`、`external_id`、`scope`、`correlation_key`、`actor`、`subject`、`body`、`metadata`，供 Taskboard 使用），其余类型不发网络请求直接抛错。JSON-RPC 发到 `mcp_url`，参数是信封字段（不含本地 `event_id`），解析 `structuredContent` 为 `IngestResult`。网络错误、非 200、非 JSON、JSON-RPC `error`、工具错误一律抛 `PublishError`（不回显 Hub 响应体），由 `OutboxDispatcher` 记失败重试；`invalid` 作为结果返回，`SwitchboardChannelAdapter` 照 Stage A 抛错。`external_id = outbox:<message_id>` 不变，Outbox 在 Hub 已收下但响应丢失后重试，Hub 判 `duplicate`，不会重复发评论或卡片。
- **凭据**：节点只持两个客户端令牌，`SWITCHBOARD_RELAY_TOKEN`（`issue_ephemeral("relay")`，Hub 侧对应 `SWITCHBOARD_RELAY_WEBHOOK_SECRET`）与 `SWITCHBOARD_MCP_TOKEN`（`issue_ephemeral("mcp")`，Hub 侧对应 `SWITCHBOARD_MCP_WEBHOOK_SECRET`），启动时与其他 `SWITCHBOARD_*` 一起移出 `os.environ`，执行器子进程继承不到；任一缺失则启动失败。非回环地址用 `ws://` / `http://` 时打印明文告警。
- **Hub 容器部署**（`deploy/switchboard/`）：镜像基于 `python:3.12-slim`，只 `COPY src/switchboard`（`Dockerfile.dockerignore` 把构建上下文限定为该目录），UID 10001 非 root 运行，`HEALTHCHECK` 用标准库探测 `/healthz`。Compose 起 `switchboard` 与 `caddy` 两个容器：`switchboard` 不映射端口，`[http] host = "0.0.0.0"` 只在 compose 网络内可达，SQLite 在命名卷 `/data`；`caddy` 独占 80/443，终结 TLS 并把 HTTP 与 `/ws/relay` 的 WebSocket 升级转发到 `switchboard:8790`，因此 `[relay]` 不设 `listen_port`、与 HTTP 共用端口，`transport = "hybrid"`。密钥只在 VPS 的 `.env`（`env_file`），仓库只留模板，实例文件被 `.gitignore` 忽略。`tests/unit/test_switchboard_deploy.py`、`tests/integration/test_switchboard_deploy.py` 校验模板可被 `load_config()` 解析及上述约束。
- **进程**：`--mcp-stdio` 伴随进程不建链接，否则第二个同 `consumer_id` 的 Agent 会以 4009 顶掉 daemon 的连接。退出时 `stop()` 发 Close 1000 并停止 Agent。
- **上行退避**（`OutboxDispatcher`，L2）：发送抛异常时按 `retry_backoff_seconds`（默认 5/15/45/135/405 秒，与 Switchboard 下行对称）排期：第 n 次失败（n ≤ 退避表长度）调 `OutboxPort.schedule_retry()`，消息保持 `pending`、`attempts + 1`，`next_retry_at = utc_clock() + 第 n 档`，写入 `last_error`；退避表用完后再失败（默认共 6 次尝试）才 `mark_failed()` 置 `failed`。显式传 `max_attempts` 时以它为总尝试上限，超出退避表的重试沿用最后一档。拉取时以 `utc_clock()` 的 `to_utc_iso()` 字符串作 `now_iso`，未到期的消息不出现在批次里，不占 `limit`；`attempts` 已达上限的遗留 `pending` 行（旧版本只计次不置终态）直接置 `failed`。`attempts` 与 `next_retry_at` 存在 SQLite `outbox` 表，进程重启后从原档位续接。Hub 重启或网络抖动几秒，消息在下一档到期时自动补发；`external_id` 不变，Hub 已收下的重发判 `duplicate`。
- **存储迁移**：`outbox` 新增 `next_retry_at TEXT`（`to_utc_iso()` 定宽 UTC 字符串，按文本比较即按时间排序）与索引 `idx_outbox_sched(status, next_retry_at, seq)`；旧库启动时 `ALTER TABLE` 补列（缺 `last_error` 一并补），已有行 `next_retry_at` 为空即立即可发；补列时一次性把 `attempts >= 3` 的 `pending` 行置为 `failed`（旧版默认上限 3 次后放弃但未置终态），避免升级后重发早已放弃的消息。
- **双进程验收**（`tests/integration/test_switchboard_dual_process_e2e.py`）：临时目录、随机端口与测试占位令牌，真实拉起 `python -m switchboard.app`（`[relay] transport = "hybrid"`）与 Hibernaut `main()`（`mode = "relay"`；入口 `tests/support/dual_process_hibernaut.py` 以 `--demo` 运行，只把演示 LLM 换成回显消息正文的确定性实现）。覆盖：`/mcp post_message` → Relay 下行 → Emit → `report_execution` 上行 → `outbound_messages` 落盘；Hibernaut SIGTERM 期间积压事件 `delivery_log` 保持 `pending, attempts = 0`，重启后按序补推并全部 `acked`；Switchboard SIGTERM 后上报首次失败进入退避（`pending` 且 `next_retry_at` 非空），重启 Hub 后到期自动重发并 `sent`。

## 9. ccpeer：与本机 Claude Code 会话收发消息

`src/ccpeer/` 是与 `agent_runtime`、`switchboard` 并列的独立包，只依赖标准库；`.importlinter` 契约 `ccpeer-zero-business-deps` 禁止它导入 `agent_runtime`、`switchboard`、`taskboard`、`runner`、`memory_hub`，`tests/unit/test_ccpeer.py`、`tests/integration/test_ccpeer.py` 另用 AST 检查。它实现 Claude Code 2.1.x 的跨会话消息协议（逆向所得，验证于 `VERIFIED_CLAUDE_CODE_VERSIONS` = 2.1.316 / 2.1.330），供 Hibernaut 与 Orca 终端里的会话直接通信；daemon 在项目 `handoff = "peer"` 时经 `peer_handoff.py` 使用它（见上文「peer 交接」）。

- **会话发现**（`sessions.py`）：扫描各配置目录的 `sessions/*.json`（默认 `~/.claude`，加上 `$CLAUDE_CONFIG_DIR`；可传多个），只保留 pid 存活且 `messagingSocketPath` 存在的登记，同一 pid 出现在多个目录时合并。`resolve()` 按 pid、`sessionId`、会话名（精确匹配）或 `uds:` 地址 / socket 路径解析，匹配多个时抛 `AmbiguousTarget` 并列出候选。
- **帧格式**（`protocol.py`）：连上目标 socket 后先写 `{"type":"auth","token":<peerToken>}`（密钥在 `<pid>.<sha256(socket)>.key`），再写一行 `{"msgV":1,"msg_id","type":"user","message":{"role":"user","content":<信封>},"priority":"next","from"}`。信封是 `<cross-session-message from="uds:…" from-name="…" from-mode="…">\n正文\n</cross-session-message>`；Claude Code 用锚定首尾的贪婪正则解析，所以正文原样放入、不转义、不 strip，正文里出现闭合标签也不会截断。2.1.330 实测：82 KB 中英文混排正文送达后，接收方会话转录里只有正文内的 `</cross-session-message>` 被 Claude Code 自己记成 `<\/cross-session-message>`，其余逐字节一致。`from-mode` 只接受 `bypass` / `prompting`，默认 `prompting`（Orca 里 `dontAsk` 会话对外声明的模式，声明一致时不被扣留）。
- **发送**（`sender.send()`）：库函数直接写 socket，不起子进程。会话登记的 `peerProtocol` 不在 `SUPPORTED_PEER_PROTOCOLS`（当前 `{1}`）时先抛 `UnsupportedProtocol`，报出对方 Claude Code 版本；socket 不存在抛 `TargetNotFound`，拒绝连接或写到一半被断抛 `PeerRefused`，连接或写入超时抛 `SendTimeout`。返回 `SendResult(msg_id, pid, name, session_id, socket_path, bytes_sent)`，只代表本地写入完成，不代表对方已读或已回复。
- **接收端**（`receiver.py`，`python -m ccpeer serve --as <名字>`）：前台进程，不 fork、不绑定 owner、无空闲超时，由 launchd `KeepAlive` 监督（`deploy/ccpeer/`）。在每个配置目录写 `standalone: true` 的登记与密钥（0600），监听 `/tmp/cc-socks/<pid>.sock`（0600），每 `--heartbeat` 秒重写登记以自愈；SIGTERM / SIGINT / SIGHUP 时清理登记、密钥、socket 后退出 0。认证行 token 不符的连接整条丢弃。同名冲突：存活且 socket 可连的同名会话在先则拒绝启动（退出码 2）；残留的 standalone 登记（进程已死或 socket 不通）删除后接管；同一状态目录另有 `flock` 文件锁。
- **收件箱**（`inbox.py`）：`~/.ccpeer/<名字>/inbox.jsonl` 存消息（`msg_id`、`ts`、`type`、`from_addr`、`from_name`、`from_mode`、`body`；无信封的消息另带 `unwrapped: true`），`control.jsonl` 单列控制回执（如 `held`）。按 `msg_id` 去重（跨重启有效），每条记录一次 `write` 加 `fsync`；接收端启动时截掉被杀时写了一半的尾行。`JsonlLog.read(cursor)` 只返回完整行，游标是字节偏移或 `msg_id`，返回下一游标；偏移不在行边界或超出文件、`msg_id` 不存在时抛 `CursorError`。读取方保存游标，接收端重启后续读不丢不重。
- **测试**：`tests/unit/test_ccpeer.py`、`tests/integration/test_ccpeer.py`（信封与 Claude Code 字节级一致、长正文与特殊标签往返、多目录发现与死进程/残留 socket、解析歧义、三类发送错误、协议版本拒绝、收件箱游标与断尾修复、launchd 模板）；`tests/integration/test_ccpeer_receiver.py` 起真实接收端进程，由 `FakeSession` 按 Claude Code 帧格式回复，覆盖「发送 → 回复 → 收件箱可读」、`held` 分流、错误 token 丢弃、SIGKILL 后重启接管与游标续读、同名拒绝、登记自愈。

## 10. Taskboard（Phase 1）：多源任务归集与 DAG 依赖编排

完整设计方案（定位与职责边界、5 态状态机、字段所有权、DAG 解锁与异常传播、Flow 展开、Schema 契约、DDL、门禁与里程碑）见 [`taskboard.md`](taskboard.md)；本节只记实现要点。

`src/taskboard/` 是与 `agent_runtime`、`switchboard` 并列的独立包，运行时只依赖标准库，L3 适配器与 `app/` 另依赖 `switchboard`（`CanonicalEvent`、`EventBusPort`、`RelayAgent`、`SwitchboardMCPPublisher`）。上线阶段 1 起 Taskboard 是独立常驻进程（§10.1），作为 `taskboard` 消费方经 Relay 外连 Switchboard；Hibernaut 消费 `work.ready` 并以 `execution.reported` 回报 `task_action`（§10.2）。没部署 Taskboard 时按 §7 的 `[routing.event_consumers]` 把 `work.*` 直接投给 Hibernaut。

- **分层与门禁**：`core/`（L0：`models.py`、`errors.py`、`state_machine.py`、`merge.py`、`dag.py`）→ `ports.py`（L1：`TaskStorePort`、`EventPublisherPort`、`AuditSinkPort`）→ `engine/`（L2：`IngestionService`、`UnlockDispatcher`、`FlowExpander`）→ `adapters/`（L3：`SQLiteTaskStore`、`SwitchboardAdapter`、`json_schema`、`SwitchboardRemoteBus`、`TaskboardMCPServer`、`TaskboardHTTPServer`、审计适配器）→ `app/`（配置与组装根，`python -m taskboard.app`）。`.importlinter` 三条契约：`taskboard-no-runtime-deps`（禁止导入 `agent_runtime`、`runner`、`hibernaut`、`broker`、`memory`、`memory_hub`）、`taskboard-clean-layers`（`app → adapters → engine → ports → core` 单向，`app/` 为最上层）、`taskboard-core-pure`（L0 不得导入 `sqlite3`、`switchboard` 及外层）；`tests/unit/taskboard/test_m4_architecture_and_schemas.py` 另用 AST 检查（含下层不得导入 `app/`；`lint-imports` 可能从另一个检出解析 `taskboard`，AST 检查始终读本检出）。
- **任务模型**（`TaskItem`）：状态 `backlog / ready / in_progress / done / cancelled`；`assignee` 单字段带前缀 `agent:` 或 `human:`；`priority` 0–3（小者优先）；另有 `task_type`、`stage`、`parent_task_id`、`blocked_reason`、`manual_override_fields`、`last_source_event_at`（来源事件水位，毫秒）、`dispatch_seq`（派发次数）、`claimed_ready_at`（领到 `dispatch_seq` 时的 `ready_at`；与当前 `ready_at` 相等说明本次 `ready` 已派发过）、`version`（乐观锁）。
- **状态机**（`state_machine.py`）：`backlog→ready/cancelled`，`ready→in_progress/backlog/cancelled`，`in_progress→done/ready/cancelled`，`in_progress→in_progress` 为幂等空操作。终态只能显式 `reopen=True` 重开（`done→in_progress/ready`，`cancelled→backlog`）；终态上迟到的运行中上报（claim、update_stage）一律拒绝。引擎把重复进入同一终态（`done→done`、`cancelled→cancelled`，不带 `reopen`）当作重放：不改状态，重新执行完成或取消的扇出（`tb_transition_task`，以及 `work.closed`、`complete` 的重投）。有未完成的 `blocks` 上游时，`backlog→ready` 与 `ready→in_progress` 抛 `BlockedByDependencyError`。
- **字段所有权与乱序**（`merge.py`）：第 1 层外部镜像字段（`title`、`description`、`artifact_ref`、`reply_target`）随来源更新；第 2 层（`priority`、`assignee`、`preferred_executor`、`scope`、`task_type`）被人手改过后记入 `manual_override_fields`，之后来源更新跳过这些字段，`tb_update_task(unlock_fields=…)` 解除；第 3 层（`status`、`dispatch_seq`、`version`、`ready_at`、`claimed_ready_at`、`blocked_reason`、`last_source_event_at`）只由状态机写，手改报错。`occurred_at_ms` 早于水位的来源事件整条忽略。
- **依赖**（`dag.py`）：边类型 `blocks`（参与解锁）与 `related`（只记录）。新增 `blocks` 边前从下游沿已有出边做 DFS，能回到上游即抛 `CycleDetectedError`（带 `cycle_path`）；上下游必须已存在，不建占位任务。`compile_flow_plan()` 把 `FlowPlan` 编译为一个 `flow_group` 父任务加子任务与边：步骤省略 `after` 时串行接上一步，显式 `after` 支持并行与汇合；无上游的根任务按 `initial_status` 起步。
- **存储**（`adapters/sqlite_store.py`）：单连接加线程锁，WAL、`busy_timeout=5000`、外键开启，写操作 `BEGIN IMMEDIATE`。`tasks.source_ref` 有局部唯一索引 `uq_tasks_source_ref`（非空时唯一）；`task_source_links` 以 `source_ref` 为主键记录一个任务的多个来源，`find_by_source_ref()` 先查链接表再查主表。`upsert_task()` 按 `version` 比较并交换，失配抛 `OptimisticLockError`；`try_promote_to_ready()` 只在 `status='backlog'`、版本匹配且同一条 `UPDATE` 里确认没有未完成的 `blocks` 上游时提升（扫描与提升之间另一线程加了新上游，任务就留在 `backlog`，等新上游完成再解锁）；`try_claim_dispatch()` 加 `dispatch_seq` 时同时记下 `claimed_ready_at`；`list_unblocked_downstream()` 用 `NOT EXISTS` 只取所有上游都已 `done` 的下游，两个上游同时完成时下游最多解锁一次。`save_expanded_flow()` 在一个事务里写入整个流程。
- **派发**（`engine/dispatcher.py`）：任务进入 `ready` 且无未完成上游时 `try_claim_dispatch()` 把 `dispatch_seq` 加一，`agent:` 任务发 `work.ready`，`human:` 任务发 `notify_kind=human_todo` 的 `execution.reported`。上游完成后解锁的下游，连同已经是 `ready` 的下游，按 `(priority, ready_at)` 排序后立即全部派发，不做背压。本次 `ready` 已领过 `dispatch_seq` 的任务不再领：重放路径（`dispatch_ready_task(replay=True)`：终态重放、`work.opened` / `work.updated` 重投）按原 `dispatch_seq` 重发同一 `external_id`，由 Switchboard 按 `(source, external_id)` 去重；非重放的并发调用（如两个上游同时完成）直接跳过，留给领号者发布。上游取消时下游记 `blocked_reason=upstream_cancelled` 并通知 `upstream_cancelled`；新增未完成上游时，`ready` 的下游退回 `backlog`，`in_progress` 的下游收到 `dependency_invalidated` 通知；上游从 `done` 重开时同样处理，`done` 的下游也会收到该通知。发布异常向调用方传播。终态先提交、扇出后发布，所以发布失败会让扇出中断；入站事件因此回 `nack`，Switchboard 重投时由上面的重放补完（重投的 `work.opened` 对 `ready` 任务同样补派发）。
- **Switchboard 对接**（`adapters/switchboard_adapter.py`）：入站消费 `work.opened`（按 `source_ref` 幂等，已存在则转为更新）、`work.updated`、`work.closed`、`execution.reported`（`task_action` 为 `claim / update_stage / complete / release`）；`source="taskboard"` 的事件直接忽略，防止自环。`source_ref` 取 `metadata.source_ref`，否则 `correlation_key`（GitHub 为 `github:<owner>/<repo>#<number>`），否则 `external_id`。
- **入站契约对齐**：`work_kind` 接受 GitHub PR 事件的 `pull_request`（`issue`、`pr`、`pull_request`、`task`）。GitHub Webhook 与未带追踪字段的 `submit_work` / `report_execution` 没有 `trace_id`、`hop_count`：缺失（或为 `null`）时在事件副本上补 `trace_id = event_id`、`hop_count = 0` 再校验，显式传入的非法类型或越界值仍按 Schema 拒收。`auto_ready_sources`（构造参数，服务配置 `[intake]`，默认 `["github"]`）决定 `work.opened` 的初始状态：metadata 显式给了 `initial_status` 以它为准，否则来源命中为 `ready`（立即派发 `work.ready`），未命中为 `backlog`。旧 Issue 后贴触发标签时 Switchboard 发的是 `work.updated`：`handle_work_updated` 找不到任务（`TaskNotFoundError`）、来源命中 `auto_ready_sources`、事件带 `subject` 且 `metadata.state` 不是 `closed` 时，按 `work.opened` 语义建单（校验 `work_opened` Schema，同一初始状态策略），记审计 `work_updated_opened_task`。`handle_work_opened` 按 `source_ref` 幂等，重投或后续更新只改同一任务；并发重复建单撞上 `uq_tasks_source_ref` 时回 `nack`，重投后成为更新。其他来源仍抛 `TaskNotFoundError`（回 `nack`）。来源命中 `auto_ready_sources` 但条目已关闭（`metadata.state = "closed"`）或没有 `subject` 的 `work.updated`，以及找不到任务的 `work.closed`，之后不会再有 `work.opened`，重试也不会成功：不建单、记审计 `untracked_work_ignored` 后回 `acked`，不进死信。`work.updated` 更新到一个 `ready` 任务后，同 `handle_work_opened` 一样用本事件的 `trace_id` / `hop_count` 重放派发：首次投递已提交 `ready` 并占用 `dispatch_seq`、但 `work.ready` 发布失败回 `nack` 时，重投（此时任务已存在，走更新路径）会以同一 `external_id`（`tb:<task_id>:d<seq>`）补发，`dispatch_seq` 不变；首次已发出时由 Switchboard 按 `(source, external_id)` 去重。`metadata.hop_count >= 8` 拒收，出站 `hop_count` 超过 8 也拒发（`MaxHopsExceededError`）。`work.opened`、`execution.reported` 的 metadata 与出站 `work.ready`、通知的 metadata 按 `schemas/taskboard/` 下的 JSON Schema 校验（内置的标准库子集校验器：`type`、`required`、`additionalProperties`、`enum`、`pattern`、`minLength`、`minimum/maximum`、`minItems`、`items`）。出站发布的任何异常（含出站 Schema 校验失败）都包成 `PublishFailedError`；`handle_canonical_event()` 对它记 `outbound_publish_failed` 后返回 `nack`，对入站校验失败、跳数超限、非法迁移记审计后返回 `acked`（不重投），其他异常返回 `nack`。出站 `work.ready` 的 `external_id` 为 `tb:<task_id>:d<dispatch_seq>`；通知为 `tb:notify:<kind>:<task_id>:<key>`，`human_todo` 的 key 为 `d<dispatch_seq>`，`upstream_cancelled` 为 `u<上游 task_id>:v<上游 version>`（重放不变，上游重开后再取消则换新），其余为 `v<version>:d<dispatch_seq>`。
- **审计**（`adapters/audit_adapter.py`）：旁路通道；审计端缺失或抛异常时只往 stderr 打一行，不影响主流程。
- **工具方法**（`IngestionService`）：`tb_create_task`、`tb_update_task`、`tb_transition_task`、`tb_link_source`、`tb_manage_dependency`、`tb_instantiate_flow`、`tb_list_tasks`，经 §10.1 的 MCP 服务暴露。`tb_update_task`、`tb_transition_task` 可带 `expected_version`：当前版本不同即抛 `OptimisticLockError`（CAS 失配后的重试重读到新版本同样失败），不覆盖调用方没看到的修改；`tb_create_task` 的 `source_ref` 已属于某个任务时抛 `SourceRefConflictError`（带该 `task_id`）。
- **测试**：`tests/unit/taskboard/` 和 `tests/integration/taskboard/`：`test_m1_core_kernel.py`（状态矩阵、重开与迟到上报、依赖守卫、三层合并与水位、环检测、流程编译）、`test_m2_sqlite_store.py`（WAL 与局部唯一索引、多来源链接、依赖存在性与环、两个上游并发完成只解锁一次、删边即解锁与 CAS 冲突）、`test_m3_engine_and_switchboard.py`（`work.opened` 初始状态与幂等、执行上报与优先级排序、取消与重开通知、跳数守卫与 `tb_*` 工具、审计降级）、`test_m4_architecture_and_schemas.py`（四份 Schema、出入站 Schema 双向契约、AST 分层边界）、`test_m5_publish_replay.py`（发布失败后 `complete`、`work.closed`、`work.opened` 重投补完扇出且 `external_id` 不变、出站失败回 `nack`、扫描与提升之间新增上游时不提升、多个上游取消各发一条通知）、`test_m6_switchboard_contract.py`（用真实 `GitHubInboundAdapter` 的输出校验：PR 的 `work_kind`、追踪字段补默认与非法值拒收、`auto_ready_sources`、旧 Issue 首条 `work.updated` 建单且只派发一次、发布失败后的重投以同一 `external_id` 补发 `work.ready`、已关闭或无标题条目的更新与未跟踪条目的关闭回 `acked`）、`test_m7_service.py`（配置与 `base_path` 规范化、URL scheme 与令牌校验、`SwitchboardRemoteBus`、`/healthz` 与两种 `/mcp` 路径的鉴权与 400/404/413、7 个工具的正常与错误返回、stdio 分发与 `python -m taskboard.app --mcp-stdio` 往返、缺令牌拒绝启动）。双进程测试见 §10.1。`scripts/select_tests.py` 把 `schemas/taskboard/**` 的改动映射到 m3–m7 与双进程测试，`taskboard.example.toml` 映射到 m7，子进程入口 `taskboard/app/__main__.py` 映射到 m7 与双进程测试。

### 10.1 上线阶段 1：独立服务（Relay + MCP）与同域子路径

- **配置**（`app/config.py`，模板 `taskboard.example.toml`）：`[http]` `host`（默认 `127.0.0.1`）、`port`（`8791`）、`base_path`（默认空；去掉首尾空白与尾部 `/`，缺前导 `/` 时补上，含空白、`?`、`#` 或 `//` 报错）、`max_body_bytes`（`1048576`）；`[sqlite]` `path`（`taskboard.db`）、`busy_timeout_ms`（`5000`，传给 `SQLiteTaskStore`）；`[switchboard]` `relay_url`（`ws://` / `wss://`）与 `mcp_url`（`http://` / `https://`），scheme 不符或缺主机名在加载时报错，`consumer_id`（`taskboard`），可选 `ca_file`（相对 `taskboard.toml` 所在目录）；`[intake]` `auto_ready_sources`（`["github"]`，可为空表）。整数项拒绝布尔值与字符串。
- **密钥**只从环境变量读，不写进 toml：`SWITCHBOARD_RELAY_TOKEN`（`issue_ephemeral("relay")`）与 `SWITCHBOARD_MCP_TOKEN`（`issue_ephemeral("mcp")`）在服务模式必填，缺任一个或缺 `relay_url` / `mcp_url` 时以退出码 2 拒绝启动；`TASKBOARD_MCP_TOKEN` 是本服务 HTTP `/mcp` 的 Bearer，常量时间比较，未设置时启动只告警、`/mcp` 一律 401（fail-closed）。`service_secrets()` 只把需要的 Switchboard 令牌放进 `EnvCredentialBroker` 的私有副本。非回环地址用 `ws://` / `http://` 时打印明文告警。
- **远程总线**（`adapters/remote_bus.SwitchboardRemoteBus`，实现 `EventBusPort`）：下行用 `RelayAgent` 外连 `relay_url`，以 `consumer_id` 订阅，推送交给 `SwitchboardAdapter.handle_canonical_event`，首次 `subscribe` 才连接；上行用 `SwitchboardMCPPublisher` 发 `work.ready` 与通知类 `execution.reported`。`publish` 返回 `invalid` 时抛 `RemotePublishRejectedError`，与网络错误一样被包成 `PublishFailedError`：入站事件回 `nack`，由 Switchboard 重投并重放扇出；MCP 工具调用返回 `isError`（状态已提交，重复同一迁移即重放）。`SwitchboardAdapter` 仍只依赖 `EventBusPort`，测试照旧注入进程内总线。
- **MCP 工具**（`adapters/mcp_tools.TaskboardMCPServer`，HTTP 与 stdio 共用）：JSON-RPC 2.0，`initialize`（`serverInfo.name = "taskboard"`）、`ping`、`tools/list`、`tools/call`；`notifications/*` 不回复，未知方法回 `-32601`。7 个工具的 `inputSchema` 都是 `additionalProperties: false` 的对象，调用参数先按它校验（缺必填、类型、枚举、范围、多余字段都报 `SchemaValidationError` 并逐条列出 `problems`）；`tb_instantiate_flow` 的参数就是 `flow_plan.schema.json`，其中 `steps[]` 每一项也是 `additionalProperties: false`，拼错的步骤字段（如 `asignnee`）报 `SchemaValidationError`，不建任何任务。结果放在 `structuredContent`，`content` 是同一 JSON 的文本：任务序列化为普通 dict（`manual_override_fields` 为排序后的列表），`tb_list_tasks` 每项另带 `incomplete_blocker_count`，`tb_manage_dependency` 返回 `changed`。`TaskboardError`、`ValueError`、`TypeError`、`KeyError` 返回 `isError: true` 的 `{"error", "error_type", …}`，并按类型附 `cycle_path`、`blocking_task_ids`、`task_id` / `expected_version`、`problems`、`source_ref`；其他异常只回 JSON-RPC `-32603 internal error`，不回显异常文本，堆栈打到 stderr。
- **HTTP**（`adapters/http_server.TaskboardHTTPServer`，标准库 `ThreadingHTTPServer`）：`GET /healthz` 与 `GET <base_path>/healthz` 返回 `200 {"status": "ok"}`；`POST /mcp` 与 `POST <base_path>/mcp` 共用同一鉴权与处理器。保留前缀的反代（Dokploy / Traefik `PathPrefix(/taskboard)`）走带前缀的路径；剥离前缀的反代（Caddy `handle_path /taskboard/*`）与容器内探活走裸路径，`base_path` 为空与否都可用。缺 `Content-Length` 回 411，超过 `max_body_bytes` 在读取前回 413，Bearer 缺失或不符回 401，不是 JSON 对象回 400，通知回 202，其他路径回 404。
- **入口**（`app/main.py`，`python -m taskboard.app`）：`--config taskboard.toml` 启动常驻服务，先起 HTTP 再订阅（启动 RelayAgent）；收到 `SIGINT` / `SIGTERM` 时先停 Relay（在途处理仍在写库），再停 HTTP、关库，退出码 0。审计默认用 `StderrAuditSink`，每条一行 JSON。`--mcp-stdio --config taskboard.toml` 每行一条 JSON-RPC（坏 JSON 回 `-32700`），不起 HTTP 与 RelayAgent，避免第二个同 `consumer_id` 的 Agent 以 4009 顶掉常驻服务的连接；配置了 `mcp_url` 且有 `SWITCHBOARD_MCP_TOKEN` 时经 `SwitchboardMCPPublisher` 发布，否则在 stderr 提示没有上行：任务照常进入 `ready` 并占用 `dispatch_seq`，但不发 `work.ready`。
- **双进程验收**（`tests/integration/test_taskboard_dual_process_e2e.py`）：临时目录、随机端口、测试占位令牌，真实拉起 `python -m switchboard.app`（`transport = "hybrid"`）与 `python -m taskboard.app`（`base_path = "/taskboard/"`）。① 向 Switchboard 发 GitHub `issues opened`：Taskboard 经 Relay 收到、自动 `ready`，经 `/mcp submit_work` 发回 `work.ready`（`external_id = tb:<task_id>:d1`，`trace_id` 为原入站 `event_id`，`hop_count = 1`），落入 Switchboard 的 `hibernaut` 投递队列（未连接，保持 `pending`），原 `work.opened` 对 `taskboard` 的投递为 `acked`；后贴标签的旧 Issue（`labeled` → `work.updated`）同样建单并派发；SIGTERM 后退出码 0。② 经 `/taskboard/mcp` 调 `tb_create_task` 与 `tb_manage_dependency` 建 A→B，把 A 推进到 `done` 后 B 自动解锁，Switchboard 收到 B 的 `work.ready`；`human:` 任务的 `human_todo` 通知经 `report_execution` 保留 `source="taskboard"`，回流给 Taskboard 时被识别为自己的事件并 `acked`。

### 10.2 上线阶段 2：Hibernaut `work.ready` / `task_action` 闭环

`work.ready` 经入站桥（§7.2）落入 Hibernaut `event_inbox`，payload 顶层带 `task_id`、`trace_id`、`hop_count`。L2 `AgentWorker` 只读这些纯数据键，不导入 `taskboard` / `switchboard`。

- **任务关联（`TaskLink`）**：L0 `SessionRef.task_link`（`task_id`、`trace_id`、`hop_count`），SQLite `sessions.task_link` 列存 JSON（旧库启动时 `ALTER TABLE` 补列）。批内事件带 `task_id` 时以最后一个为准（新的派发替换旧关联），否则沿用会话上的关联，所以审批恢复的 `approval.decided`（不带 `task_id`）仍能回写同一任务。`Suspend` 与开 PR 的 `Emit` 保留关联；`complete`、`release` 之后清空，同一会话里后续的评论不再回写已结束的任务。关联在 Run 结束后按实际执行的批次（含 fold 进来的事件）与开始时会话上的关联统一解析一次，同一个值既用于回报也写回会话。一个会话只跟踪一个任务：新的 `task_id` 取代会话上原有的任务（挂起审批中、等 PR 合并，或同一 Run 里 fold 进来的新派发取代已 claim 的任务）时，先为被取代的任务写一条 `task_sync`（`task_action = "release"`、`stage = "superseded"`），再 claim 新任务，被取代的任务不会停在 `in_progress`；同一任务重新派发不 release。
- **`claim`**：Run 开始执行前写一条 `task_sync`（`outcome_kind = "done"`、`task_action = "claim"`、`stage = "running"`，带 `task_id`、`run_id`、`session_id`、`correlation_key`、`trace_id`、`hop_count`）。停机重启接回的 Run（`resume`）不再 claim，原进程已经 claim 过。审批恢复的 Run 再 claim 一次，Taskboard 按 `in_progress → in_progress` 幂等处理，`stage` 回到 `running`。`new_event_policy = "interrupt"` 下可被中断的 Run 不提前 claim，claim 与结果在 Run 结束时一起写：被中断的 Run 不写任何 Outbox 消息，`task_sync` 也不写，合并重启后的 Run 再写。
- **结束**：同一 Run 的 `run_id` 在 claim 与结果之间一致。
  - `Suspend`：审批请求的 Outbox 元数据带 `task_action = "update_stage"`、`stage = "awaiting_approval"`；任务保持 `in_progress`，不 `release`。
  - `Emit(status = "failed")`：最后一条消息带 `task_action = "release"`、`stage = "failed"`（`outcome_kind` 仍为 `emit`，失败消息照常发给人）；Taskboard 把任务退回 `ready` 且不重派，避免失败循环。
  - `Emit` 且 `delivery.state = "pr_open"`：最后一条消息带 `task_action = "update_stage"`、`stage = "waiting_pr_merge"`；PR / Issue 关闭触发的 `work.closed(state = "closed")` 再把任务标 `done`。
  - 其余 `Emit`（含 `stopped`、`refused`）：最后一条消息带 `task_action = "complete"`（同条发送，不另发）；没有消息时补一条 `task_sync`（`complete`）。无消息但需要 `release` 时，`task_sync` 的 `outcome_kind` 为 `error`。
  - `Silent`：补一条 `task_sync`（`complete`）。
  - 执行异常（`ExecutorFailed`）：事件标 `failed` 后补一条 `task_sync`（`outcome_kind = "error"`、`task_action = "release"`、`stage = "failed"`），清空会话关联，任务不会一直停在 `in_progress`。可被中断的 Run 失败时还没 claim，任务仍是 `ready`，不发 `release`。
- **出站**：`task_sync` 经 `SwitchboardChannelAdapter` 成为 `outcome_kind = "done"`（或 `error`）的 `execution.reported`，Taskboard 按 `task_action` 迁移状态，Switchboard 出站网关不对外发（§7）；`FileOutboxChannel` 不写文件。
- **测试**：`tests/unit/test_taskboard_hibernaut_loop.py`：入站提升字段与 `preferred_executor`、出站透传与 `trace_id` / `hop_count` 补默认（按 Schema 校验）、Worker 生命周期（`Emit` / `Silent` / 空 `Emit` 的 `complete`，`Suspend` 后审批恢复仍 `complete`，`pr_open`，失败 `Emit` 与 `ExecutorFailed` 的 `release`，`interrupt` 中断不写 Outbox，`resume` 不重复 claim，无 `task_id` 行为不变，新派发替换关联并 release 被取代的任务（挂起会话、等 PR 合并、审批批次、fold、可中断 Run、新任务执行异常）），`FileOutboxChannel` 跳过 `task_sync`，以及 Taskboard、Switchboard、Hibernaut 同进程闭环（`work.ready` → `done`、审批后 `done`、异常后回 `ready`、开 PR 停在 `waiting_pr_merge`，claim 不发 GitHub 评论）。`tests/unit/test_switchboard_outbound.py` 覆盖网关屏蔽与通知路由，`tests/unit/test_switchboard_base_path.py` 覆盖 `[http] base_path` 的配置校验与带前缀 / 不带前缀的 `/healthz`、两个 Webhook、`/mcp` 与 Relay 握手。`scripts/select_tests.py` 把 `schemas/taskboard/**` 的改动也映射到 `tests/unit/test_taskboard_hibernaut_loop.py`。

## 11. Observability / Ledger：旁路执行账本（`src/ledger/`）

`src/ledger/` 是与 `switchboard`、`ccpeer` 并列的独立包，只依赖标准库；`.importlinter` 契约 `ledger-zero-business-deps` 禁止它导入 `agent_runtime`、`switchboard`、`taskboard`、`runner`、`memory_hub`，`tests/unit/test_ledger_all.py` 另用 AST 检查。它只追加事实、只读查询，Fail-Open：账本写失败只打 stderr，不影响主路径。数据契约是 ADR-0001 的两份 JSON Schema（Draft 2020-12）：`schemas/v1/audit_record.schema.json`（点状审计 `audit_events`）与 `schemas/v1/run_record.schema.json`（一次 Run 的区间档案 `runs`，事件经 `run_events` 多对多关联）。设计基线与已锁定决策见 [`docs/observability-ledger-design.md`](observability-ledger-design.md)。

- **独立 `ledger.db`**：`SQLiteLedgerStore` 用自己的 SQLite 文件（WAL），与主库 `event_inbox` / `worker_leases` 不争写锁。路径取 `[runtime] ledger_db_path`，留空时为 `db_path` 同目录的 `ledger.db`；`db_path = ":memory:"` 且未设 `ledger_db_path` 时不开账本。账本与运行日志同属一个 `RunLedger`（`adapters/ledger_bridge.py`），由 `AlwaysOnDaemon` 持有、随 `db` 一起关闭，热加载各代共用；改 `ledger_db_path` 需要重启。
- **运行日志**：`LocalLogStore` 把执行器输出写到 `<ledger.db 所在目录>/logs/runs/YYYY-MM-DD/<run_id>.log`，`RunRecord.log_ref` 记为 `local://YYYY-MM-DD/<run_id>.log`（读取时校验路径不越出根目录）；账本打开时按 14 天或 500 MB 双阈值清理旧日志。日志在 Run 结束后一次写入（`LocalCLIExecutor` 在子进程结束时才拿到输出），不是边跑边写。
- **接线 1：Switchboard 审计**：`switchboard/ports.py` 的 `AuditSinkPort.emit_audit`、`NoopAuditSink`、`RecordingAuditSink`、`safe_audit` 增加可选关键字 `correlation_key`、`scope`、`trace_id`、`severity`。`safe_audit` 只在调用方给了值时才把它们传给 sink，按旧签名写的 sink 照常工作；`RecordingAuditSink` 也只在给了值时记这些键。入站 `ingest`、投递 `delivery`、出站 `no_target` 的审计带上事件的 `correlation_key` 与 `scope`。Switchboard 不能导入 `ledger`，所以注入在 Hibernaut 组装根：`main()` 先开 `RunLedger`，再以 `start_switchboard(..., audit=ledger.switchboard_audit())` 启动同进程 Switchboard（Stage A），审计经 `SwitchboardLedgerAuditAdapter` 脱敏（键名含 token、secret、password、api_key、authorization、cookie 等的值写成 `[REDACTED]`）后写入 `audit_events`。Relay 模式（Stage B）与独立运行的 `python -m switchboard.app` 的审计留在各自进程，不进本机账本。
- **接线 2：Worker 记账与失败三路分流**：`AgentWorker` 的 `run_ledger` 为空时行为不变。注入后，每个结束的 Run 在 `_run_batch` 的 `finally` 里记一条 `RunLedgerEntry`（`run_id` 与 Outbox 元数据里的 `run_id` 相同）：`outcome_kind` 为 `silent / emit / suspend / interrupted / error`（中断与强制停机记 `interrupted`，执行器以 `RunCancelled` 抛出取消时附带的 telemetry 一并记下，如 Runner 的执行节点；脱离、交给下一进程的 Run 此处不记，接回后结束时再记），`emit` 另记 `emit_status`；另含 `fold` 并入的事件、`correlation_key`、`trace_id`（与 Outbox 元数据 `_trace_id` 相同，见 §7.2）、`work_key`、`parent_session_id` 与事件 payload 里的 `_replay_of_run_id`。`LedgerRunRecorder` 把 `RunTelemetry`（`LocalCLIExecutor` 填 stdout、stderr、退出码；`RunnerExecutorBridge` 另填 Runner 的 `error_kind` 与执行节点 `runner_id`，记为 `RunRecord.runner_id`，未填为 `local`）写成运行日志，用 `ledger.extract_usage` 从 stdout 取 token 与费用（`usage_source = "cli"`），再经 `safe_append_run` 追加 `RunRecord`。执行器每次抛异常都先经 `ledger.classify_error`（异常类型 → 结构化码 → 按执行器的 stderr 尾部正则 → 退出码）与 `ledger.route_error` 分流，每次尝试单独判断：
  - 瞬时（`rate_limit` / `network` / `crash`）：按 5 → 15 → 45 秒退避后在同一租约内重试（心跳续租），三次重试都失败后定为失败；
  - 确定性（`config_error` / `permission_denied`）：第 1 次即停；
  - 执行故障（`tool_error` / `bad_output` / `timeout` / `unknown`）：默认不重试。

  最终失败时事件 `mark_failed`，worktree 与日志保留，并向 Outbox 写一条告警（`kind = "run_failed"`、`outcome_kind = "error"`，元数据带 `run_id`、`error_kind`、`error_category`，正文带错误摘要并提示用 `hibernaut_replay_event` 重放；欠上级回投的 Run 不写，见「混合回信」）。执行器自己返回的 `Emit(status="failed" | "refused")` 是已交付的结果：只按其 telemetry 分类记下 `error_kind` 与 `exit_code`（telemetry 带合法的 `error_kind` 时直接采用，否则按 stderr 与退出码推断），事件照常 `done`，不重试、不另发告警。
- **接线 3：控制面重放 `InboxPort.replay()`**：归属 Hibernaut 控制面，不在 `src/ledger/` 里。`SQLiteInboxAdapter.replay(event_id, *, executor_id_override=None, force=False, replay_of_run_id=None)` 在一个事务里把 `failed`（`force=True` 时也可以是 `done`）事件置为 `pending`、`attempts = 0`、`last_error = NULL`，payload 写入可选的 `executor_id` 与 `_replay_of_run_id`；`processing`（Run 进行中）与 `dropped`（重复事件，重放会破坏入队幂等）一律拒绝（`ValueError`）。它不碰 `worker_leases`：重放的事件像新事件一样排队，Inbox 有 Run 在跑时等它结束。旧 `RunRecord` 原样保留，新 Run 的 `replay_of_run_id` 指向它。
- **接线 4：MCP 与配置**：`MCPServerAdapter` 增加 4 个来自 `ledger.MCPReadToolHandlers` 的只读工具 `hibernaut_list_runs`、`hibernaut_get_run_log`（日志缺失时回落到存储的 `error_summary`）、`hibernaut_list_audits`、`hibernaut_executor_stats`（按执行器统计成功率、平均耗时、token、费用与错误分布；成功 = `silent`，或 `emit` 且 `emit_status = "done"`），以及控制面写工具 `hibernaut_replay_event(event_id, executor_id?, force?)`：从账本取该事件最近一次失败的 `run_id`，调 `InboxPort.replay()`，经 `EventHandler.wake()` 唤醒该 Inbox，并写审计 `AuditRecord(service="hibernaut", stage="inbox.replay", outcome="queued")`。不可重放时返回 JSON-RPC `-32602`。未开账本时只读工具返回 `-32602`，重放照常（不带 `_replay_of_run_id`）。`--mcp-stdio` 伴随进程打开同一个 `ledger.db` 查询。
- **复盘与 Memory 闸门**：复盘结论经 MCP 工具 `memory_record_postmortem` 交给 Memory Hub 的两段式沉淀（§14）：瞬时故障不进 Memory；结论先写 `notes/postmortem/` 候选，复现 ≥ 2 次才生成 `instructions.md` 提案，由人批准后生效。账本包自带的 `memory_gate.py` 未接线。
- **测试**：`tests/unit/test_ledger_all.py`（包自身：AST 边界、Schema 双向契约、`ledger.db` 多对多与统计、Fail-Open、三级分类、日志防穿越与清理、双源计费、Memory 闸门、Switchboard 适配器脱敏与 MCP 只读处理器）；`tests/unit/test_ledger_wiring.py`、`tests/integration/test_ledger_wiring.py`（4 处接线：审计端口新参数与同进程 Switchboard 审计入账、Worker 记账与日志 / usage、三路分流与告警、账本故障不影响 Run、`LocalCLIExecutor` telemetry、SQLite 与内存 Inbox 的 `replay` 契约、`ledger_db_path` 默认值、MCP 只读工具与失败事件重放端到端）。

## 12. Runner（执行面 / 执行节点）

`src/runner/` 是无业务语义的通用代码执行宿主包（`.importlinter` 契约 `runner-zero-business-deps` 禁止其导入 `agent_runtime` / `taskboard` / `switchboard` / `workshop` / `memory_hub` / `ledger`），遵循 [`ADR-0001`](adr/0001-cross-project-protocol-schema.md) 的 JSON Schema Draft 2020-12 契约（[`schemas/runner/v1/`](../schemas/runner/v1/)），支持 Stage 1 本机同进程直调（`InProcessRunnerClient`）与 Stage 2 反向 WebSocket 多节点调度（`RunnerRelayHub` / `RunnerRelayAgent` + `conn_epoch` + `WorkspaceAffinityStore`）。完整设计见 [`docs/runner.md`](runner.md) 与交互式蓝图 [`docs/runner_blueprint.html`](runner_blueprint.html)；HB 控制面薄适配层见 `src/agent_runtime/adapters/runner_bridge.py`。

- **执行安全**：Run 结束（含被取消）前回收整个进程组；同一工作区同时只有一个 Run（`workspace_busy`）；只读 Run 用每次 Run 各自建出、结束即删的 detached worktree，放在独立的只读根下且动手前核对不是写 worktree，不挂主检出；`run_id` 只对同一请求（调用方、工作区与执行字段指纹一致）复用，Hub 缓存已结束的非拒绝结果供重试；中断与查询只对提交 Run 的调用方生效；节点断线时先等本连接的 Run 结束再重连；Supervisor 先开日志再启动进程，输出按块排空；回复只认发出请求的连接；回收与被取消的 Run 等 worktree 线程跑完才放开工作区；Bridge 被 Worker 取消时中断 Run 并等它结束；Hub 换连接或节点心跳超时时在途 Run 以 `RunnerConnectionLostError` 结束；子进程环境按白名单构造、不带凭据（含带账号密码的代理 URL）；写工作区在首次发送前认领节点，同一工作区的写请求按工作区串行派发到节点确认；交互请求在没有 Orca 终端启动能力时被拒。没有 PID-1 reaper 的 Linux 容器里，组内只剩僵尸的进程组视为已退出。Bridge 的每个结果带 `RunTelemetry`，接入后经 §11 的 `RunLedgerPort` 记账与分类。细则见 [`docs/runner.md`](runner.md) §6。
- **逐次工具授权**：`RunnerExecutorBridge(authorize_tools=True)` 给 `runner.run()` 挂 `ToolAuthorizer`，CLI 的每次工具调用由工具前置钩子经 `ToolGate`（Relay 模式再经 `tool.authorize` / `tool.decision` 帧）交给 `caps.permissions.check()`：`allow` 放行，`block` 拒绝并告知原因，`defer` 中断 Run 并返回 `Suspend`，批准后只放行一次参数相同的调用。会调工具的执行器没有授权钩子、或钩子没有加载时不运行或结果作废。支持 `claude` / `grok` / `cursor-agent`，`dsh` 没有钩子、仍被拒。
- **组装根接入**：`hibernaut.toml` 的可选 `[runner]` 段（`RunnerLinkConfig`），默认 `enabled = false`，此时组装根与以前相同。启用后 `app/bootstrap.py` 的 `open_runner` 按 `mode` 建 `RunnerHandle`：`in_process` 为 `RunnerDaemon` + `InProcessRunnerClient`，`relay` 为 `RunnerRelayHub` + `WorkspaceAffinityStore`；`build_daemon_from_config` 把各项目里列出的 CLI agent 换成 `RunnerExecutorBridge` 放进 `executors_by_project`，其余执行器不变。handle 由 `AlwaysOnDaemon.run()` / `serve_configured()` 启停，热加载各代共用。细则见 [`docs/runner.md`](runner.md) §7。
- **只读试点路由**：与 `[runner]` 互不依赖，默认关闭。`[runner_pilot]`（`RunnerPilotConfig`）打开后，`app/main.py` 给指定的任务级 Inbox 单独的 `LimitRoute` 与 `AgentWorker`：执行器固定为 `ProtocolCheckExecutor`（`adapters/runner_pilot.py`，`RunnerExecutorBridge` 的子类，`executor_calls_tools=False`，派发前仍经 `PermissionPort.check("runner.protocol_check.launch")`），新事件策略 `interrupt`，不涉及本进程的 worktree。Relay 由 `serve_configured` 管理，只监听 `127.0.0.1`、共享令牌鉴权，只接纳配置的那一台单槽位、只带校验程序的节点；未监听时该 Inbox 的事件保持 `pending`，不改由其他执行器执行。打开期间该 Inbox 的 `InboxRoute` 固定为只许 `runner-protocol-check` 的绑定（`pilot_inbox`），不受覆盖它的 `inbox_bindings` 影响；关闭后恢复原绑定。其余 Inbox 的路由、执行器与授权检查不变；各执行器表里的 `runner-protocol-check` 是只回「未执行」并关闭会话的占位（`ClosedRouteExecutor`），回退后的遗留事件因此能了结。热加载关闭时 Relay 等在途 Run 结束再关，未关闭前不接受改其他项。`RunTelemetry.runner_log` 把节点上的运行日志位置与摘要带进账本日志。完整说明见 [`docs/runner.md`](runner.md) §9，操作步骤见 [`deploy/runner/README.md`](../deploy/runner/README.md)。
- **远端只读 Agent 节点**：默认关闭，用上面 `[runner]` 的 `relay` 模式，不加新路由。`readonly_only` 让列出的 agent 每个 Run 都只读，`token_file` 从 0600 文件读 Relay 令牌。节点侧是 `python -m runner.agent_service`（`src/runner/agent_service.py`，与试点共用 `runner/service.py` 的启动、单实例锁与停机）：单槽位、单项目、只读、恰好一个 `claude` 执行器，参数固定；`RunnerDaemon(tool_guard=workspace_read_refusal)` 让节点在问 Hibernaut 之前先拒绝工作区之外的读取和三个只读工具以外的调用。两端都只用 `127.0.0.1`，跨机由 SSH 反向转发加密；`RunnerRelayAgent` 对静默连接设上限，隧道另一端断网时会重连。与试点并行、与其他执行器互不影响。完整说明见 [`docs/runner.md`](runner.md) §10，操作步骤见 [`deploy/runner/REMOTE.md`](../deploy/runner/REMOTE.md)。

## 14. Memory Hub：分层预算的项目记忆（`src/memory_hub/`）

`src/memory_hub/` 是只依赖标准库的独立包。`.importlinter` 的 `memory-hub-zero-business-deps` 禁止它导入 `agent_runtime`、`switchboard`、`taskboard`、`runner`、`ledger`；`business-packages-no-memory-hub` 禁止 `switchboard`、`runner`、`taskboard` 导入它；`tests/unit/test_memory_hub.py`、`tests/integration/test_memory_hub.py` 另用 AST 检查。数据契约是 `schemas/v1/memory_{baseline,proposal,search,postmortem}.schema.json`（Draft 2020-12）。包按 v1.0 交付件合入，之后只改过 `index_fts5.py` 的索引同步（见下文「检索索引」），Hibernaut 侧的约束都写在接线层。

- **分区**：`inbox_id` 先归到 `project_key`：`[memory_hub.inbox_projects]` 的显式映射 → 不属于项目的 Inbox（`sys:*`，以及 `[[runtime.inbox_bindings]]` 绑定了 `workdir` 的，不论叫什么）取整个 `inbox_id` 规范化，各有各的记忆 → `proj:<key>` 或 `proj:<key>:<子队列>` → `<key>:<任务>`（`user:` 除外）→ 整个 `inbox_id` 规范化。同一 `project_key` 的 Inbox 共用 `<memory_root>/projects/<project_key>/`。非项目绑定随配置热加载生效，加载失败则保持原样。目录在建 Worker 时就建好，建不出来的 Inbox 按 `InboxRefused` 处理（§4）。
- **旧目录迁移**（`memory_fs/legacy.py`）：以前每个 `inbox_id` 一个目录。首次访问某 Inbox 的记忆时，把旧目录的文件复制进项目目录，旧目录不动、留标记 `.memory_hub_adopted`，只做一次；Memory Hub 正在使用的目录属于别的分区，不会被当作旧目录。主 Inbox（`proj__<key>`）先复制；同名而内容不同的文件放 `notes/legacy/<旧目录>/`，不覆盖。
- **写入策略**（`memory_hub/governance.py`）：

  | 目标 | 运行中写入 |
  | :--- | :--- |
  | `global://`、`kb://` | 拒绝 |
  | `proj://<key>/instructions.md`、`shared://`、项目里的其他文件 | 生成提案，人批准后生效 |
  | `notes/*`、`index.md` | 去重与预算检查后写入 |
  | `progress/*` | 直接写入 |
  | `reported.md` | 追加，超出预算的旧条目滚动归档 |

  `MemoryPort.write("instructions.md", …)` 因此不再立即生效；`write_memory` 工具的返回文字会说明已排队待批。去重只判 `memory_propose_write`，`MemoryPort.write` 是整文件替换。
- **端口委托**（`memory_fs/partitioned.py`）：`PartitionedMemoryAdapter` 委托 `LegacyMemoryPortAdapter`，保持 `MemoryPort` 的方法与返回值，另有 `load_baseline_bundle()`。URI 可以写任意项目，适配器只许本项目，越界抛 `PermissionError`。
- **单写者**（`memory_fs/hub.py` 的 `GovernedMemoryHub`）：包内读改写不加锁，所以每个进程一个 hub，读写与审批持线程锁加 `<memory_root>/.memory_hub.lock` 文件锁，daemon、HTTP 服务与 `--mcp-stdio` 伴随进程不会互相覆盖。提案号校验格式，已决定的提案不能再改判。热加载各代共用同一个 hub，改 `[memory_hub]` 需要重启。
- **检索索引**（`memory_hub/index_fts5.py`）：项目与共享记忆、知识库挂载各一个 FTS5 库。列文件、同步、查询在同一个 `BEGIN IMMEDIATE` 事务里，GC 的同步与写入后的索引刷新要等它结束，线程间与进程间都互斥；中途失败整体回滚。按项目的局部同步与重建只动该项目和共享层的行，别的项目不受影响。检索不占上面的文件锁，索引大挂载时写入照常。
- **Prompt Cache 分段**（`memory_fs/segments.py`）：`stable_prefix`（全局与项目 `instructions.md`、`index.md`）在缓存断点前，`volatile_tail`（`reported.md`）在断点后。白盒执行器把前者放系统前缀，后者放每次请求的第一条消息，不进断点与压缩；CLI 与 Steward 的提示词里 `reported.md` 排在稳定部分之后；SDE 只用稳定部分，`index.md` 非空时在其后加一段 `Project memory tools`：列出的笔记用 `memory_read` 打开，动手前先看与任务相关的；没有目录时首个提示词不变。预算由 `[memory_hub.budget]` 定（单位为估算 token，默认 1500 / 2500 / 1500 / 1000，总上限 6500），超出截断并记 `memory.budget_exceeded` 审计。
- **工具与权限**：Run 里 `memory_search`、`memory_read`、`memory_propose_write` 默认放行，`memory_approve_proposal` 默认 `defer`：白盒执行器挂起，审批消息里带提案正文。Steward 没有批准工具。Hibernaut 的 MCP 控制面（`memory_bridge.py`）另给运营者 `memory_list_proposals`、`memory_reject_proposal` 与 `memory_record_postmortem`，可跨项目。
- **SDE 的记忆工具**（`executor_cli/memory_access.py`、`memory_mcp.py`）：SDE 会话有 `memory_search` 与 `memory_read`，定义与 Steward 的同名工具是同一份，没有任何写工具。
  - **接法**：会话比 Run 和进程活得久，所以不用 Steward 那种随 Run 关闭的 socket。启动参数 `--mcp-config` 挂上 stdio 服务 `hibernaut_memory`（`python -I memory_mcp.py <socket> <令牌>`，仅标准库；与 MCP 交接的 `hibernaut_handoff` 写在同一个值里），`tools/list` 自己答，每次 `tools/call` 新开一条到 daemon 的 Unix socket 连接。socket 位置由 `db_path` 定：`<数据库目录>/.hibernaut-memory/<库名>.sock`，超过 100 字节时改为 `/tmp/hibernaut-memory-<uid>/<哈希>.sock`，目录 0700 且必须属于本用户（两端都查）。令牌每个 `session_id` 一个，存 `memory_grants` 表，重启、续接后不变。daemon 从第一个 Run 之前到排空之后都在听；新进程接管 socket 后，旧进程退出时不删它。
  - **每次调用**（daemon 里执行）：只认这两个工具名 → 令牌对应的会话存在且未关闭 → `PermissionPort.check()`，非 `allow` 不执行 → 按会话的 `inbox_id` 取 `memory_for()`，项目范围与专家的 `ExpertMount` 同 Run 内。热加载生效后用新配置的范围与权限，不论会话是哪代启动的。
  - **不可用时**：daemon 停着、重启中、socket 开不了，工具返回说明（`isError`），会话与交付照常；令牌存取失败时会话不带工具启动并记日志，首个提示词里 `Project memory tools` 与 `Earlier attempts` 两段在启动那一刻去掉（挂起后才启动的也一样，看的是启动时有没有挂上）。
  - **覆盖**：一次性会话（`interactive = false`）、可见终端的 MCP 交接与 peer 交接都有，送评审、挂起、`--resume`、重启接回后仍可用。升级前已开着的会话没有，关掉后续接才有。评审会话没有。CLI 模板执行器、远端 runner 等非 Claude Code 的 harness 没有，提示词不变。`--demo` 与内存数据库不开。
  - **边界**：令牌在会话的启动参数里，同一用户的其他进程看得到；socket 只对本用户开放，且拿到令牌也只能读。
- **任务记录**（`engine/attempts.py`、`executor_cli/attempt_notes.py`，表 `attempt_notes`）：任务 payload 写 `attempt_notes = "<目标名>"` 时，hb 在任务结束时把「试了什么、结果如何」记进本项目的 `notes/attempts/<目标名>.md`；没写的任务什么都不记，因为 `index.md` 的预算有限，一次性任务各占一行会把它占满。
  - **字段**：目标名以小写字母或数字开头，只含小写字母、数字、`-`、`_`，至多 64 个字符（不收大写：macOS 不分大小写，两种写法会是同一个文件、目录两行）。受信任的入口同 `activities`、`base_ref`：`/events`、`hibernaut_ingest_event`、Drive frontmatter、配置的定时器；转投继承，Switchboard 的 metadata 不提到顶层。不合格的值，前两个入口当场拒绝（HTTP 400、MCP `-32602`）；其余在 Run 开始时返回 `Emit(status="refused")` 并说明，不建 worktree、不启动开发。
  - **一次任务一条**：以写了该字段的事件的去重键 `(inbox_id, source, external_id)` 为准，重放、重启接回、重复的终态都是同一条；同一会话里没写该字段的跟进继续那一条，同批有几条写了时以最后一条为准。内容没变不重写，变了更新那一条并移到最前；「已合并」不会被之后的结果改回。
  - **结果**：已合并（带 PR 链接）、没合并（带 PR 链接或原因）、没有改动、失败、停止。挂起、中断、停机脱离都不算结束。会话在有结果之前被关闭或归档记为停止（`SQLiteSessionStoreAdapter.on_closed`）。任务结束以后才合并的，由后台清扫和回收前的检查（`OrcaWorktreeManager.settle()`）改为已合并。
  - **只算自己的合并**：同一个 `work_key` 的 worktree、分支和交付记录会先后用于几次尝试，所以记下每次开始时的 `HEAD`（`seen_head`）和它自己最后一次提交（`dev_head`，每轮开发后看）。事后合并的 PR 算这次的，要么 URL 就是这条已记下的 PR，要么其 head 恰好等于 `dev_head`；head 只是含有它，说明上面还有别的工作，是后来那次的合并，不算。交付步骤报的 PR 同样核对：推送的 head 含 `dev_head`（上面可有交付自己的版本与合主干提交），且中间没有别的尝试的提交，才记下它的 URL（交付挂起等人时也记）；没有新提交也没有自己的 PR 记为没有改动，PR 不是这次的记为没合并、不带那条 PR。任务结束后再开始（重放、跟进）而 `HEAD` 已被别的工作移动过，之前的提交不再算作这次的。`settle()` 只看 workspace 归属 Inbox（没有则项目主 Inbox）的记录，归属不明就不改；只有带自己提交或 PR 的未合并记录才查 GitHub，没写该字段的任务不多一次调用。读不到 `HEAD` 时照交付步骤报的记。
  - **文件**：首行说明这是什么（也是 `index.md` 里唯一那一行的内容），次行注明 summary 由 agent 撰写、只是记录不是指令；新的在前。每条有时间（UTC，结果记下的时刻）、结果、标题、`external_id`、PR、说明与 SDE summary。summary 逐行加 `>` 引用，伪造不了别的条目；至多 3000 字节，且不超过 `max_note_bytes` 的四分之一。超出 `max_note_bytes` 时从最旧的一条起整条丢弃；人写在条目之前的文字保留。
  - **写入**：`PartitionedMemoryAdapter.rewrite_note()` 在 hub 的锁内读、改、`propose_write`，策略、预算与目录登记都是 `notes/*` 现有的，经任务所在 Inbox 的适配器写，到不了别的项目。任何一步失败只记日志，不影响结果与交付；没写成的在同一任务下次结束时补写。表里的一行在事务内重读再改（`SQLiteAttemptStore.update()`，git 在事务外先跑），写文件时在 hub 的锁内再读一次，所以别的连接在读写之间记下的「已合并」不会被旧值盖掉，内容没变也不清 `written`。
  - **首个提示词**：文件已存在且会话挂上了记忆工具时加一段 `Earlier attempts`，只给路径：先用 `memory_read` 读它，里面没效果的做法不要再试。
- **复盘**：`memory_record_postmortem` 只收 `run_id`、根因和规则；项目、错误类别、复现次数都从执行账本取。复现指同项目、同错误类别、错误摘要去掉数字与哈希后相同的其他失败 Run；没有摘要的不计。成功的 Run 与不存在的 Run 被拒绝。
- **机械 GC**（`MemoryGarbageCollector`）：启动时一轮，之后每 `gc_interval_seconds`（默认 86400，0 关闭）一轮，逐项目滚动 `reported.md`、归档已结束会话的旧 `progress/*`、校准 `index.md`、让过期提案失效。只归档会话已关闭且没有其他会话在用的 `progress` 文件，对不上会话的一律保留。
- **HTTP / MCP 服务**（可选，`[memory_hub.http]`）：`ScopedMemoryHTTPServer` 默认只听回环地址，明文 HTTP，跨主机要在前面加 TLS。每个 token 有角色 `readonly` / `propose` / `admin` 与项目范围，取自环境变量并在启动时删除，agent 子进程拿不到。提案列表按 token 的项目过滤，提案作者取 token 的 subject。`admin` 可批准任意项目的提案，所以不许限定项目。
- **审计**：hub 的审计事件写入执行账本 `audit_events`，`scope` 为 `project_key`。
- **测试**：`tests/unit/test_memory_hub.py`、`tests/integration/test_memory_hub.py`（包自身）；`tests/unit/test_memory_hub_wiring.py`（依赖契约、配置、分区与迁移、越权、并发写、索引同步与检索的互斥、分段、工具与审批、复盘、GC、HTTP、热加载）；`tests/unit/test_sde_memory.py`、`tests/integration/test_sde_memory.py`（SDE 的记忆工具，调用都经真实 MCP 子进程）；`tests/unit/test_attempt_notes.py`、`tests/integration/test_attempt_notes.py`（任务记录）。

## 15. 个人人机协作（`src/collaboration/`）

`src/collaboration/` 是只依赖标准库的独立包（`.importlinter` 的 `collaboration-zero-business-deps`；反向由 `business-packages-no-collaboration` 禁止）。数据契约是 `schemas/v1/{closeout_card,expert_profile,digest_snapshot}.schema.json`。默认关闭；`[collaboration] enabled = true` 打开，改 `[collaboration]` 或 `[experts]` 需要重启，项目抽调哪些专家可以热加载。

- **薄幕僚长（D1-B / D5-A）**：`user:main`（`chief_inbox`）绑一个 `steward`，`skills` 列 `builtin:steward` 与 `builtin:chief-of-staff`，绑定写明 `workdir` 与 `forward_to`；机制就是全局 Steward（§4），没有新的执行器，各项目仍由自己的 Steward 负责。`chief_inbox` 须是一条精确、不带 `system_tools` 的 `[[runtime.inbox_bindings]]`，否则加载报错。
- **共享专家池（D3-B）**：`[experts.<role>]` 声明专家（`agent` 指向 `[agents]`），项目用 `experts = [...]` 抽调。`draft_experts()` 经 `ExpertPoolRegistry.resolve_for_project()` 给每个专家生成一条 `ExpertBinding`：Inbox `proj:<project>:<role>` 与 `proj:<project>:<role>:<task>` 只用该专家的 agent，排在手写绑定之前。同一个 agent 服务多个项目（M:N）；agent 没写 `max_concurrency` 时取专家的。项目主 Inbox 须是 `proj:<key>`，`inbox_id` 须盖住专家的 Inbox。`skills`、`quality_gates`、`allow_direct_channel` 只作说明，不参与执行。
- **四层记忆（D3-B / D7-B，`memory_fs/expert_mount.py`）**：专家的 Run 只看得到下表，其余 URI 抛 `PermissionError`，检索结果同样过滤。启动时项目与角色两层按 `expert_budget_chars` 的份额截断；共享与知识库按需读取。

  | 层 | URI | Run 中写入 |
  | :--- | :--- | :--- |
  | 本项目 | `proj://<key>/` | 照 Memory Hub 的写入策略（§14） |
  | 角色 | `role://<role>/` | 只生成提案；批准时核对提案当时的 `sha256`，变了就拒绝 |
  | 共享 | `shared://notes/` | 只读 |
  | 知识库 | `kb://pkb/` | 只读（`[memory_hub.mounts.pkb]`） |
  | 另列的项目 | `proj://<other>/`（`expert_readonly_projects`） | 只读 |

  角色文件在 `<memory_root>/roles/<role>/`，各项目共用一份；`RoleSkillMemoryStore` 与 Memory Hub 共用同一把锁，批准后随 `auto_git_commit` 一起提交。提案只能在 hub 上批准，Run 没有批准工具。把专家的 Inbox 用 `[memory_hub.inbox_projects]` 归到别的项目，加载时拒绝。
- **收口卡（D2-B / D6-A，`collaboration_bridge.py`）**：`emit_closeout_card` 只写草稿（`<memory_root>/closeouts/`），不回流。提交时就核对项目存在、记忆目标合法（只许 `role://<已声明角色>/`、`shared://` 和本项目的 `proj://`）。`confirm_closeout_card` 或 hub 上「确认并回流」才依次写三处：记忆提案、Taskboard 后续任务、给幕僚长 Inbox 的 `agent:closeout` 事件。三处都用由卡号推出的固定标识（提案号、`source_ref`、`external_id`），所以中途失败后再确认一次即可补齐，不会重复。没配 Taskboard 却带后续任务的卡不许确认。`agent:closeout` 属内部来源，公开入口不收，也不产生 `origin`；正文注明由 agent 撰写、不是指令。
- **MCP 工具**：`emit_closeout_card`、`confirm_closeout_card`、`resolve_expert_mount`、`propose_role_skill`、`route_notification` 挂在 Hibernaut 的 MCP 控制面上，持控制面令牌者即运营者。`confirmed_by`、`proposed_by` 由服务端填，不信参数；`resolve_expert_mount` 只答项目真的抽调了的专家，预算与只读项目取配置。stdio 伴随进程也有这五个工具，不开 hub；环境里没有 Taskboard 令牌时不建后续任务。
- **飞书推送红线（D8-B，`switchboard_bridge.py`）**：打开协作后，`SwitchboardChannelAdapter` 出站前经 `NotificationPolicyEngine.route()`。
  - 只有审批卡，以及阻塞（`run_failed`、`resume_failed`、`agent_refused`、`return_withheld`、`forward_refused`，或任务状态为 `failed` / `stopped` / `refused`）主动推到飞书。
  - 对人在飞书里那句话的答复，发回同一个会话，不算推送，照发。定时器、Drive、Taskboard、收口卡触发的结果，或发往别的聊天的，算推送。
  - 其余改成 `outcome_kind = "done"` 并带 `notification_channel`（`hub_pull` / `silent`）发布：Switchboard 不投给人，Taskboard 照常收到 `task_action`。文件 Outbox 与其他通道不变。
  - Taskboard 自己发的通知（如 `human_todo`）走 Taskboard → Switchboard，不经 Hibernaut，不在此列。
- **Hub（D4-B / D8-B）**：`[collaboration.hub] enabled = true` 时 daemon 起 `CollaborationHubServer`，默认只听 `127.0.0.1:8796`。页面拉取最近 24 小时的简报（Taskboard 任务、账本成本，只读账本最新 500 条 Run）、两类待审提案和收口卡，在页面上批准、驳回、确认。某个数据源读不到时页面照出，并注明缺哪个。API 一律要 `Authorization: Bearer`；页面带按哈希放行的 CSP，内容全部按文本插入。对外用 `hub.guokun.ai` 时在反向代理上加 TLS 再转到这个端口；放在现有看板的子路径下则设 `base_path`，代理原样保留前缀。
- **令牌**：`HIBERNAUT_COLLABORATION_TOKEN`（hub）与 `HIBERNAUT_TASKBOARD_MCP_TOKEN`（Taskboard 的 MCP 令牌）取自环境变量，启动时取走并从环境删除，agent 子进程拿不到；缺了就拒绝启动并说明变量名。连 Taskboard 不跟随重定向。
- **与交付件 v1.0 的差别**：Hub 加了鉴权、CSP 与转义（原为无鉴权、可注入的页面）；卡号、提案号、角色与文件路径校验格式并防符号链接；批准与确认持锁，不会并发执行两次；缺 sink 时拒绝而不是悄悄丢弃；收口卡对角色文件是追加而不是整文件覆盖；MCP 工具声明并校验参数。
- **测试**：`tests/unit/test_collaboration.py`（交付件自带）、`tests/unit/test_collaboration_hardening.py`（包的缺口）、`tests/unit/test_collaboration_wiring.py`、`tests/integration/test_collaboration_wiring.py`（契约、记忆挂载、配置、幕僚长 Skill）、`tests/unit/test_collaboration_flow.py`、`tests/integration/test_collaboration_flow.py`（真 daemon、真 Taskboard 与 Switchboard gateway 的端到端）。
