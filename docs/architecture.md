# Hibernaut 架构设计文档（Git 版本化最新基线）

本文档整合原基准设计方案与已落地的全部架构演进，作为 `kun-g/hibernaut` 仓库内唯一随代码同步演进的最新架构说明（Google Drive 原基准文档《Always-on Agent 整洁架构设计方案（Task 交接文档）》保持只读存档）。参考原文：[Building always-on agents (Anthropic)](https://claude.com/resources/articles/building-always-on-agents)。

术语（Event Inbox、Inbox、`inbox_id`、Session、`work_key`、Runner、Executor 等）以 [`docs/glossary.md`](glossary.md) 为唯一基准。

## 1. 核心运行心智：休眠—唤醒周期

常驻型 Agent 绝大多数时间处于休眠状态（**Asleep, no tokens spent**），仅在外部事件或到期定时器到达时短暂唤醒执行一轮工作（**Run**），结束后状态落盘（**Stored state**）继续休眠。

单轮 Run 四步循环：

1. **An event arrives**：外部事件（用户消息、GitHub/飞书 Webhook、GitHub Issue 轮询、MCP 控制面调用、定时触发、审批回复）写入全局 Event Inbox 并快速 ACK。
2. **A session starts**：按 4 级优先级解析会话（`approval_request_id` → 显式 `session_id` → `(inbox_id, correlation_key)` → 新建），加载跨 Run 持久化状态（基线 Memory + Session 断点/历史及绑定的 `executor_id` / `executor_session_id`），并按 4 级粘滞路由（`resolve_executor_id()`）选定目标 `ExecutorPort`。
3. **The agent loop runs**：在 `PermissionPort` 门禁下执行推理、工具调用或本地 CLI 子进程，按需读取记忆与设置后续定时器。
4. **The run writes back**：持久化新状态、记忆、`(inbox_id, correlation_key) → session_id` 映射以及执行器绑定（`selected_executor.executor_id`、`outcome.executor_session_id`），产出强类型终态 `RunOutcome = Silent | Emit | Suspend` 后释放租约重新休眠。

## 2. 整洁架构分层与依赖方向（L0–L3）

依赖箭头严格由外向内单向指向：**`L2 engine/`（调用方）与 `L3 adapters/`（实现方）并列指向 `L1 core/ports.py` 与 `L0 core/models.py`**，`app/bootstrap.py` 与 `app/main.py` 为唯一依赖注入组装根（Composition Root）。

| 层级 | 路径 | 职责定位 | 依赖规则 |
| :--- | :--- | :--- | :--- |
| **L0 领域契约层** | `core/models.py` | 不可变领域数据结构（含 `Event.correlation_key`、`SessionRef.correlation_key / executor_id / executor_session_id / parent_session_id`；`Event` 只承载事件事实与 `status`，认领次数与失败原因属 L3 存储内部）、强类型终态 `RunOutcome`（仅携带 `executor_session_id`）、`NewEventPolicy` 与 4 级粘滞路由纯函数 `resolve_executor_id()` | 零外部依赖，仅 Python 标准库 |
| **L1 核心端口层** | `core/ports.py` | 定义 9 个纯抽象 `Protocol` 端口（含 `ExecutorPort.executor_id`）及 `RunCapabilities` 控制钩子 | 仅依赖 Python 标准库 + L0 |
| **L2 生命周期编排层** | `engine/` | `EventHandler`、`AgentWorker`（支持 `executors: Mapping[str, ExecutorPort]` 查表路由）、`TimerScheduler`、`OutboxDispatcher` | 仅依赖 L0 + L1，严禁 `import adapters/` 或 `app/` |
| **L3 基础设施与组装层** | `adapters/` + `app/` | SQLite 存储（含 `workspaces` 表与旧库兼容迁移）、分区 Memory、Auto Mode + Credential Proxy、外置 Drive 队列凭据代理（独立进程）、SDE 交付步骤 `PRDelivery`、白盒执行器、`LocalCLIExecutor` + `OrcaWorktreeManager`、GitHub/飞书入站与轮询、`MCPServerAdapter`、飞书出站通道、`config.py`、`bootstrap.py`、`main.py` | 实现 L1 端口或驱动 L2 `EventHandler`，仅在 `app/` 组装注入 |

### L1 全部 9 个核心端口与 RunCapabilities

| 端口 / 契约 | 职责 |
| :--- | :--- |
| `InboxPort` | 统一事件缓冲与事实源（4 态生命周期 `pending` / `processing` / `done` / `failed`，重复幂等标 `dropped`）；支持 `claim_pending`、`fetch_processing`、`bind_session`、`requeue_processing`、`mark_done`、`mark_failed` |
| `TimerPort` | 持久化定时器存储（单次 `follow_up` 与周期 `schedule`） |
| `MemoryPort` | 跨 Run 目录记忆（必载基线 `instructions.md` / `index.md` / `reported.md` + 按需 `notes/*` / `progress/*`） |
| `PermissionPort` | 每次工具调用前置三态门禁（`allow` / `block` / `defer`） |
| `OutboxPort` | 待发消息持久队列，解耦推理与外部通道投递 |
| `LockPort` | 以 `inbox_id` 为主键的单活租约锁（`acquire` / `renew` / `release`），支持进程崩溃后租约到期自动接管 |
| `SessionStorePort` | 跨 Run 会话元数据（4 态 `active` / `suspended` / `archived` / `closed`、`work_key`）、执行器绑定（`executor_id` / `executor_session_id`）、`Suspend` 审批断点（`find_by_request_id`）、活跃引用计数（`count_active_by_work_key`）、按 `inbox_id` / `status` / `parent_session_id` 过滤的 `list_sessions`、`archive_session` / `close_session` 及外部关联键映射（`find_by_correlation_key` 仅命中 `active`/`suspended`） |
| `ChannelPort` | 外部投递通道（`FeishuChannelAdapter`、`ConsoleChannelAdapter`、`WebhookChannelAdapter`；`FileOutboxChannel` 包在最外层） |
| `ExecutorPort` | Agent 单轮推理边界（声明只读属性 `executor_id`；白盒 `WhiteboxExecutor` 或黑盒 `LocalCLIExecutor`），输入批次事件与 `RunCapabilities`，输出 `RunOutcome` |
| `RunCapabilities` | 注入单轮 Run 的受控能力集合：`memory`、`timers`、`permissions`、`poll_folded_events()`、`is_interrupted()` |

## 3. 外部关联键 `correlation_key`、多执行器粘滞路由与 L3 通道

- **4 级会话解析优先级**（`AgentWorker._resolve_session()`）：`approval_request_id` → 显式 `session_id` → `(inbox_id, correlation_key)` → 新建 `session_id`。
- **同键批处理与会话轮换重绑**：`_group_into_batches()` 按解析后的键（`session_id` → `correlation_key`）稳定分组，同键全部 `pending` 事件并入一批（批内保持 `seq` 顺序），批次按各组首条事件的 `seq` 执行。无键事件彼此无关，`defer`/`fold` 下各自单独成批且不被 `fold` 注入，仅 `interrupt` 重启时合并。本键当前批次遇到两种情况会结束：带 `approval_request_id` 的审批事件（同键更早的事件与它同批，挂起会话会把不含审批结果的 Run 视为拒绝），或执行目标（payload 的 `executor_id`、`explicit_workdir`、`executor`）与本批不同的事件。同键后续事件留到下一轮重新解析会话后再执行。快照里某键有待处理的审批时，该键的第一批必须带上审批：审批前执行目标不兼容的事件暂缓到审批之后，不提前结束批次。`AgentWorker._select_executor()` 选择执行器、`LocalCLIExecutor` 选择工作目录和模板，都取自批内普通事件，只有审批单独成批时才用审批自带的目标。审批命中挂起会话的 `pending_request_id` 时，该批固定交给会话绑定的 `executor_id`（持有断点的执行器）处理；执行器绑定上线前挂起的旧会话没有 `executor_id`，当前默认执行器不能证明归属（旧版 CLI 已可按事件选模板），只接受审批事件显式指定的 `executor_id`（唯一注册的执行器也可能是替代者，不作为依据）；无法判定或持有者未注册时本批报 `ExecutorFailed`，不确认事件、不清断点，补写 `sessions.executor_id` 后原审批即可恢复；审批待处理期间，同会话里指定其他 `executor_id` 的普通事件留到审批之后执行。`fold` 只注入同键、同执行目标的事件，遇到同键审批事件即停止，含审批的批次不注入；`interrupt` 以本轮调度快照判断新事件，含审批的批次不可中断（避免重复执行已批准的工具）；重置开新 Session 时向 `SessionStorePort.save()` 写入同一 `(inbox_id, correlation_key)` 自动解绑旧会话并指向新活跃会话。
- **跨 Agent 委派与 `parent_session_id` 留痕**（异步事件接力，不新增表）：主会话的 Run 入队一条委派事件后照常结束，不等待子会话。委派事件的 payload 携带 `parent_session_id`（可选 `work_key`、`executor_id`、`readonly`），应投递到父会话同一 `inbox_id`（同分区串行单活，遵守禁止跨 `inbox_id` 挂载同一目录的红线），并使用与父会话不同的 `correlation_key`（或不带），否则会解析回父会话或在保存时把父会话轮换归档。Worker 在执行前新建子 `SessionRef` 时写入 `parent_session_id`，`work_key` 依次取 payload 的 `work_key` → 父会话的 `work_key` → `correlation_key`，因此子会话默认复用父会话的 worktree，不另开目录；子会话持久化为 `active` 后即计入 `count_active_by_work_key()`。之后 `Silent` / `Emit` / `Suspend` 回写与会话轮换都保留 `parent_session_id`。主会话先 `closed` 时引用计数仍为 1，拒绝回收；子会话 `closed` 后归零才触发回收。`readonly` 原样透传给执行器，由执行器自行约束；`hibernaut_list_sessions` 可按 `parent_session_id` 查出全部子会话。
- **多执行器粘滞路由与原生会话续接闭环**：
  - `resolve_executor_id()` 按 4 级优先级决定目标执行器：① 事件显式指定 `event.payload.get("executor_id")`（允许主动切换）→ ② 已有会话的 `session.executor_id`（默认粘滞，避免后续事件不指定时静默回退 `default_executor`）→ ③ 项目级默认 `projects.<name>.executor`（可选）→ ④ 全局 `runtime.default_executor`。
  - `AgentWorker` 持有全量注册的 `executors: Mapping[str, ExecutorPort]`，每轮查表执行后统一将 `selected_executor.executor_id` 与 `outcome.executor_session_id` 写入 `SessionStorePort`；`RunOutcome` 保持简洁不携带 `executor_id`。
  - `LocalCLIExecutor` 仅在 `session.executor_id == template.name` 且 `session.executor_session_id` 非空并配置了 `resume_args` 时启用原生会话续接；切换执行器时自动回退全新 `args`，绝不跨执行器错传原生会话 ID。
- **L3 入站驱动适配器**（直接调用 `EventHandler.ingest()`）：
  - `POST /events`：通用 JSON 事件接入（202 ACK）。
  - `POST /webhooks/github`（`GitHubWebhookAdapter`）：HMAC-SHA256 `X-Hub-Signature-256` 验签、`X-GitHub-Delivery` 幂等键、`repo -> inbox_id` 映射、Issue/PR 自动提取 `correlation_key = f"github:{repo}#{number}"`。
  - `GitHubIssuePoller`（`adapters/channels/github_poller.py`）：无公网 Webhook 时的本机定时轮询入口（支持 `gh issue list` 或 GitHub REST API 及 label 过滤），生成 `external_id = f"github-poll:{repo}#{number}:{updated_at}"` 与完全一致的 `correlation_key = f"github:{repo}#{number}"`。暂时性失败（`gh` 非零退出或超时 60s、网络错误、API 4xx/5xx）不会退出 daemon：单个仓库失败只记一条含仓库、模式与 `gh` stderr 或 HTTP 状态和响应体摘要的 WARNING，其余仓库照常入队；`run_forever()` 按指数退避重试（默认 5s 起翻倍，封顶 300s），恢复后记一条恢复日志并回到常规 `poll_interval_seconds`，期间 `/events` 等入口照常接单，停机信号在退避等待中立即生效。
  - `POST /webhooks/feishu`（`FeishuWebhookAdapter`）：支持飞书 v2.0 `url_verification` Challenge 握手（200 OK）、`verification_token` 校验、`header.event_id` 幂等键、话题 `correlation_key` 提取与审批卡片回调恢复 `Suspend`。
  - `MCPServerAdapter`（`adapters/channels/mcp_server.py`）：纯标准库 MCP JSON-RPC 2.0 入站控制面（`initialize`、`notifications/initialized`、`ping`、`tools/list`、`tools/call`），暴露 7 个核心 Tool（`hibernaut_ingest_event`、`hibernaut_list_sessions`（含 `status` / `work_key` / `executor_id` / `executor_session_id` / `parent_session_id`，可按 `parent_session_id` 过滤子会话）、`hibernaut_list_events`（含 `session_id` / `status`，以及取自 `SQLiteInboxAdapter.diagnostics()` 的 `attempts` / `last_error`）、`hibernaut_list_workspaces`、`hibernaut_resolve_approval`、`hibernaut_reclaim_workspace`、`hibernaut_close_session`），同时支持本机 `--mcp-stdio` 行帧直连与远程 `POST /mcp` Streamable HTTP（强制 `Authorization: Bearer <HIBERNAUT_MCP_TOKEN>` 校验，未配置 token 时默认禁用返回 404）。
  - `DriveTaskPoller` & `DriveResultWriter`（`adapters/channels/gdrive_tasks.py`）：无隧道 Google Drive 任务队列闭环。Hibernaut 进程不持有 Service Account 密钥：经 `ProxiedDriveClient` → `CredentialProxyClient`（本机 client token）调用外置 Drive 队列凭据代理，只收业务结果（文件元数据、任务文本、`ok`），代理拒绝时抛 `DriveProxyError`（含 HTTP 状态与原因）；按 `root_folder_id` 自动发现 `待执行` / `执行中` / `已完成` / `失败` 四个子目录（支持显式 ID 覆盖）；`poll_once()` 读取 `.md` 或自动导出 Google Doc（`text/plain`）并解析可选 YAML frontmatter（`scope` / `executor_id` / `priority` / `title`，以及供角色执行器选规范的 `activities` / `tags` / `base_ref`，逗号分隔），以 `external_id = f"gdrive:{file_id}:{modified_time}"`、`correlation_key = f"gdrive:{file_id}"` 入队后立即将文件移至 `执行中/`；`DriveResultWriter` 按执行终态回写 `## 执行结果（Hibernaut）` 并流转至 `已完成/`（`Emit`）、留在 `执行中/` 并同步走飞书/终端通知（`Suspend`）或移至 `失败/`（`failed`）；用户补充内容并移回 `待执行/` 时自动按同一 `correlation_key` 续接原 Session 与 `hb-*` worktree。
- **外置 Drive 队列凭据代理**（`adapters/credential_proxy/gdrive_queue.py`，部署见 `deploy/gdrive-proxy/`）：独立进程，以独立系统用户（macOS `_hbdriveproxy` LaunchDaemon / Linux `hb-drive-proxy` systemd）运行，代码装在 root 所有的 `/opt/hibernaut-drive-proxy`，密钥 `/etc/hibernaut-drive-proxy/sa.json` 仅该用户可读（0400）。它用 Service Account 签 RS256 JWT 换取并缓存 Access Token（多线程共用一把锁），自行调用 Drive。`DriveQueueGuard` 只开放 6 个操作：`subfolders`（仅队列根）、`list`（仅四个队列目录）、`meta` / `read` / `append`（仅直接位于队列目录内的 Markdown、文本或 Google Doc 文件；读上限 2 MiB、追加上限 256 KiB）、`move`（两端都是队列目录、互不相同、文件确在源目录）。HTTP 层只收 `POST /proxy/<service_name>/<op>`，要求 `Authorization: Bearer <client token>`（常量时间比较），带 `Origin` 的浏览器请求 403，其他路径或操作 404，非 POST 405，请求体超 1 MiB 413；ID 须为 `[A-Za-z0-9_-]`，防止注入 Drive 查询；不转发上游响应体，只回 `Drive returned HTTP <status>`。只能监听回环地址；密钥或 token 文件对组或其他用户可读、或属主不是当前用户时拒绝启动。`--check` 只读解析四个队列目录并计数。
- **L3 飞书出站通道**（`FeishuChannelAdapter`，`adapters/channels/feishu_channel.py`）：仅用标准库 `urllib.request`，基于 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` 自动缓存刷新 `tenant_access_token`，发送普通文本通知与 `Suspend` 交互审批卡片；未配置凭据时自动降级为 `ConsoleChannelAdapter`。
- **L3 文件 Outbox**（`FileOutboxChannel`，`adapters/channels/file_outbox.py`）：`[channels] outbox_dir` 设置后（相对路径以 `hibernaut.toml` 所在目录为准，支持 `~`；不设置时不建目录、不写文件，行为不变），`build_daemon` 把它包在通道链最外层：先写文件，再把原样的 `(inbox_id, content, metadata)` 交给内层（Drive 回写 → Switchboard → 飞书 / 控制台）。
  - **文件**：每条消息一个 Markdown 文件，文件名是本地时间到毫秒（`20261122-181305.123.md`），按名排序即时间顺序；同一写入者在同一毫秒内的下一条会等时钟走过这一毫秒（最多约 5 ms），与目录里已有文件重名则加 `-2`、`-3` 后缀，从不覆盖。目录不存在时自动创建。先写入隐藏临时文件并 `fsync`，再用 `os.link()` 原子地以最终名发布（目标已存在即失败，不覆盖），最后删除临时名，读到的 `.md` 总是完整的。
  - **失败与重试**：写文件失败记 ERROR 日志并抛出，`OutboxDispatcher` 照常 `mark_failed` 并重试，内层通道这次不投递，消息不丢。文件写成但内层投递失败时，重试复用已写的文件，不重复写。
  - **控制台**：启用时 `ConsoleChannelAdapter(echo=False)` 不再打印全文，`FileOutboxChannel` 每条打一行摘要 `[OUTBOX] <时间> <状态> | <任务标题> | <文件路径>`。
- **Outbox 上下文头**（`outbox_context()` 读出 `OutboxContext`，`render_header()` / `render_summary()` 渲染，文件与控制台摘要共用）：任务标题、来源（事件 `source`，加可读名：GitHub / Drive / MCP / 飞书 / Switchboard / 定时器 / `/events`）、`inbox_id`、`correlation_key`、会话 ID、执行器、状态、需要人做什么、时间，之后是 `## 正文` 与原文。缺的字段写「无」（如 worktree 回收告警这类非 Worker 消息）。等待审批的消息另有 `## 审批`：审批请求 ID、可直接执行的批准 / 拒绝 `curl`（POST 到本机 `/events`，地址取 `[channels] host/port`，通配地址换成回环；body 为 `inbox_id`、`source = "events:approval"`、`external_id = approval:<id>:approve|reject`、`payload.approval_request_id`、`payload.approved`，可加 `payload.comment`）与 MCP `hibernaut_resolve_approval` 的参数。飞书与 Switchboard 出站正文不变。
- **状态来源**：执行器在 L0 `Emit.status`（`EmitStatus = done | failed | stopped | refused`，缺省 `done`，旧代码不传即为完成）上明确标注结束方式，不解析正文：SDE `development failed` 为 `failed`、`stopped:` 为 `stopped`；评审者 `review failed` 为 `failed`、权限 `block` 为 `refused`；`LocalCLIExecutor` 无检出 / 未知模板 / 非零退出为 `failed`、工作区隔离拒绝为 `refused`；Orca 启动被 `block` 为 `refused`、续接被拒为 `stopped`。`Suspend` 的消息状态为 `awaiting_approval`。

## 4. 本机自举闭环：`OrcaWorktreeManager`、`LocalCLIExecutor` 与声明式配置

- **极简可读 Worktree 命名**（不含 repo 名与哈希）：GitHub Issue `#N` → `hb-issue-<N>` / `hb/issue-<N>`；PR `#N` → `hb-pr-<N>` / `hb/pr-<N>`；其他任务 → `hb-task-<seq>` / `hb/task-<seq>`；同仓库重名自动顺延 `-2`。
- **工作区决策优先级**：`explicit_workdir`（只读覆盖口）→ SQLite `workspaces` 表已落盘路径（按 `correlation_key` 复用）→ 动态创建（默认 `orca worktree create`，可选 `orca terminal create`，支持切换纯 `git worktree add` 后端）。命名与 `creating` 占位在同一把进程内锁下完成，同一 `work_key` 的并发请求拿到不同目录名。`workspaces.inbox_id` 记录创建该行的 inbox（新增列，旧行为 `NULL`）。
- **一个项目服务多个 inbox**（`app/projects.py`）：`[projects.<name>] inbox_id` 为字符串（单个精确 ID，原写法，原样比较、不当正则）或数组（每项直接是正则，`fullmatch` 整串匹配，如 `proj:hibernaut:.+` 匹配 `proj:hibernaut:drive`、不匹配 `proj:hibernaut:`）。数组里不含正则语法的项（只允许 `\.` 这类转义标点）只能匹配一个 ID，即精确 ID（`InboxRule.literal`，去掉转义后的原文）；只有精确 ID 能当投递地址，表达式本身从不作为投递地址。第一个精确 ID 是主 inbox，GitHub webhook / 轮询（每项目一个 `PollTarget`）与飞书入站投到它；其他渠道自配的投递目标（如 `gdrive.default_inbox_id`）不经项目规则，行为不变。旧写法的 `re:` 前缀仍接受：去掉前缀后同样按正则匹配，且该项从不算精确 ID（与旧语义一致）。加载时拒绝：空数组、非字符串或空项、空或非法正则、同项目重复项（`re:x` 与 `x` 算重复）、无精确 ID 的数组（含未转义 `.` 的 ID 算正则，报错提示写成 `\.`）、以 `re:` 开头的字符串、同一精确 ID 分属两个项目、一个项目的精确 ID 被另一项目的正则匹配。两个项目的正则互相重叠无法在加载时判定，留到分发时报歧义。`ProjectRouter.resolve(inbox_id)` 收集匹配的不同项目（同项目多条规则算一个），多于一个抛 `AmbiguousProjectMatch`（继承 `ExecutorFailed`）；组装根的 Worker 工厂在建 Worker 前解析项目，因此歧义在拿租约、选执行器、分配工作区之前抛出，`AsyncWorkerPool` 记录异常，事件保持 `pending`。检出路径、飞书 chat 等按 inbox 查的设置用 `ProjectInboxMap`（惰性 `Mapping`，正则匹配的 inbox 也能查到），执行器、默认执行器、worktree/终端后端、回收（含 MCP `hibernaut_close_session` / `hibernaut_reclaim_workspace` 经 `worktree_manager_for` 选项目的管理器）都按解析出的项目取。队列、租约、会话、记忆分区仍按 `inbox_id` 各自独立。
- **未匹配项目的 Inbox**：解析结果为空时，工厂给 `AgentWorker` 传 `hold`（`UnmatchedProjectHold`，每代配置一个实例）；需要项目检出的事件（无 `explicit_workdir`/`review_of`，不是审批回复或关闭请求，也不是挂起会话的跟进）被判为等待：Worker 只用 `InboxPort.claim_pending(inbox_id, event_ids)` 领取其余事件，等待事件不领取、不增加 `attempts`、不绑定会话，也不参与 `fold` 合并和 `interrupt` 判定；全部等待时 Worker 立即释放租约返回，不轮询、不占池位。每个事件进入等待时记一条 `WARNING`（`agent_runtime.app.projects`，含 `event_id`、source、`external_id`、`inbox_id` 与原因），同代内不重复。`AsyncWorkerPool(pending_inboxes=SQLiteInboxAdapter.pending_inbox_ids)` 在每次启动（含热加载后的新池）唤醒一次所有有 `pending` 事件的 Inbox，规则补齐后原事件按原串行与幂等语义只处理一次。
- **共享项目的写隔离**（`OrcaWorktreeManager(isolate_inboxes=True, primary_inbox_id=...)`）：服务多个 inbox（多条规则，或唯一一条不是精确 ID）的项目，每个写任务（`LocalCLIExecutor`、`SDEExecutor`）只能在 `(inbox_id, work_key)` 自己的受管 `hb-*` worktree 里运行。`workspace_key()`：主 inbox 用裸 `work_key`（与旧数据兼容），其他 inbox 用 `<inbox_id>/<work_key>`，同一 `correlation_key` 的两个 inbox 因此得到两个 worktree；`CoderReviewerExecutor` 与 SDE 的 `task_metadata` 也按这个键查写。启动前拒绝：主检出、`explicit_workdir` 不是该任务自己的 worktree（含另一个 inbox 的）、非 `hb-` 目录、归属其他 inbox 的记录；SDE 从检查点恢复时用 `assert_writable()` 复核检查点里的 workdir。拒绝时抛 `WorkspaceIsolationError`，`LocalCLIExecutor` 回 `refused: ...`，SDE 回 `development failed: ...`，不启动进程。`inbox_id` 为 `NULL` 的旧行，只有当引用它的会话全部来自请求方 inbox 时才被认领（写入 `inbox_id`），否则拒绝。字符串 `inbox_id` 的项目不启用隔离，行为不变。
- **三道安全保险**：
  1. **意图占位与对账**：创建前先在 SQLite `workspaces` 表写入 `creating` 占位，崩溃重入时先对账本地目录再决定复用或清理。
  2. **路径落盘**：分配名称时检查所有本地 `hb/` 分支，包括未挂载的分支。Orca 创建时可能再加数字后缀，执行器读取 `--json` 回执里的实际分支和路径，与主仓库的 `git worktree list --porcelain -z` 核对，确认是唯一且可用的独立工作区后登记为 `ready`。复用时用同一登记表校正 SQLite 的旧路径。执行器重试耗尽后，批次标记为 `failed`，失败原因写入 `event_inbox.last_error`（与认领计数 `attempts` 一样只在 L3 内部，经 `diagnostics()` 读取，不回填 L0 `Event`），Worker 池记录异常后继续处理其他 inbox。
  3. **引用计数前置门禁 + 三关安全回收**（`reclaim()`）：Worker 与 MCP 在会话结案后按同一 inbox 计数（`count_active_by_work_key(work_key, inbox_id) == 0`）才发起回收；`reclaim()` 再校验一次（共享项目的 worktree 只数归属 inbox 的会话，其他受管 worktree 数所有 inbox 的会话；若有 `active`/`suspended` 会话仍引用则拒绝回收并返回占用会话 ID），再执行双重归属校验（`hb-` 前缀 + `workspaces` 表记录）+ 证据关（`SQLiteWorkUsage.blockers()`：无 `review:<work_key>` 评审会话、无该任务排队或执行中的事件、无未完成的交付；GitHub 明确答复无开着的 PR，`gh` 失败即视为缺证据；无暂存/未暂存/未跟踪改动；`HEAD` 的提交都在远端，或有已合并 PR 的 `headRefOid` 正是本地 `HEAD` 且其合并提交在远端分支上，即 squash 合并），认领 `reclaiming` 后立即再查一遍，任一不通过即释放认领、保留目录并经 Outbox 告警。关闭终端从不触发回收。Orca 后端使用 `orca worktree rm --worktree path:<workdir>` 移除工作区并保留分支。
- **可配置本地 CLI 执行器**（`LocalCLIExecutor`）：实现 `ExecutorPort`，内置 `claude`（默认）、`cursor-agent`、`grok`、`dsh` 模板，支持可选 `resume_args` 原生会话续接（自动从 JSON 输出提取 `executor_session_id` / `session_id`）及透传环境变量对接本地模型网关（如 `yetone/magpie`），响应 `caps.is_interrupted()` 安全终止子进程。
- **Claude Code 共用启动适配器**（`adapters/executor_cli/claude_code.py`）：各角色（评审与 SDE）共用的启动配置与调用。`[launchers.<name>]` 声明可信启动器（`harness`、`command`、非凭据 `env`；内置 `claude`），只能来自部署配置，事件无法指定；启动器可自管配置目录、账号、网关或代理（如 `claude-sg`），原样接收参数。`ClaudeCodeProfile` 把角色以外的五项分开：`harness`、`launcher`、`billing`、`model`、`effort`（另有 `timeout_seconds`、`env`），构造时校验，启动器 harness 必须与角色一致。`harness_args()` 生成 `-p --output-format stream-json --verbose --model --effort --permission-mode <角色指定>` 加角色参数，权限模式必须显式传入，避免启动器的默认 `bypassPermissions` 生效。`child_env()` 统一剥离付费凭据、`CLAUDE_CODE_OAUTH_TOKEN`、`ANTHROPIC_BASE_URL` 与云厂商开关，叠加启动器与角色 `env`；`api` 计费把 `ANTHROPIC_BASE_URL` 指向 `[credential_proxy] url` 的 `/proxy/<anthropic_service>`，只给占位 key，真实 key 由外置凭据代理注入（与 `CredentialProxyClient` 共用 `proxy_service_url()`）。`run_claude_code()` 经 stdin 投递 prompt、读 stream-json、在 `init` 消息校验 `apiKeySource`（订阅须为 `none`，api 须为代理占位的 `ANTHROPIC_API_KEY`）与模型，并经 `process.supervise()` 处理中断与超时；`LocalCLIExecutor` 共用同一个 `supervise()`/`terminate()` 与事件取值工具（`process.py`）。
- **角色 Skill**（`adapters/executor_cli/role_skills.py`，两角色共用）：`[executors.<id>] skills` 为有序列表，元素是本地 `SKILL.md`、含该文件的目录或 `builtin:<role>`（包内 `executor_cli/skills/<role>/SKILL.md`，经 `[tool.setuptools.package-data]` 随包安装）。相对路径以配置文件所在目录为准（`parse_config(raw, base_dir=...)`，`load_config` 与热加载传入），支持 `~`。省略时用本角色内置 Skill；列出则只用所列项；空列表、找不到的文件、别的角色的 `builtin:` 均在解析时报 `ValueError`（含执行器名与路径）。解析结果存于 `ClaudeCodeProfile.skills`。每次启动由 `role_system_prompt()` 重新读取文件，拼成「程序契约 + 各 Skill（`# Role skill: <路径>`、资源目录、正文）」经 `--append-system-prompt` 传入；读取失败报 `ClaudeCodeError`，不启动。契约（返回格式、SDE 禁止 force push、评审只读）、工具白/黑名单、权限模式、`--json-schema` 与启动器仍由代码和部署配置决定，Skill、事件与项目文档都改不了，事件字段也无法选择 Skill。
- **项目规范（AGENTS.md + guidance.toml）**（`adapters/executor_cli/project_guidance.py`）：项目根目录的 `AGENTS.md` 只放简短通用约束和入口，始终注入；`guidance.toml` 以 `[[docs]]` 登记规范文档（`path`、`summary`、`activities`、`tags`、`paths` glob，`*` 不跨目录、`**` 跨目录；未知键、重复、提交里不存在或越出仓库的路径均报 `ValueError`）。**选择**：开发按事件的显式 `activities` 优先，没有时按 `tags`/`labels`（含 GitHub label 对象，忽略大小写）；评审在此基础上再按实际 diff（已提交、未提交、未跟踪）改动的路径补选（路径用 `git -z` 原样读取，不受 quotePath 转义影响，中文路径可匹配）。未命中时只给通用约束和目录（每篇一行：路径、摘要、活动、标签、路径），并写明无匹配；未选中的正文不注入。**版本固定**：所有规范文件经 `git ls-tree`/`git cat-file` 从固定 commit 读取，从不读工作区；每段正文首行 `Source: <commit>:<path>`，`git show` 可复现。仓库内 symlink 跟随至多 8 跳，越出仓库报错。`GuidancePin(workdir, commit, origin)` 决定读哪个 commit：SDE 新任务取 worktree 的 `HEAD`，连同 activities/tags 写入 `task_metadata` 表（`SQLiteTaskMetadataStore`，主键 `work_key` = 任务 `correlation_key`）和检查点 `sde.project`；同一 `work_key` 且同一 workdir 的后续任务复用已记录的 commit。开发、内置评审、返工轮、挂起恢复都用它；旧检查点只有 `commit` 时沿用，没有任何记录时取当前 `HEAD` 并在 origin 中注明。独立评审：`review_of`（或自身 `correlation_key`）在 `task_metadata` 有记录时用该 commit，activities/tags 与事件自带的合并，且无 ready workspace 时可用记录的 workdir；没有记录（仅 `explicit_workdir`）时用 `base_ref` 与 `HEAD` 的 merge base，即 diff 的基准，被审改动在其之后，无法改写评审依据。**评审引用**：阻塞项可带 `guidance_path` + `guidance_clause`（须成对），`format_blocking` 输出 `Guidance:`/`Clause:` 行；SDE 返工轮把被引用、而开发会话尚未收到的规范正文（同一 pinned commit）随修复请求补发，`sde.project.sent` 记录已发文档，每篇只发一次。
- **独立评审执行器**（`CoderReviewerExecutor`，`adapters/executor_cli/reviewer.py`）：`[executors.<id>]` 写 `role = "code-reviewer"` 时注册为评审角色（`HibernautConfig.roles`），派单用 `payload.executor_id = "<id>"`。旧名 `role = "coder-reviewer"` 与 Skill 条目 `builtin:coder-reviewer` 解析时归一为 `code-reviewer`（`role_skills.ROLE_ALIASES`），内置 Skill 目录为 `skills/code-reviewer/`。启动配置见上条共用适配器，默认 `claude-code / claude / subscription / claude-opus-5-5 / high`；非法值、`env` 中的凭据或计费开关、未声明的启动器、不适用的模板字段（`command`、`args`、`orca_agent` 等）均报 `ValueError`；热加载失败时打印原因并保留旧配置，成功后下一次评审即用新值（含切换启动器）。
  - **输入**：任务要求（`requirements` 或 `text`）、测试证据（`test_evidence`）、代码差异（执行器自己计算：`base_ref`，缺省依次尝试 `origin/HEAD`、`main` 的 merge-base 到工作区的 diff、提交列表与未跟踪文件，超 20 万字符截断）。缺要求、找不到基准或无改动直接报错，不启动模型。
  - **工作区**：`explicit_workdir` → `review_of`（开发任务的 `correlation_key`）或本事件 `correlation_key` 在 `workspaces` 表中 `ready` 的路径，再退到 `task_metadata` 记录的 workdir；评审从不创建 worktree。建议评审用独立的 `correlation_key`（如 `review:<key>`），避免开发会话的执行器粘滞绑定被切到评审者。
  - **只读**：`-p --permission-mode dontAsk`（经所选启动器），只放行 Read/Grep/Glob 与只读 git 命令，禁用 Edit/Write 类工具；运行前后用临时 index（时间戳置为 1，git 逐个按内容比对，不信任 stat，同秒同大小的改动也能识别）对工作区（HEAD + 含未跟踪文件的树）取指纹，不一致则丢弃评审结论并报错，不回滚。
  - **计费**：见共用适配器；`subscription` 用启动器自己的登录，`init` 报告任何付费来源即在会话开始时终止；`api` 只经外置凭据代理，未配置 `[credential_proxy]` 时解析即报错。`init` 报告的模型与配置全名不符同样终止。
  - **指令来源**：系统提示为评审契约 + 评审者自己的角色 Skill（默认 `builtin:code-reviewer`）；任务消息为要求、项目规范（见「项目规范」：固定 commit 的 `AGENTS.md`、目录与选中的规范正文）、测试证据与 diff。
  - **输出**：`--json-schema` 约束结构化结论，`verdict = pass | changes_requested`；阻塞项必含 `location`（文件:行）、`trigger`、`impact`，结论与阻塞项数量矛盾视为无效。结果作为一条 `Emit` 写入 Outbox；每次评审都是新会话（`--no-session-persistence`，不回填 `executor_session_id`），开发者修复后重新派单即为独立复审。权限门禁工具名 `code_reviewer.launch`（`REVIEW_LAUNCH_TOOL`）；`AutoModePermissionAdapter` 把旧名 `coder_reviewer.launch` 视为同一工具，写给旧名的 allow / defer / block 规则同样作用于新名。
- **评审者接口与 CLI 评审者**（`Reviewer` Protocol，`reviewer.py`；`CLIReviewer`，`adapters/executor_cli/cli_reviewer.py`）：SDE 评审回路只依赖 `executor_id`、`check_launch(caps, workdir)`、`review(ReviewRequest, caps) -> dict`、`format_review(review)`。`CoderReviewerExecutor` 实现它，行为不变；`CLIReviewer` 包装一个普通 `CLITemplate`（含内置 claude / cursor-agent / grok / dsh）：
  - **输入**：与评审角色相同的 prompt（需求、固定 commit 选出的项目规范、测试证据、diff、上一轮结论与增量 diff），末尾追加评审契约（只读、阻塞项字段要求）和 `REVIEW_SCHEMA`，要求只输出一个 JSON 对象。
  - **运行**：在被审 worktree 里非交互运行模板的 `command`、`args`（`{prompt}` 替换规则同 `LocalCLIExecutor`，用 `render_cli_args`；不用 `resume_args`）、`env`（叠加在进程环境上）、`timeout_seconds`；stdin 为空，`process.supervise()` 负责中断与超时。
  - **解析**：stdout 可以是纯 JSON、```json 围栏块（取最后一个能解析的），或 `{"result": "<含 JSON 的文本>"}` 信封（`structured_output` 对象优先）；再经 `validate_review` 校验。解析或校验失败时把错误附在 prompt 后重试一次，仍失败抛 `ReviewAborted`。非零退出码（消息含退出码与 stderr 前 500 字符）、超时、命令无法启动直接 `ReviewAborted`，不重试。
  - **只读**：靠事后核验，每次运行前后比对 `worktree_fingerprint()`，不一致则丢弃结论并 `ReviewAborted`；保证弱于评审角色的工具白名单。
  - **门禁与输出**：门禁同 `code_reviewer.launch`，参数 `executor`、`workdir`、`command`；`format_review` 首行 `[<executor_id>] verdict=... (cli=<command>)`，其余行与评审角色相同（`render_review`）。独立派单的评审事件仍只路由到评审角色执行器。
- **SDE 执行器**（`SDEExecutor`，`adapters/executor_cli/sde.py`）：`[executors.<id>]` 写 `role = "sde"` 时注册，派单用 `payload.executor_id = "<id>"`。启动配置同共用适配器，默认 `claude-code / claude / subscription / claude-opus-5-5 / high`；另有 `review`（布尔，默认 `true`，非布尔报错）、`reviewer`（默认 `code-reviewer`；`review = true` 时必须是已声明的评审角色执行器或普通 CLI 模板（含内置模板），指向 sde 角色、指向自己或不存在的名字解析时报错并列出可选项；未显式写 `reviewer`、没有名为 `code-reviewer` 的执行器但有名为 `coder-reviewer` 的评审角色执行器时回退用它）、`max_review_rounds`（正整数，默认 3）。热加载重建执行器，下一次运行使用新值。
  - **工作区**：同 `LocalCLIExecutor`：`explicit_workdir` → `workspaces` 表按 `correlation_key` 复用 → 动态创建。
  - **开发**：`--permission-mode dontAsk`，放行 Read/Grep/Glob/Edit/Write/MultiEdit/NotebookEdit/Bash，禁止 `git push`、`gh pr create/merge`；在任务分支提交。系统提示为 SDE 契约 + 角色 Skill（默认 `builtin:sde`：先写失败测试并保存原始输出、最小修改、跑项目规定的全套检查），任务消息为需求 + 按 `activities`/`tags`/`labels` 选出的项目规范（见「项目规范」）。`--json-schema` 约束报告（`status = done | needs_input`、`summary`、`test_evidence`、`question`、`change_kind = breaking | feature | fix | test_docs`、`change_rationale`），`done` 缺测试证据、缺合法 `change_kind` 或缺理由均视为无效；契约要求按整个分支归类并说明理由，版本由 Hibernaut 据此决定。需求取 `requirements` / `text`，都没有时取 `title` + `body`（GitHub Issue、Drive 任务），`title` 另作 PR 标题。`needs_input` 返回 `Suspend`，回答可来自同任务的跟进消息或批准时的 `comment`，经 `--resume` 回到同一开发会话；拒绝则输出 `[sde] stopped: question declined`（含问题、工作区与已有进展），不算交付。权限门禁 `sde.launch` 在每次开发启动前检查（含修复轮）：`defer` 以 `launch_pending` 挂起并把完整状态与待执行提示词写入检查点，批准即执行该次启动，拒绝输出 `stopped: launch declined`；`block` 输出 `stopped: launch blocked`。
    项目配置 delivery 时由 HB 按部署授权发布；缺省时沿用 0.7.1 的 SDE 自行推分支和开 PR 流程，合并 PR 时通过 `--delete-branch` 一并删除源分支（若 worktree 占用导致本地删分支失败，确保删掉远端分支且不碰其他 worktree）。
  - **挂起期间的跟进**：同 `correlation_key` 的非审批事件记入检查点 `followups`，以原请求 ID 重新挂起；与审批决定同批到达的非审批事件同样计入；拒绝评审重试时交付消息列出未处理的跟进；恢复时并入需求，先交开发会话处理，再送评审者。引擎规则：`Suspend` 沿用会话当前 `pending_request_id` 时只更新检查点，不重发审批卡（`AgentWorker._apply_outcome`）。
  - **评审回路**（`review = true`）：SDE 在进程内调用同一配置代生成的评审者（`Reviewer`）的 `review()`：评审角色为 `CoderReviewerExecutor`（独立只读会话，保留评审者自己的启动器、计费、模型），CLI 模板为 `CLIReviewer`；两者门禁都是 `code_reviewer.launch`，给出的 `pass` 对 `PRDelivery` 的 `require_review` 同样算数，输入为需求、执行器自算的实际 diff 与测试证据；复审额外附上轮阻塞项和两次工作区指纹（`worktree_fingerprint` 的树对象）之间的增量 diff。`changes_requested` 把阻塞项经 `--resume` 交回同一开发会话修复后再送审；`pass` 交付。评审无法完成（评审者报错、结论无效、门禁未放行）或超过 `max_review_rounds` 时返回 `Suspend`，检查点 `{"sde": {...}}` 保存工作区、需求、证据、轮次历史与阻塞项；批准则重试（有阻塞项时再修一轮），拒绝则以 `review=pending` 交付，不标为已评审。
  - **关闭评审**（`review = false`）：开发完成即交付（`review=off`），不启动评审者。
  - **交付**：一条 `Emit`，含状态、五项启动设置、工作区、摘要、`Change: <kind> (<理由>)`、测试证据、评审历史与最后一次评审结论；项目配置了交付步骤时追加其状态、PR 链接、版本决定、检查、CI 与合并 SHA。`executor_session_id` 回填开发会话 ID。中断沿用 `supervise()`，不写半成品。
- **SDE 交付步骤**（`PRDelivery`，`adapters/delivery/pr_delivery.py`；状态表 `deliveries`，`SQLiteDeliveryStore`）：SDE 只负责开发、测试与本地提交（`git push`、`gh pr create/merge` 仍被禁用）；发布由 Hibernaut 在 SDE 报告 `done` 且评审通过（或 `review = false`、或拒绝评审重试后以 `review=pending`）后执行。配置只来自部署文件的 `[projects.<name>.delivery]`（`parse_delivery()`，未知键、`auto_merge` 无 `open_pr`、越出仓库的 `version_file`、无 `version` 命名组的 `version_pattern` 等均报 `ValueError`），被改动的仓库无法授予发布权限；不配置则任务以本地提交结束。`SDEExecutor` 的 `delivery` 由组装根按项目注入，未匹配项目的兜底执行器没有交付步骤。
- **交付证据、终端退出与回收**：事件处理与交付分开完成。SDE 每次报告 `done` 后，`inspect_worktree()` 对照任务起点钉住的提交检查 worktree（`git status --porcelain --untracked-files=all`、`git rev-list --count <base>..HEAD`）：有未提交改动（测试与文档同样算）或没有新提交时，自动打回开发者一次，仍未完成则 `Suspend` 为 `incomplete`，保留会话、终端与 worktree；报告 `code_change: false` 且无提交、树干净时以「无代码改动」结束，不评审不交付。`PRDelivery._confirm()` 要求远端分支与 `gh pr view` 的 `headRefOid` 都等于推送并通过检查的提交；`PRDelivery.unverified()` 列出尚缺的证据（授权合并时还要求已合并）。仅当 `close_terminal = true`、证据齐全、无待人回答的问题、无 `SQLiteWorkUsage.peers()` 报告的在线评审交流时，先把 SHA、PR URL 与可恢复会话 ID 写入 `deliveries`，再由 `OrcaVisibleRunner.release()` 关闭终端（绑定保留 native ID 供 `--resume`；关闭失败则保留 handle）。
  - **两项授权**：`open_pr`（推任务分支并创建或复用 PR）与 `auto_merge`（合并，须先有 `open_pr`）分开配置，并分别经 `PermissionPort.check("delivery.open_pr" | "delivery.merge")` 门禁：`defer` 以 `delivery_pending` 挂起，批准后带该授权重试；`block` 记为说明，按当前状态交付。Auto Mode 默认放行这两项（项目配置即明确授权），部署可移入 defer 名单逐次确认。
  - **准备**：工作区须干净、在任务分支上；在仓库级进程内锁下 `git fetch <remote> +refs/heads/<base>:refs/remotes/<remote>/<base>`，基线不是祖先时 `git merge --no-ff` 进任务分支（只有 `version_file` 冲突时用 `git merge-file --theirs` 取基线一侧，其余冲突 `merge --abort` 并挂起报文件名）；从基线读版本，按 `change_kind` 定 `major` / `minor` / `patch` / 跳过（`bump_version()`），写入 `version_file` 并提交，分支自改的版本一律以此覆盖。随后按序运行 `checks`（同一 commit 已全部通过则不重跑），任一失败不推送并挂起附输出。
  - **发布**：`git ls-remote` 与本地 HEAD 不同时才 `git push <remote> HEAD:refs/heads/<branch>`，从不强推；`gh pr list --head <branch> --state all` 找到同 head 已合并的 PR 则直接记为 `merged`，有开着的 PR 则复用并更新标题与正文，否则 `gh pr create`。所有 `gh` 调用带 `-R <projects.<name>.repo>`。标题按 `title_template`（`{title}`、`{version}`，版本未变时只用标题），正文含摘要、类别与理由、版本决定、检查结果、评审状态与测试证据。
  - **合并**（仅 `auto_merge = true`）：要求独立评审 `pass`（`require_review`）→ 门禁 `delivery.merge` → 轮询 `gh pr checks` 直至全部 `pass`/`skipping`（失败则不合并、记说明；超时挂起，批准再查；可被 `interrupt` 中止）→ 锁内重新 fetch 基线：若基线版本已变（并发 PR 先合并），回到准备步骤重新合入基线、重算版本、跑检查、推送、更新 PR 并再等 CI（至多 3 次）；否则 `gh pr merge <n> --<method> --match-head-commit <已测 SHA>`，再以 `gh pr view` 记录实际合并 SHA。
  - **状态与恢复**：`local`（本地开发完成）→ `pr_open`（PR 已创建）→ `merged`（已合并），连同分支、基线 SHA 与版本、推送 head、PR、检查、CI、合并 SHA、尝试次数与历史按任务 `correlation_key` 存入 `deliveries`，每完成一步即落盘。任何可恢复失败（fetch、冲突、检查、推送、`gh`、CI 超时、`defer`）都返回 `Suspend`（检查点 `stage = delivery_pending`，提示含当前交付状态），批准只重试交付步骤并从已记录状态续接（不重复推送、复用 PR、采纳他人已合并的 PR 且不再加版本）；拒绝则按当前状态交付并注明 `delivery declined`；挂起期间到达的跟进与批准一起触发重新开发、评审与交付。交付中被中断抛 `DeliveryInterrupted`，SDE 转为 `CancelledError`，不写 Outbox。
  - **认证**：`git`、`gh` 与检查命令的环境剥离 `GH_TOKEN`、`GITHUB_TOKEN`、`GH_ENTERPRISE_TOKEN`、`GITHUB_ENTERPRISE_TOKEN` 并关闭交互提示，由宿主机自身的凭据（`gh auth login`、git credential helper、SSH agent）或部署配置的可信包装命令（`git_command` / `gh_command`）在进程外认证，daemon 不持有 GitHub token。
  - **版本规则**：本仓库的规则在 `docs/process/versioning.md`，经 `guidance.toml` 按 `versioning` / `release` 活动（或评审 diff 触及版本文件）选取；纯测试任务不加载其正文。开发派单模板在 `docs/dispatch/`（`sde-task.json`、`sde-task.drive.md` 显式 `executor_id = sde`；`review-task.json` 用 `code-reviewer`）。
- **Orca 可见执行**：模板的 `orca_agent` 指定 Orca 管理的 agent。项目使用 Orca worktree 时，同一 Hibernaut 会话的后续事件回到已绑定的对话（`OrcaVisibleRunner`，`adapters/executor_cli/orca.py`）。绑定存在 SQLite `terminal_bindings` 表（键为 `session_id`，记录 `executor_id`、`agent`、`workdir`、终端 `handle`、进程 `incarnation_id` 与原生会话 ID），原生会话 ID 同时写入 `sessions.executor_session_id`，会话换了 `session_id` 也能按它找回绑定。每轮按顺序选择：
  1. **新开**：会话没有本执行器的绑定（且未带原生会话 ID）时 `orca agent launch --surface terminal` 在后台标签页提交，按回执记录终端句柄与 `incarnationId`。
  2. **复用**：绑定终端仍在 `orca terminal list` 中、`incarnationId` 与 `agentIdentity` 都一致时，用 `orca terminal send --enter` 投递到原对话（`terminal show` 的 `orphaned` 只表示尚无可见窗格，不作存活依据；同句柄换了进程视为另一个对话）。
  3. **恢复**：终端已关闭但有原生会话 ID 时，`orca terminal create --command "<command> --resume <id>"` 新开终端，等 `tui-idle` 并确认 `agentIdentity` 后再投递。
  4. **无法确认**：会话有绑定却既无存活终端也无原生会话 ID、工作目录变了、恢复没能启动 agent 或终端拒收时，什么都不发送，返回 `Suspend`（检查点 `{"orca_continuation": "unconfirmed"}`）说明原因；批准后才新开对话，拒绝则跳过本轮。建表迁移时，已有执行器的旧会话各补一条无终端、无原生 ID 的绑定，因此升级前跑过的会话走这一步而不会被当成新会话。
  原生会话 ID 不靠 agent 自报：每轮结果文件所在的临时目录名唯一且写在投递的 prompt 里，执行器在 Claude Code 转录目录（模板 `env.CLAUDE_CONFIG_DIR`、daemon 的 `CLAUDE_CONFIG_DIR` / `ORCA_CLAUDE_CONFIG_DIR`、`~/.claude` 下的 `projects/*/<uuid>.jsonl`）里找含该标记的会话，恰好一个（或与已绑定 ID 相同）才确认，否则不写入并记警告。完成以每轮唯一的临时结果文件为准。投递后中断或超时则先确认原生会话 ID、再关闭本轮终端，下一轮走恢复；启动回执或投递回执不确定时转为 `Suspend` 供人工确认，不重复投递。
- **角色交互会话**（`OrcaVisibleRunner.converse()`，`adapters/executor_cli/orca.py`）：角色执行器的 `interactive`（默认 `true`；旧名 `visible` 仍可读，同一执行器两键都写则配置报错）只表示每次运行需要人可接入的交互会话；`false` 走非交互（headless）。会话由项目的 `terminal_backend` 打开，与 `worktree_backend` 解耦：取值 `orca | none`，`worktree_backend = "orca"` 的项目默认 `orca`（行为不变），`git` 项目默认 `none`，可显式设 `orca` 在 git worktree 里开 Orca 终端；目前只有 Orca 一种实现。组装根（`app/main.py`）按项目给角色执行器传 `terminal`：非交互为 `None`，有后端为共享的 `OrcaVisibleRunner`，缺后端为 `TerminalUnavailable(reason)`（`terminal_backend = "none"` 的项目，或未匹配任何 `[projects]` 的 Inbox 所用的兜底执行器）。交互角色绝不静默改走后台：缺后端时 SDE 以 `terminal_pending` 挂起（检查点存完整状态与待发提示词，什么都不启动），配置改好热加载后批准即重试（权限门禁照常再跑），拒绝输出 `stopped: interactive session declined`；独立评审输出 `review failed: interactive review not started: <原因>`，内置评审使 SDE 进入 `review pending`。后端挂接失败（无 `orca` 命令、Orca 不认识该 worktree、会话检查失败）以 `ClaudeCodeError` 报告 Orca 的原因，同样不回退 headless。标题标明角色与任务：`sde · <task>`、`code-reviewer · review of <task> round <n>`（内置评审）、`code-reviewer · review of <task>`（独立 `review_of` 事件）；执行器名与角色名不同时写作 `<id> (code-reviewer) · ...`。
  - **启动**：`orca terminal create --command "exec python -I claude_gate.py <spec>"`。`claude_gate.py` 在终端内按角色计费剥离或注入环境变量，先以 headless 探针（`-p`、无工具）读 `init` 做与 headless 相同的 `check_init` 校验（订阅无付费来源、api 只走代理、模型一致），结果写入本轮 `gate-status.json`，通过后 `execvpe` 成交互式 Claude Code：同一组 `--model --effort --permission-mode dontAsk` 与角色工具参数，指令放在 `--` 之后。
  - **结果回传**：启动器经 `--mcp-config` 挂上 stdio MCP 服务 `hibernaut_handoff`（`handoff_mcp.py`，`python -I`，仅标准库），`--allowedTools` 追加 `get_task` 与 `submit_result`。每轮在会话的 handoff 目录下建 `turn-*` 子目录，放提示词；终端只收到「调 `get_task(turn)`、完成后调 `submit_result(turn, …)`」的短指令。`submit_result` 的输入 schema 即角色 schema（另加 `turn`），服务端按 schema 校验，不合格返回错误让 agent 重交，合格则原子写入 `result.json`，`OrcaVisibleRunner` 轮询读取。`turn` 只接受 handoff 根目录下直接存在的 `turn-*` 名，无法指向别处。agent 不读写 handoff 目录，不需要 `--add-dir`：新加目录会弹出阻塞的信任对话框，而 worktree 本身的信任机制不受影响。
  - **续接**：SDE 按 `session_id` 绑定终端（`terminal_bindings`），后续事件、`needs_input` 的回答与修复轮投递到存活终端（`orca terminal send`），终端已关则 `--resume <原生 ID>` 新开；评审每次都是新会话，复审的上下文只来自提示词里的上轮结论与增量 diff。
  - **只读评审**：交互评审只放行 Read/Grep/Glob、只读 git 命令与两个 handoff 工具，Edit/Write/MultiEdit/NotebookEdit 全部拒绝；前后工作区指纹校验照旧。
  - **开发者通道**（`DeveloperPeerResolver`，`adapters/executor_cli/peer.py`）：独立派单的评审（`review_of` 事件）与开发者默认用 Claude Code 原生 `SendMessage` 对话，两条 `/events` 任务各自保留事件、会话、原生会话与结果。通信对象只按运行时自己记录的绑定确认：同一 `inbox_id` 下 `review_of` 对应的未关闭会话 → 执行器属于 `sde` 角色 → 该会话的 `terminal_bindings` 工作目录等于被评审 worktree、原生 ID 与会话记录一致 → Claude Code 会话注册表（`<config dir>/sessions/*.json`，进程存活）中该原生 ID 恰好一条、cwd 同为该 worktree、名字无其他存活会话占用。全部满足才把开发者的确切会话名与消息套接字（Claude Code 消息信封里 `from` 是发送方套接字 `uds:<path>`，`from-name` 才是会话名）写进评审提示词，并给评审追加 `SendMessage`、`ListAgents`（不加任何写文件工具，只读不变）；任一不满足则提示词写明原因、不给消息工具。评审消息以 `[review of <task>]` 开头，往来记录在 `developer_messages`，评审结论里列出 `Developer channel:` 与往来。SDE 提示词写明评审者地址 `<reviewer> · review of <task>`（即评审终端标题；同名会话仍存活时 Claude Code 会改名为 `<name>-<words>`，如同一任务的第二次评审，同样接受），只回复 `from-name` 符合且正文以确切 `[review of <task>]` 开头的发送方、附证据、评审期间不改工作区；SDE 的 `--disallowedTools` 含 `Agent` 与 `Task`，评审不能由 SDE 启动成子 agent。
  - **超时与中断**：`timeout_seconds` 含等人回答的时间；超时或中断关闭本轮终端、不写 Outbox，SDE 的原生会话 ID 保留在绑定里供下次 `--resume`；终端提前退出则报「exited before it returned its result」。
- **声明式配置与禁止静默回退 Demo**（`hibernaut.example.toml` + `app/config.py` + `app/main.py --config`）：使用标准库 `tomllib` 解析，仅存静态主检出、执行器模板（全部 `[executors.<id>]` 注册进 `AgentWorker`，`[projects.<name>]` 支持可选 `executor`）与凭据环境变量名，绝不存动态 worktree 路径。以 `--config` 正式启动时严禁静默回退 `RuleBasedDemoLLM`：若未配置 `[executors]` 或缺少 `default_executor`，则向 `stderr` 打印清晰提示并以 **`ingest-only`（仅入站控制面）模式**启动，不启动消费 Worker 池，所有新事件安全保持 `pending` 等待配置修复（仅无 `--config` 或显式传 `--demo` 时才允许使用 Demo 执行器）。HTTP daemon 热加载（`serve_configured`）不等进行中的 Run：先组装新配置（失败则保留当前配置），再停旧代的调度器、Outbox 投递与 GitHub/Drive 轮询（只等各自当前一轮结束，避免两个投递循环发同一条 Outbox 消息）并以新配置立即重启，启动新 Worker 池，然后 `AsyncWorkerPool.retire()` 退役旧池：旧池不再认领事件，排队中的 Inbox、此后到达旧池的唤醒（在途 HTTP 请求、旧代轮询）以及每个放锁的 Inbox 都转交当前池；进行中的 Run 用旧执行器跑完并照常写回（`AgentWorker.retire()` 只阻止它再领取、再 `fold` 新事件，未开始的已领批次退回 `pending`）。`ingest-only` 代的池不运行但照常收集唤醒，重载时同样退役转交，切换前已开始、切换后才落库的请求也会唤醒新池。监听 socket 不关，新请求改由新 handler 处理（`RequestHandlerClass` 原子替换）；端口变更时先起新监听，再关旧监听（等在途请求写完）。两池不会同跑一个 Inbox：池内 Worker ID 每代唯一（`pool-<n>-worker-<i>`），`AgentWorker` 在执行期间每 TTL/3 续租（Run 可超过 TTL），新池拿不到旧 Run 持有的租约，旧 Run 放锁后经转交唤醒新池处理积压事件。沿用同一条 SQLite 连接。停机（SIGINT/SIGTERM，含 `scripts/run_updating.py` 自动更新）沿用同一原则，由 `drain_pools()` 先排空：所有池（含已退役的）经 `AsyncWorkerPool.drain()` 停止认领（`retire()` 的转交改为丢弃唤醒，事件留在 `pending`，下一个进程启动时由 `pending_inbox_ids()` 扫描接手；无 `--config` 的 `build_daemon()` 池同样扫描），进行中的 Run 跑完并写回，且不再被新事件 `interrupt`（`AgentWorker.retire(interruptible=False)`，本进程不会重启被打断的批次）；排空期间 HTTP 入口照常入库返回 202（去重不变），调度器、Outbox 投递与 GitHub/Drive 轮询照常运行，不再热加载配置。所有池的 Run 结束后才依次关闭 HTTP（`shutdown()` 等在途请求写完）、停服务、退出。第二次 SIGINT/SIGTERM 不再等待：取消各池的 `run_forever()`，Run 按中断语义收尾（`supervise()` 终止子进程，不写 Outbox，已领事件退回 `pending`，放锁）。`run_updating.py` 照旧 `terminate()` 后 `wait()` 旧 daemon 退出，再复核检出并快进、`execv` 重启；它收到的第二次信号转发给 daemon。Orca 终端里仍在运行的任务不会在重启后接回。

## 5. 多 `inbox_id` Actor 分区并发与 `NewEventPolicy`

- **多 `inbox_id` 并发**：`AsyncWorkerPool` 跨 `inbox_id` 并行、同 `inbox_id` 单活互斥（`worker_leases` 主键即 `inbox_id`）、`Suspend` 立即放锁；`WorkspacePartitionRegistry` 强制禁止不同 `inbox_id` 挂载同一本地代码目录，全局 `global/instructions.md` 只读共享。
- **HTTP 入站与 SQLite 并发**：`WebhookHTTPServer`（`ThreadingHTTPServer`，`request_queue_size=128`）每请求一线程；`shutdown()` 等待在途请求全部写完 Inbox 后返回，停机（Worker 排空之后）与热加载换端口时关闭旧监听据此排空。`SQLiteDatabase` 只有一条连接，所有语句经同一把可重入锁串行；写操作走 `transaction()`（`BEGIN IMMEDIATE`），去重、租约等先读后写在线程间和共享同一文件的进程间保持原子；租约时钟在拿到写锁后读取，等锁时间不计入 TTL；`mark_done()` 按 SQLite 参数上限分段更新；文件库开启 WAL 与 `busy_timeout`。回收 worktree 时，`claim_for_reclaim()` 以读到的 `updated_at` 做比较并交换：进行中的 `reclaiming` 认领是排他的，只有超过 `reclaim_stale_after_seconds`（默认 600 秒，认领方已崩溃）的认领才可被接管；删除期间心跳线程定期续期认领（遇到临时的 `SQLITE_BUSY`/`SQLITE_LOCKED` 缩短间隔重试，不退出），慢删除不会被当作过期而被接管；删除成功后 `finish_reclaim()` 同样按认领做比较并交换，认领已失效时不删除被他人重新登记的记录；删除失败时 `release_reclaim()` 恢复原状态，可直接重试。
- **`NewEventPolicy` 三策略**：`defer`（默认，推迟到下一轮）、`fold`（回合间隙通过 `poll_folded_events()` 增量注入同会话/同关联键事件并统一 `mark_done()`）、`interrupt`（安全取消当前 Run/CLI 子进程，绝不向 Outbox 写半成品，原批次保持 `pending` 与新事件同租约合并重启）。

## 6. 三道防腐化门禁与术语基准

提交前与 `.github/workflows/ci.yml` 强制执行：`lint-imports`、`pytest -v`、`pyright`（strict，覆盖 `agent_runtime/core`、`agent_runtime/engine` 与 `switchboard`）。PR 上由 `scripts/select_tests.py` 按 Python AST 反向依赖图与资源映射仅跑受影响测试（加 `full-ci` 标签或合入 `main` 时跑全量兜底）。

术语定义以 [`docs/glossary.md`](glossary.md) 为唯一基准，本文不再重复定义。以下是术语在当前实现中的落地约束：

- **Inbox / `inbox_id`**：经项目的 `inbox_id` 规则（字符串为精确 ID；数组每项为整串匹配的正则）解析到至多一个项目；多个 inbox 可属同一项目，但各自持有 worktree。
- **Event**：认领计数 `attempts` 与 `last_error` 只存于 L3 `event_inbox` 内部列，跨重启保留，供毒丸止血与排障；执行前立即 `bind_session()`；抢锁先恢复孤儿 `processing`。
- **`session_id`**：委派出的子会话另记 `parent_session_id`；轮换标 `archived`（新会话继承 `parent_session_id`），结案标 `closed` 且引用归零触发回收。
- **`correlation_key`**：同时作为 `workspaces` 表动态 worktree 复用键。

## 7. Switchboard（Phase 1 + Phase 2 Relay + Stage A/B 接入）：外部事件归一化交换机

`src/switchboard/` 是与 `agent_runtime` 并列的独立包（过渡期单仓多包）。`.importlinter` 的 `switchboard-zero-business-deps` 契约禁止它导入 `taskboard`、`agent_runtime`、`runner`、`memory_hub`，`tests/test_switchboard_core.py` 另用 AST 检查它只依赖标准库与自身。

- **纯被动入站（Pure Push-in）**：只接收推送（GitHub Webhook、飞书事件与卡片回调、MCP 工具调用），不内置 Poller 或 Cron；定时任务由外部 Cron 调 MCP `submit_work(source="timer")`。命名统一为 Inbound / Outbound。
- **统一信封 `CanonicalEvent`**（`envelope.py`）：`@dataclass(frozen=True, slots=True)`，`event_id = "evt_" + ULID`，`metadata` 构造期冻结为 `MappingProxyType`（浅层只读，必须可 JSON 序列化）。`validate_envelope()` 按 `event_type` 校验必填顶层字段与 metadata 键；`execution.reported` 的 `outcome_kind` 只允许 `emit/suspend/error/done`（Silent 不上报）。
- **去重键是业务指纹**：`inbound_events` 的 `UNIQUE(source, external_id)`。GitHub 用 `issue:{repo}#{num}:{action}:{updated_at}` / `pr:...` / `comment:{id}`（PR review 为 `review:{id}`，review comment 为 `review_comment:{id}`），不用 `X-GitHub-Delivery`，所以 Redeliver 换新 UUID 仍判重；飞书卡片审批用 `approval:{approval_request_id}`（不含 decision），二次点击（即使改点拒绝）被丢弃并返回首个决定的只读卡片。
- **入站管道**（`pipeline.InboundPipeline`）：校验信封 → 同一事务内 `INSERT OR IGNORE` 入 `inbound_events` 并按路由表写 `delivery_log` → 唤醒投递线程。401（验签失败）、400（缺字段/信封不合法）、413（超过 `max_body_bytes`）只写旁路审计与 stderr，不落表。`AuditSinkPort` 异常降级为 stderr，不中断主链路。
- **声明式路由**（`router.py`）：`work.opened/updated → taskboard`；`work.closed → taskboard + hibernaut`；`work.ready / conversation.message / approval.decided → hibernaut`；`execution.reported → taskboard + switchboard.outbound`。scope 由 `[routing]` 的 `github_repos` / `feishu_chats` 映射，未命中按 `unmatched_policy` 回落 `default_scope` 或忽略。
- **投递**（`DeliveryWorker` + `ConsumerTransport`：Phase 1 的 `InProcessTransport`、Phase 2 的 `WebSocketRelayTransport`，或二者组合的 `CompositeTransport`）：同 `(consumer_id, scope)` 严格队头保序，队头处于 `retry`/`dead_letter` 时只阻塞该队列。`nack`/`timeout`/异常按 `retry_backoff_seconds`（默认 5/15/45/135/405 秒）退避，重试次数等于退避表长度，最后一次重试仍失败（默认共 6 次尝试）转 `dead_letter`，并经出站网关向 `dead_letter_alert_channel/target` 发告警；`offline` 保持 `pending` 且不计次数。`replay_delivery(event_id, consumer_id)` 只接受 `dead_letter`/`retry`，重置为 `pending, attempts=0, next_retry_at=now`。
- **出站网关**（`outbound/gateway.py`）：`outbound_messages` 的 `UNIQUE(idempotency_key)` 防重发；每个 `(channel, target)` 一个令牌桶（`rate_limit_per_target_rpm`），限流只推迟不计次数；可重试失败（5xx/429/网络）退避，超过 `max_retry_attempts` 或 4xx 标 `failed`。`execution.reported` 自动转换：`suspend` → `approval_channel`（默认飞书 `approval_target`）审批卡，按钮 value 打包 `approval_request_id/decision/correlation_key/scope/session_id`；其余回复到 `correlation_key` 的来源（GitHub Issue/PR 评论，支持 `add_labels`/`remove_labels`；飞书单聊或话题回复）。渠道插件经 `CredentialBrokerPort.issue_ephemeral()` 取短期令牌，HTTP client 可注入。
- **SQLite**（`store_sqlite.py`）：WAL、`busy_timeout=5000`、`foreign_keys=ON`；一条连接在一把进程内锁下串行，写入用 `BEGIN IMMEDIATE`。三张表 `inbound_events`、`delivery_log`、`outbound_messages` 及索引 `idx_inbound_corr`、`idx_delivery_sched`、`idx_delivery_order`、`idx_outbound_sched`。
- **MCP 工具**（`inbound/mcp.py`，`Authorization: Bearer` 对 `get_webhook_secret("mcp")` 常量时间比较）：`submit_work`、`post_message`、`decide_approval`、`report_execution`、`replay_delivery`。`report_execution` 供远程 Hibernaut 节点上报运行结果：固定 `source="hibernaut"`、`event_type="execution.reported"`，`actor` 缺省 `hibernaut`，`occurred_at` 归一为 UTC（缺省或无法解析时取服务端时钟），`event_id` 由服务端生成；`scope` 不回落 `default_scope`（报告属于节点自己的 inbox），缺 `scope`、`correlation_key`、`subject` 或 `metadata.run_id/session_id/outcome_kind` 时按信封校验返回 `invalid`（`isError=true`、不入表）。随后走标准 `InboundPipeline`：按 `(hibernaut, external_id)` 幂等去重，重复上报返回 `duplicate` 与首个 `event_id`，新事件扇出到 `taskboard` 与 `switchboard.outbound`。
- **HTTP**（`http_server.py`）：单端口 `ThreadingHTTPServer` 挂 `/webhooks/github`、`/webhooks/feishu`、`/mcp`、`/healthz`；按 `Content-Length` 先拒超限请求，入库后立即返回，不等下游。组装根是 `switchboard/app.py`（`python -m switchboard.app --config switchboard.toml`）。

### 7.1 Phase 2：RelayHub 与 Relay Agent 长连接推送

私网或本机（如合盖休眠的 Mac）上的消费方无法被公网回调，改由消费方主动外连 `wss://<host>/ws/relay`，Switchboard 经这条长连接推送事件。仍只用标准库：RFC 6455 握手与帧编解码在 `relay_protocol.py` 里手写，TLS 用标准库 `ssl`（Agent 侧）或由前置反代终结（Hub 侧）。

- **帧协议**（`relay_protocol.py`）：WebSocket 只走文本帧，每帧是一个带 `type` 与 ISO-8601 UTC `ts` 的 JSON 对象：`hello`（Agent → Hub：`consumer_id`、`token`、`agent_version`）、`welcome`（Hub → Agent：`consumer_id`、`conn_epoch`、`heartbeat_sec`、`ack_timeout_sec`）、`push`（`conn_epoch` + 完整 `CanonicalEvent`）、`ack` / `nack`（`conn_epoch`、`event_id`，`nack` 另带 `error`、`retryable`）、`ping` / `pong`（`conn_epoch`）。自定义 Close Code：4001 鉴权失败或首帧超时，4009 被同 `consumer_id` 的新连接取代。客户端帧必须掩码，控制帧不超过 125 字节，单消息上限沿用 `[http] max_body_bytes`。
- **鉴权**（`relay_hub.RelayHub`）：建连后 `auth_timeout_sec`（默认 5 秒）内必须收到 `hello`；Token 与 `CredentialBrokerPort.get_webhook_secret("relay")` 常量时间比较，未配置密钥一律拒绝。超时、首帧不是 `hello` 或 Token 不符都以 Close 4001 关闭，并经 `AuditSinkPort` 记 `relay/auth_timeout` 或 `relay/auth_failed`（不含 Token）。Agent 侧 Token 经 `CredentialBrokerPort.issue_ephemeral("relay")` 申领。
- **`conn_epoch` 防脑裂**：同一 `consumer_id` 每次握手成功在一把锁内递增 `conn_epoch` 并替换在线路由表，`welcome` 发出前该连接不接收任何推送或心跳。旧连接的未确认推送按 `offline` 交还 Worker（回 `pending`、不计次数），随后以 Close 4009 关闭；旧连接在 2 秒宽限期内发来的帧、以及新连接上携带旧 `conn_epoch` 的 `ack` / `nack` 一律丢弃并记 `relay/stale_frame`。
- **`WebSocketRelayTransport`**（实现 `ConsumerTransport`）：消费方不在线返回 `offline`；同一 `(scope, consumer_id)` 最多 1 条在途（队头保序），单连接在途上限 `max_in_flight`（默认 8），不同 scope 可并行；窗口占满等到 `ack_timeout_sec` 仍无空位时按 `offline` 返回（推送未发出，不算一次尝试）。推送后 `ack_timeout_sec`（默认 15 秒）内无 `ack` 判 `timeout`，记 `relay/ack_timeout` 并立即补发一次 `ping` 做健康检查。同一 `event_id` 的迟到 `ack` 可以结算下一次重试，因为事件确已被处理（At-Least-Once）。
- **心跳与离线摘除**：Hub 每 `heartbeat_sec`（默认 20 秒）向每条连接发 `ping`；任意入站帧都算存活，连续 2 次心跳间隔无入站（默认 40 秒）即摘除在线表（`relay/heartbeat_timeout`），未确认推送按 `offline` 回退 `pending` 等待重连。
- **离线不等于故障**：`offline` 保持 `pending`，不增加 `attempts`、不消耗死信重试额度；只有在线时的 `nack` / `timeout` 才进入 `retry_backoff_seconds` 退避与死信流程（含出站告警）。
- **重连零延迟补推**：`welcome` 发出后 Hub 回调 `on_consumer_connected(consumer_id)`，组装根把它接到 `DeliveryWorker.reset_offline_pending()`：`SwitchboardStore.reset_offline_pending(consumer_id, now)` 把该消费方因离线延后的 `pending` 行的 `next_retry_at` 置为现在（`retry` 行保持在线失败的退避），然后唤醒 Worker 按 `(scope, created_at)` 队头保序补推。若推送失败与重连同时发生，Worker 在写入离线延后之后会再执行一次重置。
- **Worker 并发**：每轮取出的待投递项各自是不同 `(consumer_id, scope)` 的队头，`[delivery] max_parallel` 个线程并发投递不破坏保序；未配置时 `in_process` 为 1（与 Phase 1 相同），`relay` / `hybrid` 为 `2 × max_in_flight`。
- **传输模式**（`[relay] transport`）：`in_process`（默认，Phase 1 行为）；`relay`：除内置 `switchboard.outbound` 外的消费方全部走长连接；`hybrid`：有进程内处理函数（内置或 `bus.subscribe`）的消费方走 `InProcessTransport`，其余（如 `hibernaut`、`taskboard`）走 `WebSocketRelayTransport`（`pipeline.CompositeTransport`）。`transport` 不是 `in_process` 时必须 `enabled = true`。
- **挂载**：默认与 `[http]` 同端口，`GET <path>` 带 `Upgrade: websocket` 时升级（不带返回 426）；配置 `listen_port`（可选 `listen_host`）则另起一个只服务该路径的监听。
- **Relay Agent**（`relay_agent.RelayAgent`，CLI `python -m switchboard.relay_agent`）：外连 `ws://` / `wss://` 后立即发 `hello`；收到 `push` 在线程池（默认 8）里调用注入的 `ConsumerHandler`，处理函数返回（即本地落盘完成）后才回 `ack`，返回 `nack` / `timeout` / `offline` 或抛异常则回 `nack(retryable=true)`；自动回应 `ping`；`3 × heartbeat_sec` 无任何入站帧视为半开连接主动断开。断线后按 1 → 2 → 4 → 8 → 16 → 30 秒（封顶）±20% 随机抖动退避重连，成功握手后退避归零；收到 4009 说明另一个同 `consumer_id` 的 Agent 接管，不再重连。

### 7.2 Stage A：Hibernaut 同进程桥接（`adapters/channels/switchboard_bridge.py`）

`hibernaut.toml` 的 `[switchboard]` 段默认 `enabled = false`，此时不启动 Switchboard，GitHub / 飞书 / MCP / Drive 旧通道行为不变（旧通道退场留待 Stage C）。开启后 `app/main.py` 启动时用 `load_config(config_path)` + `build_switchboard(..., credentials=EnvCredentialBroker(...))` 建同进程 Switchboard 并 `start()`，进程退出（SIGINT/SIGTERM）时 `stop()`。只有 L3 `adapters` 与 `app` 依赖 `switchboard`；L0/L1/L2 不导入它。

- **入站桥 `SwitchboardInboundBridge.handle_canonical_event`**（符合 `ConsumerHandler`，以 `consumer_id`（默认 `hibernaut`）`bus.subscribe`）：`CanonicalEvent` → `EventHandler.ingest(inbox_id=scope, source="sb:<source>", external_id=event_id, correlation_key=...)`。`external_id` 用 Switchboard 全局 `event_id`，At-Least-Once 重推命中 `(inbox_id, source, external_id)` 去重记为 `dropped`，仍回 `acked`；落库异常回 `nack`，由 `DeliveryWorker` 退避重试。payload 含 `event_type/subject/title/body/actor/external_id/occurred_at` 与原样 `metadata`，并把引擎读取的 `approval_request_id`、`decision`、`work_key`、`reply_channel`、`reply_target` 提到顶层（`approval.decided` 由此按 `approval_request_id` 恢复挂起会话）。
- **`work.closed` 联动**：入站桥给事件加 `action = "close_session"`，由 Worker 在 Inbox 租约内走既有的关闭流程：关闭该 `(inbox_id, correlation_key)` 会话，`count_active_by_work_key(work_key, inbox_id) == 0` 时触发 worktree 回收；找不到会话则只标记完成。不在投递线程里直接改会话，避免与正在运行的 Run 竞争（Run 结束时会把会话写回 active）。
- **出站桥 `SwitchboardChannelAdapter`**（实现 L1 `ChannelPort`）：Outbox 消息 → `execution.reported`（`source="hibernaut"`、`scope=inbox_id`、`actor="hibernaut"`、`subject` 取 metadata 的 `title`/`subject`，缺省 `Hibernaut update`，`body=content`），metadata 带 `run_id/session_id/outcome_kind`，并透传 `approval_request_id`、`reply_channel`、`reply_target`、`task_id`、`executor_id`、`error_kind`、`notify_channels`、`approval_channel`、`approval_target`。`outcome_kind` 取 metadata 显式值，否则按 `kind`：`emit → emit`、`approval_request → suspend`、`silent →` 不发布、其余 → `error`。`external_id = outbox:<message_id>`，没有 `message_id` 时用 `(inbox_id, content, metadata)` 的确定性哈希，Outbox 重试不会重复发卡。发布回调 `publish: Callable[[CanonicalEvent], Any]` 由构造函数注入（Stage A 为 `switchboard.bus.publish`，Stage B 为 `SwitchboardMCPPublisher.publish`，翻译逻辑不变）；返回 `invalid` 时抛异常，由 `OutboxDispatcher` 记失败并重试。缺 `correlation_key` 或 `session_id` 的消息（如 worktree 回收告警）没有可回复的来源，交给 `fallback`（原飞书/控制台通道）。
- **Outbox 元数据**：`AgentWorker` 写 Emit / Suspend 时补齐 `run_id`（每批一次）、`correlation_key`、`session_id`、`outcome_kind`，Suspend 另带 `approval_request_id`，并透传批内事件 payload 的 `reply_channel` / `reply_target`；原有 `kind`、`request_id` 不变。另写嵌套键 `task_context`（L0 `TASK_CONTEXT_KEY`）：`title`（批内 payload 的 `title`，否则 `drive_file_name`、`issue.title` / `pull_request.title`）、`source`（批内首个非审批事件的 `source`）、`executor_id`、`status`（`Emit.status` 或 `awaiting_approval`）。嵌套而不放顶层，Switchboard 透传的顶层 `title` / `executor_id` 与 `subject` 不受影响。`DriveResultWriter` 对带 `run_id` 的 Emit 不再经通道写 Drive（已由 `handle_run_report` 写入），避免重复。
- **凭据**：Stage A 的 `EnvCredentialBroker` 让 Hibernaut 进程持有 `SWITCHBOARD_*` 令牌，与「零真实密钥」契约有缺口。启动时把这些变量从 `os.environ` 移到 broker 私有副本，执行器子进程继承不到；Stage B 的 `relay` 模式把 Switchboard 移出 Hibernaut 进程，GitHub / 飞书等渠道密钥只留在远程 Hub。
- **重载**：`[switchboard]` 段变化需重启；其它配置热重载时重新 `subscribe`，入站桥指向新的 daemon。

### 7.3 Stage B：跨网 Relay 模式（`adapters/channels/switchboard_relay.py`）

`[switchboard] mode = "relay"` 时 Hibernaut 不在进程内拉起 Switchboard，改连远程公网 Hub。配置 `relay_url`（`ws://` / `wss://.../ws/relay`）与 `mcp_url`（`http://` / `https://.../mcp`），`enabled = true` 时两者必填，scheme 不符或缺主机名在加载时报错；可选 `ca_file`（私有 CA，相对 `hibernaut.toml`）。`config_path` 只在 `in_process` 模式使用。`mode = "in_process"` 与 `enabled = false` 的行为与 Stage A 相同；旧 L3 通道（GitHub / 飞书 / MCP / Drive）保留，退场留待 Stage C。

- **`SwitchboardRelayLink`**（L3，组合 `switchboard.relay_agent.RelayAgent` 与 `switchboard.mcp_publisher.SwitchboardMCPPublisher`）：对外与进程内 `InProcessEventBus` 同形（`SwitchboardBus` Protocol：`publish` / `subscribe`），组装根经 `switchboard_bus()` 统一取用，`SwitchboardInboundBridge` 与 `SwitchboardChannelAdapter` 两种模式共用、不改。
- **下行**：首次 `subscribe(consumer_id, handler)` 才启动 RelayAgent 外连，保证推送到达前入站桥已接好；热重载再次 `subscribe` 只在锁内替换处理函数，不重连（连接与 `conn_epoch` 不变）。`consumer_id` 与连接时不同则拒绝。处理函数返回（`event_inbox` 落库完成）后 Agent 才回 `ack`，落库失败回 `nack` 由 Hub 退避重推；重连、退避、4009 接管、半开检测沿用 7.1。
- **上行**：`SwitchboardMCPPublisher.publish(event)` 只接受 `execution.reported`，以 `tools/call report_execution` 发 JSON-RPC 到 `mcp_url`，参数是信封字段（不含本地 `event_id`），解析 `structuredContent` 为 `IngestResult`。网络错误、非 200、非 JSON、JSON-RPC `error`、工具错误一律抛 `PublishError`（不回显 Hub 响应体），由 `OutboxDispatcher` 记失败重试；`invalid` 作为结果返回，`SwitchboardChannelAdapter` 照 Stage A 抛错。`external_id = outbox:<message_id>` 不变，Outbox 在 Hub 已收下但响应丢失后重试，Hub 判 `duplicate`，不会重复发评论或卡片。
- **凭据**：节点只持两个客户端令牌，`SWITCHBOARD_RELAY_TOKEN`（`issue_ephemeral("relay")`，Hub 侧对应 `SWITCHBOARD_RELAY_WEBHOOK_SECRET`）与 `SWITCHBOARD_MCP_TOKEN`（`issue_ephemeral("mcp")`，Hub 侧对应 `SWITCHBOARD_MCP_WEBHOOK_SECRET`），启动时与其他 `SWITCHBOARD_*` 一起移出 `os.environ`，执行器子进程继承不到；任一缺失则启动失败。非回环地址用 `ws://` / `http://` 时打印明文告警。
- **进程**：`--mcp-stdio` 伴随进程不建链接，否则第二个同 `consumer_id` 的 Agent 会以 4009 顶掉 daemon 的连接。退出时 `stop()` 发 Close 1000 并停止 Agent。
